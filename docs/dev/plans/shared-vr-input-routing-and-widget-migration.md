# Shared VR input routing and widget migration

## Goal

Provide one reusable VR input and widget foundation for the shipped desktop and third-party plugins. Migrate the wrist menu, runtime manager, reload, and workspace switching onto that foundation, with one desktop keyboard instance serving both application input and Lua text fields and no physical keyboard or mouse binding required for a session workflow.

## Implementation Summary

Evolve `lunette/focus` into the single arbiter of keyboard input targets. Keep native seats and sinks as application-delivery mechanisms, but represent the current target as a discriminated native or Lua receiver. Add an owner-scoped routing client for keyboard sources and a surface-local input adapter with capture/cancellation.

Implement a public UI library, not only internal manager helpers. Its neutral typed API is `@lunette-contracts/ui`; its built-in implementation is `@lunette-plugins/ui`, providing `lunette/ui`. It supplies buttons, single-line text fields, choices, scrollable lists, panels, and custom regions. The wrist menu, manager, and third-party example all consume that public API. The UI library is skinnable through schema-derived style/theme values and replaceable draw hooks. The entire UI provider is also substitutable through the same capability contract, independently of skinning. Provider-substitution and skinning scenarios are required acceptance tests. A full layout engine is out of scope.

The operator explicitly selected inclusion of the small widget library. The operator also accepted automated completion with actual headset readability, GPU presentation, and controller ergonomics left open as a named manual follow-up. Those aspects must not be reported as verified.

Touch points:

- Contracts: `lua/lunette-contracts/focus.luau`, `frame.luau`, `keyboard.luau`, `vocabulary.luau`, `surface.luau`, `interaction.luau`, `keys.luau`, and new `ui.luau`, `menu.luau`, and `keyboard-display.luau` contracts.
- Providers: `lua/lunette-plugins/focus/`, `frame/`, `interaction/`, `laser/`, `keyboard/`, new `ui/` and `menu/` providers, and existing inspection vocabulary.
- Desktop: `desktop/input`, `desktop/keyboard`, `desktop/manager`, `desktop/bindings`, `desktop/workspaces`, desktop composition/settings, and their tests. - Examples and tooling: migrate `examples/keyboard/tiny.luau`, keyboard/development examples and tests, binding-based desktop examples, strict checker fixtures, and generated native declarations if the grapheme helper is added as specified below.

### 2. Make focus the sole keyboard-route arbiter

Evolve `lua/lunette-contracts/focus.luau` and the provider. Bump the capability schema when the service contract changes; migrate every in-tree provider/consumer together. Do not add an independent UI-focus service overlaying the old native grants.

Define these concepts in the contract, with concrete declarations and documentation:

- `Receiver`: plain `key(event) -> boolean`, `text(text) -> boolean`, and optional focus notification callbacks. Key events are evdev key activations with an immutable modifier list and source/repeat metadata. They are not key-down/key-up streams. Committed text is valid UTF-8 transferred intact. Key and text are distinct operations.
- `Target`: `{ kind = 'native', seat: Seat?, sink: Sink }` or `{ kind = 'local', receiver: Receiver, keymapSeat: Seat?, wantsKeyboard: boolean }`. `wantsKeyboard` is immutable target metadata; text fields set it true, nontext regions false. Focus notifications carry the live target identity, revision, kind, and wantsKeyboard as readonly data; they do not invoke a getter. A widget receiver is never a native Sink. Native `seat=nil` retains default-seat delivery semantics.
- `TargetHandle`: an owner-bound registration, created with `service:register(owner, target)`. It exposes `dead`, `focus()`, `blur()`, and `destroy()`. Disposing/owner unload invalidates it and clears its callbacks before notification. Multiple fields of the same owner have separate handles.
- `focused()` returns the active route handle or nil; `revision()` and `onChanged(owner, listener)` expose deterministic route changes without invoking receiver callbacks or native getters during inspection.
- `newSource(owner, options)` returns an owner-bound input source with `key`, `text`, `keymapSeat`, `reset`, and destruction. It owns native key/modifier cleanup, observes route changes immediately, and snapshots one route generation for each operation. `options.nativeTarget` retains the existing keyboard `Options.target()` override as a native-only adapter; it is subordinate to a currently focused local target. No override can bypass widget input isolation.

The provider publishes one current route, not a stack. Focusing a different target changes the revision; refocusing the identical live target is idempotent. Blurring/destroying an older handle does not clear a newer handle. Blurring/destroying the current target produces no current target; it does not resurrect a previously focused widget or application. Explicit subsequent interaction refocuses an application. Native focus of other seats remains per-seat, as today, even though the shared keyboard has one current route. Replace `focus/holders.luau` with a tagged-route state machine that records both the global current route and a separate authoritative handle per native seat. Focusing a window route establishes native focus before claiming authority; false window-focus results refuse the transition and leave the previous state intact. Blurring/destroying a native handle clears that seat only if it remains the authoritative handle, even when it is not globally current; a superseded handle can never clear a newer holder. Clearing a window seat attempts the native inverse and reports refusal without restoring an old route. Native-to-native selection on another seat retains the first seat's authority until explicitly blurred/destroyed. Switching from a native target to a local target clears only the former route's authoritative seat, without altering pointer hover or unrelated seats. Host-domain sinks are valid keyboard delivery routes but do not attempt `Seat:setFocus(hostSink)`, which the public native API does not support. Add a narrow public `lunette.defaultSeat()` accessor in the existing native Lua seat/module surface (no compositor change), generate its declaration, and use it for establishing/clearing default-seat focus consistently. Do not guess the default from `lunette.seats()` order. Normalize `seat=nil` and explicit `defaultSeat()` to the same stable seat-id authority identity before equality/bookkeeping; fresh wrappers with the same id cannot acquire competing authority. Window-route activation, including nil-seat activation, calls `Seat:setFocus(intendedSink)` before committing authority; `Sink:key` delivers to the seat's existing focus and does not establish it. Delivery can still pass nil to preserve the optional-seat API. A `nativeTarget` override is registered/reconciled by the same arbiter as a source-owned native target and establishes window focus through this transition operation before key/text dispatch. It cannot change focus during old-target cleanup or supersede a local route. Add `focus_nil_and_explicit_default_seat_share_authority` under AC.2 for both supersession orders/fresh wrappers; extend the native nil-seat integration test to assert Focus(intended window) precedes Key/text, and blur queues Focus(nil). The accessor is required by this migration and tested through the production native API. Native route equality uses stable Seat.id/Sink.domain and window/monitor identity, not incidental Lua userdata wrapper equality. Add shared-seat supersession, independent-seat disposal, host targets, nil/default-seat, and false window-focus tests to AC.2 and AC.5.

Native pointer focus uses target registrations owned by the interaction activation/pointer, preserving the existing explicit `Pointer:focus(sink)` operation and the configured `focusOnPress` policy. Repeated application clicks on the same sink after a widget was focused must still refocus that application. Do not rely on changes to the old seat/sink pair alone. Route registrations/reuse must not grow without bound on every pointer frame or click.

Source delivery rules:

1. Snapshot target and revision once. Never deliver a continuation into a replacement target after a receiver changes focus or unloads itself.
2. Virtual key activation offers `receiver.key` first. If consumed, no text is inserted. Otherwise, for a permitted printable key, translate with the same live seat used for legends and offer `receiver.text` once. Physical delivery uses committed LÖVR text events and must not translate a printable key again.
3. Local rejection or callback failure never falls through to a native target. Report callback failures with the target owner's diagnostic context and preserve isolation. Return an explicit consumed/unhandled/failed result internally; never equate failed with unhandled. Do not swallow errors to keep dispatch alive without reporting them.
4. No implicit text fallback for control, logo, or plain Alt command chords. Shift, lock modifiers, and `mod5`/AltGr can produce text. Reject C0/C1 control-character fallback. Explicit text actions may deliver committed text independent of a keymap.
5. Keymap choice is explicit local seat if live, then the recently selected native target seat if live, then the first live session seat. Legends and translation share this choice. No key label, hexadecimal symbol, or assumed US layout becomes inserted text. No live seat means unhandled key-to-text translation, not invented text.
6. Native delivery keeps keycodes/modifiers and current `strokeFor`/`typeText` mechanics; it does not become local text delivery. Respect false native refusal and propagate a structured failed/refused result instead of claiming success. Attempt native key-up and modifier-reset inverses independently on failure.
7. Every route change, target death/loss, source disposal, and provider shutdown releases old native key/modifier state before the next route can receive input. Sources clear state before inverses so reentrancy cannot double-release. Announce route changes after committing arbiter state; a cleanup error is reported and blocks unsafe delivery rather than reverting to an old target.
8. Keyboard latches and locks clear immediately on a route change, not only on the next valid sink. A normal activation consumes one-shot latches even if unhandled or failed; locked modifiers persist only within the same route. Receiver exceptions still run source cleanup. Invalid retained handles remain inert.

Keep focus inspection owner-scoped and callback-free: current route kind, registration owner, revision, keymap seat identity when safely available, source count, and failure state. Do not expose receiver closures. Test provider replacement and substitutions through the public capability.

### 3. Add complete surface pointer events and cancellation

The current interaction provider sends identical surface press callbacks for every button, has no UI scroll callback, and conflates withdrawal with ordinary release (`interaction/init.luau:166-208,249-267`). Introduce an optional typed `Surface.onPointer(event)` callback in the shared vocabulary. Its discriminated events include enter, move, leave, press, release, scroll, and cancel; carry the real pointer identity, button for press/release, logical coordinates when available, captured/inside flags, scroll deltas, and a closed cancellation reason. Keep the existing callbacks as a compatibility fallback for external surfaces; a surface defining `onPointer` receives that protocol only, never duplicate legacy callbacks. Migrate in-tree interactive surfaces to it. Native sink delivery remains separate and unchanged.

Capture belongs to one pointer/button gesture, not global hover. After a surface press, moves/releases reach the original pressed surface even when another surface is hovered. Add optional `Surface.project(origin, direction)` to compute unbounded local coordinates for captured motion while keeping `raycast` bounds for ordinary hit testing. Add a pure `quad.project` alongside `quad.hit`; `hit` is a bounded wrapper. Native panel pointer delivery does not need this new projection callback.

Cancel and release are distinct. Tracking loss/`withdraw`, pointer destruction, dead/withdrawn surface, provider replacement, UI-panel hide, control removal/disable, and a grip beginning a panel grab terminate active UI captures. Clear state before callbacks and attempt all cancellations before reporting combined failures. A held trigger after cancellation cannot reactivate a control until an observed release followed by a new press edge. On tracking loss, quarantine button edges until tracked input has reported all relevant buttons up; do not treat reacquisition with a held trigger as a new press. Update `lua/lunette-plugins/laser/init.luau` and its tests as well as interaction withdrawal, since the laser currently calls `Pointer:withdraw()` whenever its input reader returns nil. Hover leave alone does not cancel a capture. Grip-driven spatial grabbing takes priority and cancels a UI gesture before moving the surface. Preserve haptics and native pressed-sink release semantics.

Expose scroll deltas to Lua surfaces using the existing tuning/dead-zone scaling exactly once. Do not deliver both native sink scroll and UI scroll for the same hit. Keep two pointers independent; a control may explicitly declare exclusive capture and the adapter enforces it.

### 4. Build a small replaceable UI provider

Add `lua/lunette-contracts/ui.luau` and `lua/lunette-plugins/ui/` with a schema-configured provider requiring focus and surfaces. The contract is neutral and usable by a substitute provider. Keep the file tree by responsibility (`panel`, `input`, `button`, `text-field`, `choice`, `list`, `draw`, `config`, and their tests), not generic helper categories.

Public shape:

- `ui.Service:newPanel(owner, options) -> Panel`. Options describe world pose/size, logical size, visibility, grabbing, immutable style settings, and an optional drawing hook. The panel is an owner-scoped surface, offered once by the UI provider. The caller draws the returned panel in its frame callback; the provider does not impose a frame order.
- `Panel` exposes dead-aware pose/size/visibility setters, `draw(pass)`, and owner-scoped factories `button`, `textField`, `choice`, `list`, and `region` for custom input/rendering. Returned control handles have `dead`, `setBounds`, `setEnabled`, `destroy`, and their specific value/list setters. A custom region uses the same pointer/focus machinery without being forced into a widget renderer.
- Bounds use one documented top-left logical coordinate system. Hit testing uses half-open rectangles and deterministic registration/z order. Rendering and input share the same rectangles. Negative/nonfinite sizes fail with named diagnostics; zero-area/disabled controls never activate.
- Give panels stable production names and controls stable owner-local ids, rejecting duplicates. `ui.Service:panels()` returns readonly live panel handles; `Panel:describe()` returns detached, callback-free geometry: panel name/world pose/size/logical size/visibility, control id/kind/label/enabled, logical visible bounds after clipping, and immutable custom-region items. Descriptions carry provider generation/revision and no callbacks or mutable internal tables. This is a production custom-layout/diagnostic API, not a test click escape. Choice/list rows include stable item ids and only current visible hit bounds. Custom graph regions publish graph node/edge item ids and exact selectable rectangles/polyline routes from the same pure graph geometry used by input/rendering. Custom renderers cannot change the declared input geometry silently; explicit bounds/item updates change description revision. The harness discovers current panels/controls/items through this API, transforms logical positions/ray paths with the described world pose, then drives actual pointers. It never holds geometry across a generation change. Add `vr_ui_fixture_discovers_dynamic_control_and_rediscovery_after_reload` to AC.1, proving independent discovery of dynamically created controls and new-generation requery. AC.10–12 scenarios reuse this discovery path for menu/manager fields/options/graph routes, including clipped/scrolling content.
- Shared adapter owns per-pointer hover/capture and routes events to controls. It uses target handles for text focus, not direct global key subscriptions. Rebuilding a manager toolbar must retain handles by identity or explicitly dispose them; it cannot leak a target every update.
- Buttons activate once on a primary-button release inside the original control after a press, not on unrelated releases or cancel. Expose hovered/pressed/enabled state to drawing. Secondary buttons do not duplicate activation. Haptic policy is configurable.
- Text fields are single-line with a value, caret, selection, onChange, onSubmit, and onCancel. Support insertion, replacement of selection, left/right/home/end, Backspace/Delete, select-all, and pointer caret selection. The shared keyboard supplies the same evdev control activations as other input sources. Do not add automatic system clipboard reading, rich text, password policy, multiline editing, or IME/preedit. Field validators report errors without discarding the retained draft. Manager numeric parsing remains in its schema editor.
- Choices are immutable-value lists with a selected item and onChange; opening options and choosing them is entirely pointer-accessible, including long lists. Lists have stable item identities, selection, paging/continuous scrolling, and an overflow indicator. Their viewport clips rendering and hit testing consistently; offscreen items are not clickable.
- Panel hiding/removal and control destruction/disable cancel captures and blur their targets immediately. Clicking a nonfocusable toolbar button preserves the current field unless the action explicitly ends editing. Clicking another text field changes the route. Keyboard and menu surfaces are focus-transparent; they do not steal field focus merely because they receive a pointer press.

The public UI library is skinnable and provider-substitutable. Its schema-derived `theme` exposes colours, typography size, spacing, border/focus/selection/error treatment, and haptic tuning as immutable settings with documented override precedence: provider theme, panel overrides, then control overrides. Geometry-affecting theme values are resolved once into shared production layout/hit/render bounds and descriptions; drawing cannot silently move the input target. `Panel:setTheme(overrides)` and `Control:setTheme(overrides)` replace immutable local overrides, recompute resolved theme/geometry, increment description revision, and cancel incompatible captures before the next interaction. Provider-level theme changes use normal configured-provider replacement; they do not mutate settings in place. Default drawing hooks at provider, panel, and control scope receive readonly visual state plus the base renderer, allowing replacement of visuals without replacing input semantics. Widgets have default rendering usable in VR. Hooks do not override input routing. A third-party implementation of `lunette/ui` can replace the entire built-in provider; consumers require only `@lunette-contracts/ui`, never built-in implementation types or private control state. Add `ui_theme_and_draw_hook_skinning_preserves_input` with a visibly different theme/custom renderer and `ui_provider_substitution_runs_unchanged_consumers` with an independently implemented compliant provider against the same menu/manager/example scenario subset. A forwarding wrapper around the built-in provider is not sufficient evidence of contract substitutability. Add safe pass push/pop restoration on success and draw errors, reuse the existing draw clipping conventions, and keep style tunables schema-derived. Do not add automatic layout, a global widget tree, DOM propagation, modal focus stacks, or implicit keyboard shortcuts. Custom UI remains possible through `region` and renderer replacement.

Unicode text editing must use extended grapheme boundaries rather than bytes or only code points. The tree has no grapheme helper. Add a small public native mechanism `lunette.textBoundaries(text) -> { number }` returning Luau-compatible one-based UTF-8 boundary offsets including the terminal offset, backed by pinned `unicode-segmentation = '=1.13.3'` (current verified docs: https://docs.rs/unicode-segmentation/1.13.3/unicode_segmentation/). Register and generate declarations normally; never edit `lua/lunette/init.luau` manually. Put policy (caret, selection, edits) in Lua. Rust validates UTF-8 and tests UAX #29 representative clusters; Lua uses the helper for edits. No compositor/vendor edits. Segmentation is a mechanism, not a native widget implementation. Document that full text shaping, bidi caret semantics, and IME composition are not provided by this first single-line control.

### 5. Route the existing keyboard and physical application delivery

`keyboard/service.luau` should use one focus input source for all pressKey, typeText, text actions, and chord actions. Remove duplicate native stroke/routing logic once covered by the source. Keep existing rows, layers, modifier configuration, layout legends, draw hooks, and per-owner keyboard instances. The keyboard service remains usable by custom compositions, but shipped desktop UI must reuse the one `desktop/keyboard` instance.

Change `desktop/keyboard` into a provider of a small `lunette/keyboard-display` contract in a neutral module: show, hide, toggle, visible, and dead-aware lifecycle. It lazily creates and reuses one keyboard, owns its surface offer/drawing, retains `placement` behaviour, and destroys it with its owner. Widgets request visibility through focus state (`wantsKeyboard` on a local target), not a direct dependency on the desktop consumer. Add `Options.onVisibilityChanged`, an owner-bound plain callback receiving readonly `{ visible, reason }` where reason is show, hide, user-hide, or destroy. All built-in and substitute keyboard providers invoke it on actual visibility transitions and destruction; built-in Hide calls the user-hide path. `Keyboard:setVisible` emits show/hide only when the state changes. Callback failure is reported to the keyboard owner, and state is committed before notification. Bump the keyboard capability schema and migrate tiny/split/rounded providers and checker fixtures. Do not poll private board state to detect Hide.

The keyboard-display contract exposes show/hide/toggle, isVisible, and owner-scoped onChanged with the same visibility reason plus the current local target identity when applicable. The display consumer records `manualVisible` and the auto-shown target identity. Menu Show sets manualVisible=true and places on a hidden-to-visible transition; Menu Hide or Toggle-to-hidden sets manualVisible=false and blurs only the matching current local target. Built-in user-hide does the same. Focusing a wantsKeyboard field shows the existing board, places it only on hidden-to-visible, and records the target identity. Field-to-field focus keeps the board pose. Ending editing hides only auto-shown visibility; a manually shown board stays visible for application input. A user-hide clears auto intent and blurs before handling notifications; guard the exact target/revision so focus-change reentrancy cannot reopen it or blur a subsequently focused field. A programmatic hide from auto-intent ending never blurs a newer target. Destruction/provider replacement clears display state and stale callbacks; the replacement display can auto-show only for a new live focus target, never a dead retained one. Field drafts remain retained on blur/user-hide, and clicking the field again resumes editing/showing the shared board. Cover built-in Hide, menu toggle, manual retention, field switching/pose, drafts, reentrancy, and substitute visibility notifications in AC.9.

Migrate `examples/keyboard/tiny.luau` to the same source contract so provider substitution can type into Lua fields as well as applications. Keep split/rounded keyboard hooks working. Update relevant checker fixtures, `dev` keyboard tests, and example desktop tests. Native-only `Options.target` remains supported via the source adapter with documented local-focus precedence.

`desktop/input` uses a focus source for physical application passthrough and generic focused-field key/text delivery. It registers delivery-phase handlers only; no manager/session shortcut is introduced. Define Source mode as `virtual` (key-to-text translation allowed) or `physical` (never key-to-text translation). Extend `keys.FROM_LOVR` with a complete explicit map for the supported LÖVR key-name enum to public evdev named codes; do not interpret platform scancode as evdev. Modifier query distinguishes right Alt as mod5 from left Alt as alt and includes Shift for receiver key activations. The complete map supplies all local receiver activations, but native application delivery sends only nontext/control keys and command chords from keypressed. Ordinary unmodified, Shift, lock, and AltGr printable native input uses the committed-text path only; never also send its mapped printable key stroke. For control/logo/plain-Alt chords, send one mapped native activation and suppress text under the command-modifier policy. Keypressed/textinput are not deduplicated by guessed correlation. Local text events forward the whole valid UTF-8 string; native application reverse mapping iterates scalars, not `gmatch('.')` bytes. Add `physical_native_printable_and_chord_delivery_once` under AC.3 with exact native logs for paired unmodified/Shift/AltGr input, command chords, repeat, and multi-scalar committed text.

LÖVR does not identify the originating key of a text event. Add a conservative physical-input batch token to the frame contract/provider: key/text events dispatched between two `lovr.update` boundaries share a batch id, and the first event snapshots the focus revision. Add `beginBatch` to the physical source and metadata to key/text dispatch. Poisoning never reroutes text to a replacement target/application. Unhandled ordinary printable activations do not poison and committed text can then be inserted once. Extend `frame.install` event payloads/dispatcher with batch opening and an owner-scoped batch observer so the focus source records the revision before the first key or text callback, not after binding handlers have already changed it. Virtual keyboard operations are not affected by this physical batch mechanism. Pair public `lovr.keypressed`/`lovr.textinput` tests for consumed keys, errors, local-to-local/native changes, self-unload, select-all, Shift, AltGr, multiple events in a batch, and independent text in a fresh batch. Binding-phase external handlers remain an explicit plugin extension, but shipped session actions cease registering physical bindings. An unhandled focused local input is consumed with respect to native fallback.

## Risks, Blockers, and Required Decisions

Answered decisions: include the small widget library; retain replaceable drawing without a layout engine; route one desktop keyboard to native and local targets; all session workflows have complete VR paths; hardware acceptance remains an explicit later follow-up, not a completion gate. No ordinary implementation decisions remain assigned to execution.

- Focus is a pre-stable breaking contract migration. Update all in-tree providers/consumers and bump capability schema consistently; do not mix old/new services through permissive casts. The plan intentionally preserves only the native keyboard Options.target adapter and legacy surface callback fallback.
- Single-route callbacks can change focus or unload themselves. Generation snapshots, state-before-callback cleanup, and failed-versus-unhandled distinction are essential to prevent cross-target leakage.
- Native sink key-up/modifier cleanup may fail. Attempt all inverses, report ownership/context, clear internal state first, and do not claim safe input delivery after unresolved cleanup.
- Provider graphs can cycle if widget focus directly requires the desktop keyboard. Focus only publishes keyboard visibility intent; the display consumer observes it. Menu actions register independently of rendering consumers.
- Manager protection grows to include the actual VR recovery path. Tests must distinguish mandatory input providers from optional inspectors so the graph remains useful for management.
- Widget replacement on every frame would leak focus handles and cancel editing. Keep stable handles and explicit reconciliation/disposal.
- Grapheme segmentation adds one pinned native dependency and generated declaration. Follow repository dependency/generator conventions; no vendor/compositor changes. Full shaping, bidi caret navigation, and IME/preedit are deliberately excluded and documented.
- Removing physical session-binding settings is observable breaking behaviour. Emit clear rejection/migration guidance, migrate all examples, and do not silently accept unused settings.
- Logic-headless tests and the added VR fixture cannot establish actual GPU/headset presentation. The operator explicitly accepted this reliability gap and the named manual follow-up before plan authorship.
- Keep unrelated PDF and previously committed plugin/schema/inspection work untouched. Planning makes no project edits or test/build claims. Implementation commits only the explicitly approved phase-9 batches after exact-staged-tree verification/review. Changed splits need fresh consent; push permission is not granted.
