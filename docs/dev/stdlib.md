# Standard library

The Lua standard library is installed below `$PREFIX/share/lunette/lua/`. `@lunette-plugin`, `@lunette-contracts`, and `@lunette-plugins` provide the typed plugin facade, neutral service contracts, and every built-in plugin, provider or consumer. Every policy the library ships is a provider or a consumer, written against the public `lunette` API, and a configuration replaces or omits it as it does any plugin. `@lunette-desktop` holds the entry list that composes the providers and the desktop's consumers, which the shipped configuration runs. Their lifecycle and type boundary are specified in [The Lua API](lua-api.md#plugin-authoring) and [Architecture](architecture.md#plugin-runtime).

## Module roots

The source tree is `lua/`. A running session mounts the file-backed roots through LÖVR's virtual filesystem, and the checker resolves aliases from generated `.luaurc` files. [Build and development](build-and-development.md#module-roots) lists each root's alias, source directory, runtime resolution, and installation, and names the source of truth.

A relative require follows Luau's require-by-string rules in the checker and in a session alike. A module's path is its file's path without `.lua` or `.luau`, and a directory's `init.luau` is the module the directory names. `./` and `../` start from the directory that holds the requiring module, and `@self` from the module itself, so in `keyboard/init.luau`, which is the module `keyboard`, `./draw` is a sibling of the directory and `@self/draw` is inside it. LÖVR's loader takes a name as a path from the root of the virtual filesystem, so the session wraps `require` (`crates/lunette/src/require`) to resolve a relative path against the requiring chunk's file first; the resolved name, such as `nested/b` or `@lunette-plugins/keyboard/draw`, is what the loader finds and what `package.loaded` is keyed by. A relative path cannot leave the root it starts in, the configuration root or a module root, cannot name the root itself, and cannot hold a `.` in a component, which the loader reads as a separator; each raises at the requiring line. A chunk with no file, such as one `lunctl eval` sends, resolves as a module at the configuration root would, and has no `@self`. `pcall(require, './x')` resolves against the chunk that called `pcall`.

The checker follows directory symlinks and retains the module path used by the configuration for relative requires. An imported example's `.luaurc` resolves its relative aliases from the actual directory containing that file. `dev/examples` uses these rules to reuse the checked-in examples without copying their plugins. The checker retains Luau's file-extension and `init` ambiguity checks.

A configuration can use `lunette` without loading the built-in providers or the desktop.

Panels, UI panels, drops, focus, key bindings, interaction, lasers, the virtual keyboard, tags, rules, placement, adoption, layouts, the error stream, frame pacing, and output scale are built-in providers, and the arc layout is a built-in plugin that registers with the layouts broker, all under `@lunette-plugins`. The desktop's consumers are there too, each in the folder its entry id names, so `desktop/pacing` is `@lunette-plugins/desktop/pacing`, except `desktop/persistence`, which provides `lunette/arrangement` and is named for it as a provider is, `@lunette-plugins/arrangement`; and `@lunette-plugins/desktop/logging` is the log channel those consumers report through. [Decisions](#decisions) records why no optional root of helpers sits beside them. Pose encoding and the key vocabulary are contracts vocabulary, the default key rows belong to the keyboard provider, and arrangement persistence belongs to `@lunette-plugins/arrangement`, the plugin that provides `lunette/arrangement`. The modules that are neither plugins nor contracts, and the one plugin module that carries an API beside its plugin, are these:

| Module | Responsibility |
|---|---|
| `@lunette-contracts/vocabulary` | The surface and pointer types shared by several contracts, the per-window pose property, `encodePose` and `decodePose`, the one encoding of a pose as the property store's sixteen numbers, and `PRECEDENCE`, the named precedences of the desktop's rules sources. |
| `@lunette-contracts/keys` | The key vocabulary: `CODES` from `lunette.keyCodes()`, `LOCKS` from `lunette.lockingModifierNames()`, `MODIFIER_ORDER` from `lunette.modifierNames()`, which key latches which modifier, the translation from LÖVR's desktop key names, and `heldModifiers`, the modifiers LÖVR reports held, which the bindings provider and `desktop/input` both read. |
| `@lunette-plugins/arrangement`, with `state`, `capture`, `slots`, and `format` | The `desktop/persistence` plugin, exported as `factory`, beside the custom-format API: the versioned file representation with the constructors a format of a configuration's own answers its loads with, and the default `FORMAT`, `FILE`, and `defaultKey`. Inside it, `state` is the arrangement state the plugin owns, with file loading and saving through a chosen format; `capture` captures and restores; `slots` is the saved slot each live window holds and the identity it is keyed on. |

## Contracts and providers

A neutral contract module declares a service shape and exports a capability. The capability pairs a Luau type with an authority-qualified contract name and schema number. Vocabulary that is shared by several contracts belongs in a neutral contract module so service types do not need to import a provider implementation.

A plugin definition declares its name, its required and provided capabilities, and its initializer, whose configuration parameter gives the definition its configuration type. Its context reads required services with `Context:require<T>(capability)`. Its initializer stages provided services with `Publisher:provide<T>(capability, value)`. The native graph validates runtime wiring and publishes all provided values as one provider generation after initialization succeeds. See [Plugin authoring](lua-api.md#plugin-authoring) for the type boundary and runtime checks.

A provider's service methods carry no liveness guard of their own: consumers reach them through the facade's service view, which raises once the provider's activation has ended. Objects a method returns, such as panels, pointers, lasers, keyboards, and tags, outlive the call and check their own state. A provider whose owner-scoped method needs one of its own dependencies registers that work under its own context, inside the effect it places on the caller's owner, rather than forwarding the caller's owner; the adoption provider's `install` registers its rules source this way. A provider subscribes to native events for its own activation through `Context:on`. The adoption provider's `start` subscribes inside the effect it registers on the caller's owner instead, because that subscription belongs to the caller.

A resource a consumer asks a provider for, such as a pointer, a laser and its seat, a keyboard, a focus target or source, a tag membership, or a selection override, is released by an inverse registered on the consumer's owner, not on the provider's context. An inverse that raises while the owner unloads is the owner's failure and quarantines the owner; the provider keeps serving its other consumers. Direct disposal raises a failing inverse to its caller. Routed input reports delivery failures as explicit results and retains native cleanup on the original target; [Focus](lua-api.md#focus) states its refusal and failure rules.

Every change a consumer makes to state it does not own is an effect of its owner. A tag `hold` made lasts while any owner holds it; a tag `new` made belongs to that owner. A tag membership is held by the owners that added it and an exclusion by the owners that excluded it, and the panel is a member while a holder remains and no exclusion does; an owner removes only its own hold, and the owner of a tag `new` made removes every hold. A tag's selection and its layout are each decided by the most recent live override, one per owner, and a tag with none has the value it was made with. The `lunette/focus` schema 2 contract holds one current native or local route through owner-scoped target handles. Native window seat authority remains independent: a target withdraws only focus it still owns, and another native seat keeps its authority when the current route moves. Blurring or disposing the current target leaves no route and does not restore an older target. Sources isolate unhandled or failed local input rather than forwarding it to native clients. A panel's visibility is decided by the most recent live override, one per owner, and a panel with none is shown. A key chord names one binding, and binding a chord that is bound raises. A laser hand has one owner under `attach`, which raises rather than hand one owner another's laser. A rules source name names one registration, and registering a name already registered raises.

The `lunette/panels` contract is schema 3. The built-in provider requires theme and exposes owner-scoped `onAdded` and `onRemoved` listeners, resolved `windowRadius` and `monitorRadius`, and its leased font style. Radius values inherit from the global theme unless provider or panel style overrides them. Rules ends a placement when its panel is removed, adoption ends an adoption, the desktop's mirror consumer ends a mirror, and persistence restores a monitor panel as it arrives, all through this contract and none through a provider's private module. A listener that raises is reported through `lunette.reportError` and does not fail the operation that added or removed the panel.

LÖVR's frame and input callbacks reach plugins through `lunette/frame` at schema 2, and the surfaces a pointer picks from are brokered by `lunette/surfaces`; [Frame and surfaces](lua-api.md#frame-and-surfaces) states both. Each frame update opens an input batch before handlers, and `onBatch` lets physical sources capture the route before bindings run. Key and text events carry that batch identity. Binding key consumption and delivery-side `blockText` requests republish blocked batch metadata before later physical callbacks. `desktop/input` persists command or rejected delivery and source-release invalidation there, so a replacement source cannot accept remaining text in the same batch. A cached `blockText` method checks its provider activation before mutation; fresh lookups retain the normal service-lifetime guard. Key events also carry an optional readonly physical modifier snapshot; native keypad routing uses it for ordinary PC NumLock/Shift behavior and refuses an unavailable mode. [Physical keypad modes](input.md#physical-keypad-modes) records the supported behavior and host-layout limits. `@lunette-plugins/frame` exports `install`, which binds the LÖVR callbacks to it, and `run`, which binds them to a composition, beside the module shape every provider has. Both providers call each handler and offer through `@lunette-plugins/protected`, which reports an error through `lunette.reportError` and continues; the panels provider calls its listeners the same way.

The interaction contract is schema 2. Surface pointer events distinguish button-specific capture from hover and cancellation from release. Optional unbounded projection keeps a captured drag on its original surface after it leaves the hit bounds. Tracking loss blocks button edges until a tracked all-up sample. Native sinks retain their input path, and external legacy-only surfaces retain their callback fallback. The keyboard, UI wrist menu, and existing manager surface use the pointer event protocol; panel and decoration sinks remain native. `@lunette-contracts/quad` provides unbounded `project` and bounded `hit` for flat geometry.

The keyboard contract is schema 3. The built-in provider requires focus and theme, delivers virtual activations through an owner-scoped focus source, derives legends from the same live keymap selection as local translation, and clears latches and locks immediately on a route change, hide, or destruction. Its owner's `onVisibilityChanged` callback receives `show`, `hide`, `user-hide`, or `destroy` after state changes. The native-only `Options.target` adapter remains supported and never supersedes a focused local receiver.

`desktop/keyboard` provides `lunette/keyboard-display` at schema 1. It lazily creates, offers, and draws one keyboard. Local text-field focus shows that board through the focus contract's `wantsKeyboard` metadata. Manual visibility persists after editing ends; automatic visibility ends with its requesting target. Explicit hide and the keyboard's Hide action blur only the matching current field and preserve its draft. Field switching keeps the board's pose. A replacement display waits for a new live focus notification rather than replaying a retained target. The wrist menu's Keyboard action toggles this shared display; the display consumer renders no wrist trigger. It requires the UI service for the shared Keyboard titlebar. Its X button uses the display's existing hide and focus cleanup, and its background supports trigger dragging. Its configuration accepts only `placement`. [Keyboard display](lua-api.md#keyboard-display) defines the public methods and visibility notifications.

The `lunette/menu` schema 1 broker holds owner-scoped actions with stable ids. Registration returns an effect; disposing that effect removes the action. Listing returns immutable callback-free values sorted by group, order, and id. State updates require the registering owner and exact live effect. Invocation reports invoked, unavailable, or failed and attributes callback failures to the registering owner. An optional registration token prevents a retained action row from invoking a replacement with the same id. The broker adds no wrist surface or session action by itself. [Menu actions](lua-api.md#menu-actions) defines its API.

Constants and helpers that several providers agree on are neutral vocabulary rather than service fields. The per-window pose property is `@lunette-contracts/vocabulary`'s `POSE_PROPERTY`, written by `desktop/pose-memory` and read by the adoption provider with its `encodePose` and `decodePose`; the key names, modifier keys, and locks are `@lunette-contracts/keys`; and ray intersection with a flat quad is `@lunette-contracts/quad`. A name the native API already answers, such as a key's evdev code or the set of modifiers, is read from it rather than restated. A provider's tuning and style are its configuration, merged over its defaults, and each activation receives its own frozen copy, so no consumer can retune another's.

Built-in provider modules exist for adoption, bindings, drops, the error stream, focus, frame dispatch, frame pacing, interaction, keyboard, laser, layouts, menu actions, output scale, panels, placement, rules, surfaces, tags, theme, and UI panels. The providers use the typed plugin facade. Each module answers `{ definition, define, build, requires }` and validates its configuration, as [Provider modules](lua-api.md#provider-modules) states. Panels take `style`, `priority`, `height`, `aspect`, `chrome`, and the `shape` hooks; interaction takes `tuning`, `focusOnPress`, and the `drive` and `constrain` hooks; the laser takes `style`, `buttons`, and the `readInput` and `draw` hooks; the rules provider takes its default `precedence` and the adoption provider its install `precedence`, by default `PRECEDENCE.rules` and `PRECEDENCE.native`; placement takes the `panelOptions` hook; the error stream takes `window`, `maxKeys`, `history`, and `clock`; frame pacing takes `tuning` and the `choose` hook; and output scale takes `tuning` and the `ideal` hook, which [Frame pacing and output scale](lua-api.md#frame-pacing-and-output-scale) states. Frame, surfaces, drops, focus, bindings, layouts, menu actions, and tags take none. Panels, interaction, and the laser still expose their style or tuning as upper-case fields, `STYLE` and `TUNING`; [Pointers and interaction](lua-api.md#pointers-and-interaction), [Lasers](lua-api.md#lasers), [Panels](lua-api.md#panels), and [Bindings](lua-api.md#bindings) state the rest. The keyboard takes `rows`, `layers`, `style`, `modifierKeys`, `locks`, and the `onKey` and `drawKey` hooks, and its service exposes none of them; [Keyboard](lua-api.md#keyboard) states them. The arc layout, `@lunette-plugins/layout/arc`, provides nothing: it registers a layout with the layouts broker, and its module answers `definition`, `define`, and `requires`. It takes `layout`, the name it registers, and `tuning`; [Layouts](lua-api.md#layouts) states them. A pointer carries `vibrate`, which its creator supplies; the laser supplies its hand's controller. Replacing a provider keeps its capability and declared service shape. A replacement implements the existing interface; the contract is not weakened to accommodate it.

## Runtime themes

`@lunette-contracts/theme` declares the neutral `lunette/theme` schema 1 service. `@lunette-plugins/theme` provides owner-scoped selections, change subscriptions, retained font leases, and data-only inspection. The last live registration determines the complete effective theme; updating it preserves its rank, and disposal restores the previous live registration or the square base. Invalid updates and font acquisition failures preserve the previous selection. [Runtime themes](lua-api.md#runtime-themes) defines validation, notification delivery, editable font projection, and invocation lifetimes.

`lua/lunette-plugins/theme/presets.luau` owns the base and the complete Dark, Light, and Arcade presets. Dark and Light share typography, metrics, and radii, and differ only in palette. Arcade uses saturated colours, larger text and spacing, different borders and radii, and the bundled Space Mono Regular face. Base, Dark, and Light use zero monitor radius; Arcade uses 0.012 m. Logical UI metrics do not imply a fixed metre scale. File faces use LÖVR filesystem paths, not require alias resolution. The font and OFL licence are explicit installed artifacts beside the module roots.

The shipped `desktop/theme` selector starts with the configured `preset`, defaulting to `dark`, then applies its sparse `overrides`. It registers `Theme: Dark`, `Theme: Light`, and `Theme: Arcade` actions in the session menu. Menu action state tracks the active preset. A preset choice updates the selector's existing theme registration, so other selections keep their rank and the new complete theme does not mix palettes. Its definition retains the current selection across activations in one runtime when the configured preset is unchanged. A changed configuration preset takes precedence; a source reload creates a new definition and starts from configuration again. Disabling `desktop/theme` removes its registration and reveals another live selection or the base theme. Disabling the selector leaves the theme service available to recovery consumers.

The broker acquires no native face at module require. File faces belong to a provider activation and remain alive through selection, lease, and invocation holds. `getFont` is an immediate borrow; retained consumers use `acquireFont`, and callback-spanning use goes through `FontLease:withFont`. The callback must not retain or release the borrowed Font. Each invocation pins the exact face until the callback unwinds, including reentrancy, callback errors, owner teardown, and provider shutdown. The borrowed default font is never released. Inspection retains an ended lease as a not-live hold while its invocation remains active, with the exact file specification and invocation count as data. Final unwind removes that hold. The [theme-broker-lifecycle workflow](../guide/desktop-configuration.md#theme-broker-lifecycle) checks these synchronous observations and their original reports. [theme-font-fit](../guide/desktop-configuration.md#theme-font-fit) checks real mounted-font loading; both remain manual gates.

The runtime theme stays a neutral data contract. The built-in selector is a separate consumer, so configurations can replace or disable preset policy while keeping the theme provider available to recovery UI. A preset replaces the selector's complete registration instead of layering palette fragments over other live selections. This prevents a palette from one preset from combining with geometry or typography from another. Sparse theme layers let omitted fields continue to follow global changes; filled consumer defaults would mask later theme changes. Zero is an explicit value, and nil means inheritance, so consumers can preserve the existing style option names.

Consumers prepare replacement leases and measurements before publishing new appearance. They keep the old lease until publication succeeds, then release it. A callback can change the theme or end an owner while a renderer still uses a face. `FontLease:withFont` pins the exact face until that invocation returns, so synchronous reentrancy and shutdown cannot release it early. Palette-only changes preserve input captures because colors do not change control geometry. Font and geometry changes cancel only affected gestures after the replacement is ready.

The direct theme consumers resolve their own sparse settings as follows. Omitted fields inherit. Explicit zero remains a value. Existing option names stay in place.

| Consumer | Theme-backed fields | Local configuration and geometry |
|---|---|---|
| `keyboard` | Font, backing and key radii, keyboard gap, plate and key colours, held and hover colours, legend colour, and legend height. | `keyUnit`, margin, plate depth, legend depth, rows, layers, modifier keys, locks, and haptics remain keyboard options or input policy. Resolution continues from global theme to provider style to per-keyboard `Options.style`. |
| `panels` | Font, window and monitor radius, title height and colour, border thickness and colour. | `borderDepth`, `titleMargin`, curve, priority, dimensions, and rendering mode remain panel configuration. Native chrome uses its leased theme font. Scene meshes and initial hits share a clipped rounded perimeter; granted layers remain rectangular. |
| `ui` | Global colors, font, font size, padding, spacing, border width, row height, logical panel and control radii, titlebar font, titlebar height, titlebar border thickness, titlebar corner radius, and title color. | UI provider configuration, panel overrides, and control overrides retain their own layers. UI panel radius converts from metres to logical x and y units. Rounded faces do not change declared bounds; content and rectangular control targets use a conservative content clip. |
| `laser` | Pointer and hover colors. | Length, cursor radius, haptic strength, and haptic duration remain laser style; aim, trigger lock, button mapping, and tuning remain separate. |
| `desktop/hint` | Foreground color and font. | Existing `size`, `text`, and `position` fields remain in place. An omitted size inherits the global hint text height. |
| `desktop/errors` | Foreground color and font. | Existing `textHeight`, background, report layout, and position fields remain in place. An omitted text height inherits the global error text height. The existing background option keeps its permissive four-number validation; a new foreground color uses strict RGBA validation. |
| `desktop/theme` | Applies a selected complete preset and sparse global overrides. | `preset` and `overrides` configure the selector. |

The `desktop/manager` requires theme directly for its custom graph and details drawing, and also receives UI styling through the UI provider. Its UI controls and Plugins titlebar use theme-backed appearance. The 26-unit toolbar controls use `min(padding, 3)` and `min(smallSize, 16)`. The 34-unit fields use `min(padding, 5)` and `min(bodySize, 20)`. The 102-unit choice editor uses `min(rowHeight, 40)`, `min(padding, 5)`, `min(spacing, 6)`, and `min(bodySize, 20)`. These retained explicit layers preserve theme-derived font, colours, border width, and clamped radii. They keep Arcade's larger defaults within existing control geometry without masking larger general rows/details. Palette-only updates do not call cancelling setters. The manager keeps its minimum logical canvas at 800x472. Theme changes do not change its panel dimensions, logical scale, structural toolbar layout, or control identities. Keyboard `keyUnit`, rows, layers, and retained `setSize` scale also remain outside theme; resolved gap, legends, and radii follow that scale.

The [field-to-consumer acceptance checklist](../guide/desktop-configuration.md#theme-field-to-consumer-checklist) enumerates every exact `colors`, `typography`, `metrics`, and `radii` field against its resolver, visible consumer, and explicit limit. The [theme acceptance workflows](../guide/desktop-configuration.md#theme-acceptance-workflows) give the named operator checks: theme-broker-lifecycle, theme-runtime-switch, theme-appearance-matrix, theme-font-fit, and theme-documentation-check. The same guide's [headset verification](../guide/desktop-configuration.md#headset-verification) records theme-rounded-content, theme-joined-frame, theme-widget-edges, and theme-rendering-exceptions. Their manual observations remain pending. Existing geometry, draw, reload, and installed-byte recorders establish their recorded Lua/resource behavior only, not native rasterization or a successful installed session.

`examples/ui/main.luau` includes a checked public theme-registration consumer alongside the form. Its entry stays active with `enabled = false`, but its initializer creates no observation UI, actions, selections, listeners, leases, or children. Plugins -> select `example/ui/theme-registration` -> Configure -> set `enabled = true` -> Apply activates the example through normal replacement. Entry Enable alone is not activation. Its 28 controller actions use public theme/UI/menu/frame/inspection operations and child Instance ownership. Setting the configuration false, disabling, or removing the entry ends its resources. It is the manual observation workflow for arbitration, reentrant delivery, failed file-reader refresh, owner-ending invocation, and draw mutation/error unwind; it supplies no new automated broker cases.

## Rounded surfaces and joined frames

`lua/lunette-plugins/theme/rounded-geometry.luau` supplies pure dimension, corner-profile, perimeter, and clipping geometry. `theme/drawing.luau` supplies shared faces and ring drawing. Nonzero quarter arcs use eight segments. Initial hits test the emitted perimeter, including its chords, rather than an analytic circle outside the mesh. Owner and provider records cache native meshes by geometry and clip, release replaced meshes, and clean them up on teardown. Module require acquires no native mesh, and unchanged frames reuse cached geometry. [Rendering](rendering.md#rounded-scene-geometry) defines the draw and hit agreement.

Scene window and monitor UVs derive from the original panel-local coordinates before monitor rotation and flip. Curved content splits clipped polygons at the existing horizontal arc strips and maps vertices to the cylinder. Cutouts remove content and depth-writing outline geometry, leaving farther surfaces visible and pickable. Native releases still reach the original pressed sink, and native motion stops on a miss without added capture projection. Protocol captures can project through cutouts with `inside = false` and cannot activate there on release. Granted layers retain rectangular content and hits, unchanged claims, and raw copies. Radius changes do not force scene fallback. An ungranted claim uses rounded scene geometry. Base, Dark, and Light use square monitor bodies; Arcade uses 0.012 m, and explicit zero restores square content.

The neutral vocabulary supplies optional `Surface.attachFrame` and the readonly `FrameStyle` and `FrameAttachment` types. [Joined frame attachments](lua-api.md#joined-frame-attachments) defines their exact fields, validation, full-style updates, and disposed errors. A target permits one live attachment, including a dormant one, and computes joining from its current eligibility. Native joining requires a live source and target, visibility, flat geometry, and actual scene rendering with no granted layer. UI targets require liveness and visibility. Eligibility changes retain the attachment; heading removal, heading invisibility, owner teardown, or target destruction releases it. Surfaces that omit the method retain a separate titlebar.

A joined header has top outer corners, an independently rounded body has bottom outer corners, and their adjoining edges are square at zero margin. The header radius clamps to its own height. The target draws one outline using the header's border thickness, depth, and current normal or highlighted colour, superseding body outline overrides even when native chrome is disabled. Ordinary body and separate header borders are suppressed. The ring has no internal seam or rectangular depth backing in cutouts. Header faces, including hovered and held actions, clip to the same top-only perimeter. The drag surface gates hits with that perimeter before reserving action width and preserves the owning grab target. Curved scene content still rounds, but its flat titlebar remains separate. Granted layer content also keeps separate treatment.

## UI toolkit

`@lunette-contracts/ui` declares the neutral `lunette/ui` schema 2 service, and `@lunette-plugins/ui` supplies its built-in provider. It requires focus, surfaces, theme, and frame. It accepts `theme`, `draw`, and `titlebarStyle` configuration, and creates owner-scoped flat VR panels with buttons, single-line text fields, choices, lists, and regions. It does not install frame drawing policy. A consumer draws only the panels it creates, through its own frame registrations. [UI panels](lua-api.md#ui-panels) specifies the public operations, and the [UI guide](../guide/ui.md) gives a contract-only checker fixture.

The UI provider owns one extensible titlebar implementation for native decorations, the manager, the keyboard display, and the expanded wrist menu. UI panels opt in through `PanelOptions.titlebar` or `Panel:setTitlebar`; other owning surfaces use `Service:newTitlebar`. Inputs supply the title, an optional close callback, and extra actions. The titlebar sits above the body without changing its logical dimensions. It tracks current pose, size, and visibility, retains shared action widgets, and owns the background drag surface and cleanup. The compact wrist control and unheaded error quad remain undecorated. One UI-owned scene update at order 1000 synchronizes all retained titlebars after built-in source, layer, and decoration updates and before pointing and all drawing. Theme callbacks, highlights, and public titlebar updates synchronize immediately. Target drawing refreshes eligibility without a private titlebar callback. The UI provider still installs no global panel draw subscription.

Panel input, drawing, and detached descriptions share top-left, y-down logical coordinates and half-open clipped bounds. The backing uses full silhouette bounds. Default controls, custom hooks, items, descriptions, and input use a conservative rectangular content clip inside that silhouette. Declared dimensions and bounds do not change. Controls retain rectangular ergonomic targets within the content clip; rounded-face text stays within safe bounds, and reduced content room retains overflow indicators. Captured pointer gestures remain on their original control and cancel without activation on hide, disable, destruction, or geometry replacement. Local text fields use focus targets and focus sources rather than direct native sink delivery. The native `lunette.textBoundaries` helper supplies one-based UTF-8 byte offsets at extended grapheme boundaries, including the empty and terminal positions; Lua owns editing and rendering policy.

Theme overrides resolve from provider to panel to control. Draw hooks wrap renderers in that order, receive immutable visual snapshots, and cannot alter declared input geometry. Pass state and transforms are restored around each invocation, but a hook must balance its own pushes and respect clipping. Every provider activation creates a fresh frozen `ui.Generation` token. A panel description carries that token and a revision. Control handles and descriptions carry a frozen `ui.OwnerIdentity` token, stable within an actual creation-owner activation in the provider and fresh after owner or provider replacement. Control ids are unique across all live panels per actual creation owner; different owners can reuse an id within one panel. The generation token, owner token, and id disambiguate a live control. Tokens are compared by identity and expose no context or resource authority.

The underlying local focus target is registered under the UI provider's context. The control's owner-held inverse releases the target and rethrows cleanup failures, retaining the control lifetime and owner-cleanup failure boundary without describing the focus registration as consumer-owned.

The strict UI fixtures in `crates/lunette/tests/luau_check/ui` cover read-only covariance, owner identity metadata, mutation and wrong-token rejection, contract receiver types, pointer-event discrimination, and widget options and callbacks. The separately registered `crates/lunette/tests/luau_check/pass/ui-substitute.luau` checks a complete substitute typed only through the neutral contract. `ui_modules_resolve_from_installed_manifest_roots` copies manifest artifacts into an isolated installation and checks the public contract and provider aliases from a separate configuration. `runner::ui_modules_load_from_installed_manifest_roots` loads the copied UI modules through the custom Lua test runner. Both regressions cover both feature sets. They do not exercise LÖVR's production virtual-filesystem mounting, an installed session boot, or GPU-backed drawing. The separate runtime UI substitute scaffolding remains development-only.

## Configuration descriptors

`@lunette-plugin/schema` derives runtime validation, immutable editor metadata, and Luau `Input` and `Output` types from one descriptor composition. Objects reject unknown fields and merge declared defaults; arrays and string-keyed maps replace, including empty collections. Declared containers reject metatables and cycles, while custom typed values remain atomic and preserve their references. Numeric and vector values require finite components. Callback signatures remain a static constraint; runtime validation checks their function kind. Errors carry a name, path, code, and message. `inspect` returns the parser tree, and `resolve` applies input over validated output settings. The [configuration schema guide](../guide/configuration-schema.md) records the constructor API and pinned checker limits. Configured providers and consumers take a descriptor in `schema`; it determines both their input configuration and resolved settings. Every built-in, development, and configurable example plugin derives these types from its descriptor. A schema-backed definition exposes its immutable metadata and a preflight resolver over its bound defaults. The resolver validates configuration without acquiring initializer effects. Custom validators preserve the exact checked reference and do not transform it. Resolved collection indexers are read-only, matching their frozen runtime tables.

## Default configuration

`etc/xdg/lunette/main.luau` is the shipped configuration. It calls `require('@lunette-desktop').run()`. The desktop is a list of entries, `{ id, definition, config }`, or `{ id, factory, config }` for a definition that is made once for each runtime: the built-in providers, the `layout/arc` registration, and the `desktop/` consumers the tables below describe, each under its definition's name. `lua/lunette-desktop/init.luau` is the source of truth for the entries and their order, and holds nothing else of the desktop: every plugin it lists is under `@lunette-plugins`. `entries()` answers the list, frozen, so a configuration can read the ids.

`run { patches = { ... } }` applies patches to the list with `plugin.compose`, binds callbacks with `frame.install`, and starts the session composition service at load. [Composition](lua-api.md#composition) states the patch rules and errors. `run { entries = { ... } }` starts from another list instead of the default. `run` composes before it binds any callback, so a malformed patch fails the configuration's load and safe mode reports it. `compose(options)` answers the patched list without starting it, and `plugin.start(entries)` starts a list.

```lua
require('@lunette-desktop').run {
  patches = {
    { id = 'keyboard', disabled = true },
    { insert = { id = 'my-hud', definition = hud, config = {} } },
  },
}
```

The one order the placement entries rely on is that the rule list and the saved arrangement are sources before adoption resolves the first window, as the next paragraphs state; a source a configuration inserts goes `before = 'desktop/adoption'` for the same reason.

`settings` configures the desktop consumers through their exported `Config` types. Its fields are `menu`, `decorations`, `arrange`, `persistence`, `wristKeyboard`, `rules`, `monitors`, `hint`, `errors`, `pointing`, `pacing`, `workspace`, `adoption`, and `manager`. `lua/lunette-desktop/settings.luau` composes these descriptors from the corresponding plugins; the settings add no second validation specification. Each maps to the corresponding `desktop/` entry id, with `persistence` mapping to `desktop/persistence` and `wristKeyboard` to `desktop/keyboard`. `menu` maps to `desktop/menu` and owns `hand`, `size`, `offset`, `haptic`, and the expanded panel geometry. `wristKeyboard` retains only `placement`; its removed geometry and haptic fields report a migration error naming `settings.menu`. The keyboard provider remains the separate `keyboard` entry. `settings.bindings` and `desktop/bindings` are removed, while the neutral `bindings` provider remains available for custom inputs. Expansion creates ordinary configuration patches and retains each consumer's validation and failure boundary. A setting and a raw patch targeting the same id raise an error naming both sources. Raw entries and patches remain available for disabling, inserting, or substituting plugins. [Desktop configuration](../guide/desktop-configuration.md) gives checked examples.

`configureEntry(id, definitionOrFactory)` is `plugin.configureEntry`, which targets the actual entry id and uses the definition or factory only for its configuration type. It does not invoke factories. `configure` is `plugin.configure`, which [Composition](lua-api.md#composition) states. `configure(laser.definition)(config)`, written `configure(laser.definition) { ... }`, answers `{ id = 'laser', config = config }`, so the patch is the plain patch and composes the same way, and the checker reads the options against the laser's option types. Every shipped entry's id is its definition's name, so a patch made from a shipped module's definition, or from the factory `desktop/arrange` exports and the `factory` field of `@lunette-plugins/arrangement`, which is `desktop/persistence`, names that entry.

The shipped desktop opens no application automatically. The repository-only development configuration inserts its own terminal plugin; [The development loop](build-and-development.md#the-development-loop) states its launch command. Each consumer requires the frame and surfaces contracts it uses, as a plugin in a user's configuration would, and validates its configuration with its schema, so an option it does not take is rejected by name and path. `desktop/render`, `desktop/input`, `desktop/actions`, `desktop/pose-memory`, and `desktop/scale` take none.

Placement is six consumers, each replaceable or configurable by its id:

| Entry | Does | Options |
|---|---|---|
| `desktop/workspace` | Holds the workspace tag and selects it while active. | `name`, default `main`. |
| `desktop/rules` | Registers its rule list with `rules:setRules` under the default source name and precedence. | `rules`, the list; the default sizes and places Firefox. A list replaces the default wholesale. |
| `desktop/pose-memory` | Writes a dropped window's panel pose to the window's `lunette.pose` property, which the adoption provider's native source reads back after a reload. | None. |
| `desktop/persistence` | A definition factory. Each definition makes one persistence state at its first activation and keeps it outside its activations, binds it as a rules source at each activation, saves when `lunette/drops` announces a drop and again at normal quit, and provides `lunette/arrangement`, whose `save` and `restore` a consumer can call, as the `save-menu` example does. | `file`, the file in the save directory, default `arrangement.state`; `format`, `{ read, render }`, default `FORMAT`; `keyFor`, the identity a window or monitor is saved under, default `defaultKey`; both are fields of `@lunette-plugins/arrangement`. |
| `desktop/arrange` | A definition factory. Arranges placed windows that were placed without a pose, tag by tag, each with its own layout or the configured one from the layouts broker, and leaves out a window the user dropped. | `layout`, default `arc`; `options`, each layout's options keyed by its name, each replacing that layout's defaults wholesale, default none; `tags`, the tags to arrange, every tag when empty, the default. |
| `desktop/adoption` | Installs the adoption provider's native pose source and starts adoption. | `tags`, the tags an adopted window joins unless a rule names others, default `{ 'main' }`; `filter`, which answers whether to adopt a window, default every window. |

The rule list and the saved arrangement are sources before adoption resolves the first window, which is why they come before it in the list. The workspace tag needs no place in the list: a placement that names it, the saved arrangement restoring a panel into it, and `desktop/workspace` all hold it, so whichever comes first makes it and it lasts while any holds it. The rule sources apply in ascending precedence, which `@lunette-contracts/vocabulary`'s `PRECEDENCE` names: configured rules at `rules`, 100, saved arrangement state at `persisted`, 200, and native per-window properties at `native`, 300. A higher-precedence source overrides a lower-precedence value for the same property. Saved state supplies pose, size, and tags; the native source supplies hand-placed pose.

`desktop/arrange` reads what to arrange from the placement contract's `placed()` each time it arranges, and arranges when it activates, when placement announces a placement through `onPlaced`, when any panel is removed, when a layout registers or unregisters, and when a tag is made, ends, changes its selection, changes its layout, or changes its members. The candidates are every live placement made without a pose, in placement order, less every panel dropped while the consumer was active and every window with a kept pose, the `lunette.pose` property `desktop/pose-memory` writes on a drop, so a window dropped while the consumer was unloaded stays where it was dropped. The dropped panels are kept in the factory's state, weakly, so an outage of the consumer does not return them to the set either. The tags are those `tags` names, or every tag, and the selected ones come first, then the rest, each group in the tags service's order. Each tag poses the candidates that are its members and that no earlier tag posed, with its own layout when it names one and otherwise with `layout`, so a window in several tags is arranged by the first selected tag that holds it, or by the first tag that holds it when none of its tags is selected. A layout is applied with `options[name]`, its own entry, whichever tag uses it, or with none. A layout registered as `continuous` and in use is also applied on every frame update, in the `scene` phase before the panels update. `desktop/arrange` logs a warning, once for each name, on the first frame that finds a layout it would use not registered, naming those that are; it arranges as soon as one registers. A layout's options error is the layout's: it fails the activation that arranged, or is reported through `lunette.reportError` when the arrangement ran from a listener.

A placement holds each tag it names by a string, making it when no tag has that name. Cleanup at the end of the placement's lifetime removes the memberships it added, its panel, its hiding, and its holds, so a tag it made ends with the last placement or other owner holding it. A tag given as a tag is joined as it is.

A persistence state reads its file through its format, by default the versioned Lua table `@lunette-plugins/arrangement/format` writes. A format of a configuration's own answers its loads with the module's `arrangement`, `fromTheFuture`, `broken`, or `empty`, and keeps the version rules `format` states: a reader answers `fromTheFuture` for a version it cannot write back whole, so the file is refused rather than written over, and a version is bumped when a field is added. A reader that raises or answers something other than a load makes the file broken, and a render that answers something other than text fails the save. `keyFor` answers the identity a window or monitor is saved and restored under; the default is a window's application id and a monitor's id, and a configuration that keeps terminals apart by title answers a window's title. A persistence state retains its loaded arrangement, the slot each live window holds, and any refusal to overwrite a broken or newer-format file while `desktop/persistence` is disabled and re-enabled. A binding belongs to one activation. Its rules source and arrival listener read the arrangement last loaded or saved, so a save reaches the windows and monitors that appear after it. A saved entry that no live panel matches is reported once for the arrangement it belongs to, at the first binding or `restore` that finds it unmatched, and not again by later restores or bindings of the same arrangement. Resolving a window is a query: a window answers the slot it holds, or the lowest slot no live window of its application holds, and only the creation of its panel takes the slot. A window holds its slot until it dies, so a window that closes and reopens takes the slot it left. A monitor panel that appears after the binding, through hotplug or a reload of the mirroring consumer, is restored as it appears. The source and listener are effects of the context the binding was made with, so they end with that activation, and a bind that fails during an initializer is rolled back with the failed load. A binding has no disposal of its own: one kept past its activation answers nothing, refuses to save, and holds no reference to that activation's context or services. A normal quit attempts to save. A returned write failure or a thrown save error is reported by the frame provider, and `lovr.quit` returns `false` so the failure does not veto shutdown.

The desktop consumers require the contracts they use. Consumers that resolve global appearance require theme directly. The manager also requires theme for its graph and details drawing, and uses UI for control and titlebar styling. The shipped desktop adds the `desktop/theme` selector, which requires `lunette/theme` and `lunette/menu` and has `preset` and sparse `overrides` settings as described above.

Geometric options use native `vector` values constructed with `vector.pack(x, y, z)`. The hint and error consumers take a vector `position`, the wrist menu takes a vector `offset`, the monitor consumer takes a vector `placement.center`, and the arc layout takes a vector `tuning.center`. Each rejects non-finite components. Option resolution replaces a vector as a whole. Colours remain numeric lists, and pose matrices remain `Mat4` values. The built-in modules own their defaults. Saved arrangement poses remain sixteen-number strings in the existing format.

The shared keyboard display places its keyboard at the configured horizontal `placement.distance` from the head, independent of head pitch, and below it by `placement.drop`. A near-vertical head direction uses the forward direction `(0, 0, -1)`.

`desktop/pacing` observes, for every window panel, whether it is hidden, its window's `contentType`, and whether its window's `commit` changed since the previous frame, and passes them to a pacer kept for the window. Whether the client drew is observed only while the window is unthrottled, because a throttled client's commits describe the throttle; the pacer's exemption is then decided by the history from before the throttle and the hint. With the default tuning a hidden panel's window is paced at 1 Hz, a hidden video, game, or busy window at 30 Hz, and a shown panel's window is unthrottled. A window without a panel is not paced, and a window whose panel is removed is returned to unthrottled. A monitor panel is not a window and has no frame rate; while `pauseMonitors` is true a hidden one's capture is paused with `monitor:setPaused` and resumed when it is shown or removed.

`desktop/scale` measures the distance from the head, `lovr.headset.getPosition 'head'`, to the centre of every shown window panel, takes the nearest for each `window.output`, and sets the output's scale when its chooser's step differs from the scale last set. An output shared by several windows takes the scale its nearest shown panel wants, so the nearest is sharp and the others render more pixels than they need. An output with no shown window panel keeps its scale, a monitor panel gives no distance because a monitor's scale is its host's, and nothing is done while the headset reports no head.

Unloading either entry undoes what it did. `desktop/pacing` returns every window it throttled to unthrottled and resumes every capture it paused. `desktop/scale` sets every output it changed back to the scale it had before the first change, unless the output's scale is no longer the one it set, which means another plugin has set it since. A source reload therefore returns each output to its original scale and raises it again on the next frame.

`workspaces` is an optional desktop configuration field with the workspace consumer's `Config` type. It inserts `desktop/workspaces` immediately before `desktop/adoption`, sets `desktop/workspace.name` to the first configured workspace name, and sets `desktop/adoption.tags` to that name. The name is `main` when the workspace list is omitted. An explicitly empty list or invalid first name raises during composition. The expansion rejects `settings.workspace`, `settings.adoption`, preconfigured holder or adoption entries, and competing raw patches or inserts for the three affected ids. Explicit rule tags and persisted tags remain unchanged. A configuration that needs different coordination uses raw patches instead.

`@lunette-plugins/desktop/workspaces` is shipped and is not one of the default entries; a configuration can also add it with `{ insert = { id = 'desktop/workspaces', definition = require '@lunette-plugins/desktop/workspaces' }, before = 'desktop/adoption' }`. It holds one tag for each workspace and selects one, the first already selected or the first in the list. A panel that is a member of a workspace's tag and of no selected one is hidden by its visibility override, which the consumer withdraws rather than overrides to show the panel, so a panel another plugin hid stays hidden; a panel in no workspace's tag is left alone. Its options are `workspaces`, a non-empty list of unique `{ name }` records, default `main`, `two`, `three`, and `four`; and `follow`, default true, which moves a window placed into workspaces none of which is shown into the one that is, by excluding it from the others. `lua/lunette-plugins/desktop/workspaces/config.luau` owns these defaults. The removed `key` and `modifiers` options report migration errors. A child plugin registers actions in the Workspaces menu group with ids `desktop/workspace/<name>`, in configured order. Its selected state follows tag selection. A menu outage removes those actions and leaves workspace selection, visibility, and follow policy unchanged.

The frame provider runs each handler under its own protected call and reports a handler's error through `lunette.reportError`, so one handler's error does not stop the others, including the error panel's.

They do not establish an actual XR or GPU-backed boot, host-desktop acceptance, or successful installation and execution of a copied configuration.

Safe mode is compiled into the binary and requires `lunette` alone. It does not depend on the provider roots or the desktop, because a missing or broken installed module tree must not prevent recovery. [The Lua API](lua-api.md#errors) records its behavior.

## Session composition and inspection

`@lunette-plugin/management` owns the running entry definitions and their session configuration. It publishes `lunette/composition`, whose service enables, disables, reloads, configures, adds, removes, restores, and recovers entries. Configuration preflight uses the definition's descriptor and resolver before any replacement cleanup. A failed initializer remains failed and inspectable; recovery explicitly reloads the most recent configuration observed active. Native replacement is not transactional. Cleanup failure retains a quarantined entry and its reservation rather than reporting removal.

The catalog retains each known entry's identity and source order after removal. `restore` reinstalls a known entry from its retained definition and last accepted configuration; it does not resolve a module path. Uninstalled entries remain catalogued even when restoration later fails validation or activation.

The composition service protects its own provider and the configured management entries. Protection follows their actual current and failed bindings and parent ownership recursively. `desktop.run` supplies `desktop/manager`, `desktop/menu`, `desktop/keyboard`, `desktop/pointing`, and `desktop/actions` as protection seeds when those ids exist in the composed list. Their actual dependency bindings keep the normal recovery controls available. Optional broker-inspection children are not protection seeds, and an inspection-only provider is not protected merely because the manager can inspect it. The raw runtime remains native mechanism; callers that mutate it directly bypass the composition service's policy.

`Runtime:snapshot()` returns coherent detached records without running callbacks, draining lifecycle work, or consuming diagnostics. Its instance, binding, generation, activation, and effect identities are exact decimal strings. It distinguishes declared capabilities from actual allocation bindings and failed activation bindings. It records enabled intent, retirement, phase, authority, ownership, dependents, blockers, lifecycle failure, and effect states. Native inverse identity describes the actual acquisition owner, not an inferred broker caller. Disarmed effect metadata remains for the complete activation, so inspection storage and copying cost grow with acquisitions until the next activation or removal. Callable inverses are released when disposed.

Inspectable brokers expose `inspect()` through their neutral service contracts. A snapshot contains primitive metadata for logical registrations, actual owners, resource counts, service state, and explicitly unavailable facts. Inspection invokes no user handler, offer, rule resolver, clock, or filter, and performs no dead-member pruning. Logical registrations and native effects have separate counts because one registration may acquire several effects. A tag membership or exclusion's `live` and `dead` fields describe its retained entry and owner status. Its `details.targetLiveness` reports a raw boolean target observation as `live` or `dead`, or `unavailable` when observation would require a getter. Window source identities are numbers, and monitor source identities are strings. Mutable opaque custom references remain atomic; structural configuration snapshots do not claim to detach those references.

`desktop/manager` offers a movable flat panel through `lunette/ui`, hidden initially. Its Plugins menu action, `desktop/manager/open`, toggles the panel named `desktop/manager`, and its selected state follows visibility. The panel opts into the shared Plugins titlebar. Its X button hides the panel with the same cancellation and focus cleanup as the menu toggle, and its background supports trigger dragging. The panel initially shows an entry list with runtime state and protection status. Selecting an entry opens its details and lifecycle actions. Entries and Graph switch between the list and the diagnostic custom `graph` region. Graph navigation appears only in Graph, and configuration and catalog actions appear in their corresponding sidebar tabs. Buttons, text fields, and choices use shared controls with stable ids. The configuration and catalog rows use custom scrollable regions with one controller-owned offset. `@lunette-contracts/ui` is the public contract; `@lunette-plugins/ui` is the replaceable built-in provider. The pure graph projection and editor transformations remain separate from UI input and drawing. The graph supports pan, zoom, selection, search, forward and reverse dependency traversal, direct and transitive traversal, and affected-instance traversal. Parallel relationships and self-loops remain independently selectable. The sidebar exposes lifecycle, ownership, binding generations, effects, broker registrations, and configuration metadata. Independent child consumers inspect each broker; an inspection-only provider outage suspends its reader without withdrawing the management panel. Schema editing preserves callback and custom references and leaves opaque values read-only. Text-field confirmation updates the editor draft; Apply remains a separate action that invokes composition preflight. Field blur retains the draft, and rejected edits report an error without discarding it. Recovery remains explicit. The manager uses no global frame key or text handlers. `lua/lunette-plugins/desktop/manager/init.luau`, `config.luau`, and `widgets.luau` own the consumer, its configuration schema, and its UI controls.

## Module lifecycle

The host's source reload retains the Lua state. It shuts down plugin runtimes, which advances the plugin contract epoch, clears native subscribers and configuration callbacks, drops unprotected modules from `package.loaded`, and runs `main.luau` and `lovr.load` again.

Plugin implementations register cleanup effects with their context or owner. The native runtime runs these effects during disable, instance reload, disposal, and shutdown. An expired activation cannot use its context or publisher. [Architecture](architecture.md#plugin-runtime) states how a cleanup failure quarantines an instance and how the failure is reported.

Plugin effects are the only cleanup mechanism. There is no Lua teardown registry; issue #32 places that role in the effect layer. A library module keeps no module-level state: a persistence state belongs to the caller that creates it, and its bindings are plugin effects. A Lua module outside a plugin that owns native resources releases them through a lifecycle path of its own or tolerates their continued existence; [Known gaps](#known-gaps) records this.

## Policy and mechanism

| Concern | Owner | Reason |
|---|---|---|
| Window and monitor handles, sinks, input delivery, outputs, layers, and capture | `lunette` | These operations cross native, compositor, or device boundaries. |
| Panel layout, surface picking, pointer behavior, and frame-rate policy | Lua modules and providers | Configurations can replace policy without changing the native API. |
| Contract identity, exact provider bindings, lifecycle, and resource cleanup | Native plugin runtime | These rules span service providers and must remain consistent within a runtime graph. |
| Service methods and configuration types | Luau contracts and definitions | The checker can validate local source shapes without inferring the complete runtime graph. |

The panels provider adapts native window and monitor pixels to Lua-defined geometry and interaction. Its `rendering` setting defaults to `'plane'` so window content participates in scene depth and stays behind session controls. `'layer'` opts windows into sharper backend-owned composition layers with scene fallback. A monitor panel remains in-scene because the native layer claim API accepts windows, not monitors. Interaction keeps pointer hover and keyboard focus separate; pointer motion does not implicitly take focus. These boundaries let a configuration change geometry and input policy without changing Wayland protocol behavior.

## Decisions

The Lua roots stay separate from `lunette`. The native root exposes mechanism, while the providers and consumers hold replaceable policy. Keeping distinct roots avoids making a Lua implementation look like native mechanism and lets a configuration replace or omit any provider.

Liveness of a service belongs to the facade, not to each provider. A guard in every provider against calls after its activation ends is repeated code, and a provider that omits one exposes torn-down state. The facade's service view enforces liveness once for every provision. Providers keep the checks that guard objects outliving a call, which the view does not reach.

Neutral contracts stay separate from providers. A contract describes a service without importing the module that implements it. This allows plugins to typecheck against the service surface while keeping provider implementations replaceable.

The plugin API uses local capability and configuration types with runtime graph validation. A recursive inferred type for the complete provider graph exceeds Luau's 20,000 subtype-normalization budget even with an empty initializer. Changing compiler flags or limits was rejected. Local static checking remains useful, while declarations and the lifecycle graph validate whole-runtime wiring.

The native adapter contains erased casts. A mapped `Services<R>` and `Provisions<P>` authoring API is not used. `Context:require<T>(capability)` and init-only `Publisher:provide<T>(capability, value)` keep the public typing model direct and place runtime membership checks at the boundary.

### Desktop consumers reach frame and surfaces through contracts

The desktop consumers require `lunette/frame` and `lunette/surfaces` and take no callback registry through their configuration, and they are installed under `@lunette-plugins` rather than kept as configuration files. A registry passed through configuration would tie a consumer to the configuration directory: it could not be moved out of it or written by a user without copying the registry. [The Lua API](lua-api.md#frame-dispatch-and-the-surface-list-are-contracts) records the contracts' shape, the phases, and why the LÖVR callbacks are bound by `frame.install` rather than by the provider. Offering panels as surfaces is a child plugin of `desktop/render`, so a surfaces outage stops pointing at panels and leaves them drawing.

### Pointer feedback draws after overlay UI

The frame contract separates update and draw phase sets. Picking remains in the `pointing` update phase after scene geometry, so overlay reactions observe the current hit. The final `feedback` draw phase places beams and landing indicators after every scene and overlay draw. The manager draws with scene depth testing. Pointer feedback disables depth testing so its indicator remains visible over panel content; depth-free custom overlays still require the final draw phase. Raising the pointing draw's numeric order is insufficient because order applies only within a phase. Moving the pointing update after overlays would also change interaction timing. The existing draw phases and shared phase aliases remain valid for callers that do not draw pointer feedback.

### UI depth offsets follow drawing nesting

Opaque shared UI backing and outline geometry writes scene depth; corner cutouts contain no depth-writing geometry. Controls, their contents, and glyphs use successive 1 mm offsets without depth writes. This prevents coplanar conflicts and preserves sibling painter order without accumulating physical depth across controls. The built-in details span 3 mm in front of the backing. Intersecting or nearly coincident panels can show draw-order-dependent details within that span. This limited overlap is accepted rather than adding per-panel visibility masks. The [UI drawing contract](lua-api.md#ui-panels) specifies the offsets and hook state.

### Panel lifecycle is announced through the panels contract

The panels contract carries owner-scoped `onAdded` and `onRemoved` listeners, and every consumer that follows a panel's life uses them. A consumer that imports the panels provider's private modules cannot work with a replacement provider that implements only the contract, and a module-global registry of per-panel cleanups outlives activations. A per-panel destroy hook was rejected: owner-scoped listeners are effects of their owner, so a listener ends with the plugin that registered it.

A panel is released before its owner's effect is disposed, rather than by that effect's inverse. The runtime withholds an owner's authority while one of its inverses runs, so a removal announced from inside the inverse would reach the owner's own listeners, such as rules ending its placement, as if the owner were gone.

### Consumer resources are released on the consumer's owner

Pointers, lasers, keyboards, focus targets, and input sources release their resources through inverses on the consumer's owner. Direct disposal raises its own inverse failure; routed input returns explicit results for delivery and native cleanup refusal or failure. Registering the release as an effect of the provider's context was rejected because a failing inverse would quarantine the provider for every consumer. The interaction and laser providers' own teardown releases anything left, which happens only if an owner never unloaded.

### Focus and tag changes belong to the owner that made them

Focus targets belong to the owner that registered them. Their current route and native per-seat authority have separate lifetimes. Ending a target clears only authority it still owns, and ending the current target leaves no route. Restoring an older route was rejected because the earlier owner or interaction can have ended. Clearing all native seats on every route change was rejected because an independent seat still has its own authority. Stable native identifiers and `lunette.defaultSeat` keep authority consistent with fresh wrappers and omitted-seat delivery.

Sources snapshot one route per operation and retain native inverses on its original sink and seat. A local receiver that declines or fails cannot forward into an application behind it. Physical committed text is eligible only for the batch revision captured before bindings; a transition or consumed or failed local key invalidates remaining text until the next update. Per-key text suppression was rejected because LÖVR does not correlate the callbacks. The keyboard resets latches and locks on route changes immediately and uses the same live keymap selection for legends and virtual translation. These contracts support local receivers without requiring a widget or menu implementation.

Tag memberships are held per owner. A tag's selection is a stack of per-owner overrides in which the most recent live override wins. No consumer changes another's focus, selection, or memberships without an inverse. Reverting an owner's tag change to the value from before it was rejected because the outcome depends on unload order and can restore a value that belonged to an ended owner.

### One registration per name and one laser owner per hand

Registering a rules source under a name already registered raises, and so does `attach` for a hand whose laser another owner holds. Replacing the registration, or answering the existing laser, was rejected: either ends or shares a resource another owner still holds. A consumer that needs a shared resource borrows it from the provider that brokers it.

### Saved slots are held by windows

A slot is held from the creation of the window's panel until the window dies, resolving is a query, and the source reads the arrangement last saved. Taking a slot on every resolve was rejected: `rules:resolve` would consume slots, and a window that closed and reopened would lose its placement. Freeing a slot when the panel is removed was rejected: a provider outage removes every panel while the windows remain, and recovery would then give windows each other's slots.

### The arrangement is saved on a drop and at quit

The arrangement is saved on a grab's drop and at quit. Saving on panel removal was rejected: a panel is removed mostly by outages, reloads, and unloads, when the binding is ending and a save would capture a desktop that is coming apart. A drop is the moment a user has finished arranging a panel.

A drop is announced through `lunette/drops`, and pose memory and the save both hear it, so the saved arrangement and the native property agree. A grab ended while the interaction provider is live, including by the pointer's owner unloading during an interaction outage, emits the drop. A grab the provider's own teardown ends emits nothing, because the provider's context can no longer act as an owner; that happens only to a pointer whose owner never unloaded, and the pose is then neither remembered nor saved until quit.

### A persistence binding ends with its activation

A persistence binding has no disposal of its own. Its rules source and arrival listener are effects of the context it was bound with, so they end with that activation, and a bind that fails during an initializer is rolled back with the failed load. A `dispose` method was rejected: with the effects owned by the context, it could only stop the binding answering while its source still held the source name, so a second bind in the same activation would fail.

### The desktop is an installed root, changed by patches

The desktop's consumers are installed under `@lunette-plugins`, the composition is the installed `@lunette-desktop` root, and it is a list of entries with ids that a configuration changes with patches. Consumers kept in the configuration directory, composed by a fixed sequence in `main.luau`, were rejected: a user configuration could not reuse a consumer without copying it, and changing one provider would mean copying `main.luau`. The patches are modelled on profile patches: they name what they change by a stable id, and they say whether to remove, replace, configure, or add, rather than restating the list. Unknown ids and conflicting patches raise, because a patch that silently matches nothing is a configuration that does not do what it says. Each id takes one patch, so the outcome never depends on which of two patches applied last. Exposing the instances as a mutable table the configuration edits was rejected: it would have no error for a misspelt id and no point at which the result is known to be complete.

The root is required for installation, like the provider roots, because the shipped configuration requires it and an installation without it cannot run its own default. Safe mode is compiled into the binary and requires none of it.

### Desktop settings expand without merging plugin lifetimes

Typed `settings` reuse each consumer's `Config` and expand to ordinary patches. A combined desktop plugin was rejected because it would require the union of its consumers' dependencies and remove independent outage behaviour. The workspace option coordinates the holder and adoption with the first configured workspace, while explicit rule and saved tags remain authoritative. Competing settings and raw patches raise instead of depending on an implicit precedence. Raw patches remain available for configurations that need another coordination.

### Every plugin is under `@lunette-plugins`

A shipped plugin lives in `@lunette-plugins` whatever its role, and `@lunette-desktop` holds only the composition. Repository-only development plugins live under `dev/plugins/` and are loaded by their configuration, not installed as standard-library modules. A reader looking for any plugin, a provider or a consumer, looks in one root, and a configuration that composes a list of its own reuses a consumer the way it reuses a provider. A provider's folder is the contract it provides, and any other plugin's folder is its entry id, `desktop/<name>` for a desktop consumer, because the id is what a patch and a log line name, so the path follows from it; it also keeps the consumers that share a subject with a provider, such as `desktop/keyboard` beside `keyboard` and `desktop/pacing` beside `pacing`, apart without renaming either. Grouping the consumers by domain, such as a `windows/` or an `input/` folder, was rejected: the ids cannot change without breaking existing patches, and a path that differed from its id would have to be looked up. Keeping the consumers in `@lunette-desktop` beside the list was rejected because it made the composition root also an implementation root, so reading what the desktop is meant reading through what each part does. `desktop/persistence` provides `lunette/arrangement` as well as consuming, so it follows the provider rule and is `@lunette-plugins/arrangement`; its id stays `desktop/persistence` so existing patches still name it. Each plugin is a folder, so what belongs to it stays beside it.

### Shared vocabulary lives with what it describes

Each shared helper lives where its subject is. A helper kept in an optional root would make a shipped provider depend on a root an installation may lack, and a copy kept to avoid that dependency would drift from the original.

The key names are the native seat and sink API's vocabulary, because that API speaks evdev codes, so `lunette.keyCodes()` answers them. The table is read from `lunette-capture`'s `VirtualKey`, the closed set the host sinks emit, so a named key reaches either kind of sink and the names cannot drift from what the runtime sends. `lunette.lockingModifierNames()` answers the modifiers a keymap locks, read from `KeyModifier`, beside `lunette.modifierNames()`. The Luau type of the table is keyed by a `KeyName` union, so a misspelt key is a type error. Generating the table from `linux/input-event-codes.h` is not possible without a new dependency or a copy of the header, and no crate in the tree carries its constants; the codes are instead checked against xkeyboard-config's evdev table through libxkbcommon, which the compositor already links. A hand-written table in `@lunette-contracts` was rejected because it would restate what the runtime knows and go stale when the set changes.

Which key latches which modifier on an on-screen keyboard, and how LÖVR's desktop key names map to codes, are policy several consumers agree on rather than native facts, so they are `@lunette-contracts/keys`, written in terms of the native names. The default rows are the keyboard provider's `rows` option, because a layout is the keyboard's configuration. Pose encoding is `@lunette-contracts/vocabulary`'s, next to the property it encodes, and it is the one encoding the property store, rule sources, and the arrangement file share. The pose property is `lunette.pose`, named for the session rather than for the module that encodes it. Persistence is `@lunette-plugins/arrangement`, the plugin that provides `lunette/arrangement`, and its custom-format API is a field of that module, because a configuration writing a format is configuring that plugin; a replacement for it is still chosen in the desktop's composition, under the `desktop/persistence` id. Keeping it in `@lunette-desktop/persist` beside the entry list was rejected once the desktop root came to hold only the composition, as [Every plugin is under `@lunette-plugins`](#every-plugin-is-under-lunette-plugins) records.

### Configuration merges records and replaces everything else

A schema-backed configuration merges declared objects and replaces arrays, maps, unions, and atomic values. `{ style = { color = ... } }` changes one colour and leaves the rest of the declared style. An empty array or map replaces its default, while an empty object retains declared defaults. A colour list and a geometric vector are each one value. Merging `{ 1 }` into `{ 0.5, 0.5, 1, 1 }` by position would yield a colour the configuration does not specify. A shallow merge is insufficient because changing one colour would restate the whole style. Descriptor-driven validation replaces inference from defaults because optional values, closed unions, callbacks, and empty collections need an explicit type. The descriptor states each option once and supplies runtime parsing, editor metadata, and the static input and output types. Legacy `plugin.options` retains its default-inference semantics for compatibility; built-in plugins do not use it.

### Geometric values use native vectors

Three-dimensional positions, directions, and offsets use native vectors. Native vectors provide component fields and immutable arithmetic, and `Mat4:translate` accepts them directly. Numeric tables for these values were rejected because they lose the geometric type and require repeated indexing and scalar arithmetic. Callers use the value returned by methods such as `normalize`; these methods do not change the receiver. Configuration validation checks finite components with `plugin.checkVector`. Colours and numeric lists are not geometric vectors, and saved poses retain full matrices and their existing format.

### Provider modules share one shape

Every provider module answers `{ definition, define, build, requires }`, made by `plugin.provider`, so a configuration varies, wraps, or replaces any provider the same way. `define` makes a variant without copying the module, and `build` lets a plugin wrap a built service and publish the wrapper. Exporting a bare definition was rejected: a variant would copy the module, and a plugin could not reach the built service to wrap it. Wrapping changes only the outer surface: a built-in calls its own methods through closures, not through `self`, so a wrapper that replaces one method does not change what the others do. Variation inside a provider is left to hooks; [Provider modules](lua-api.md#provider-modules) records the convention they follow.

### Placement is composition entries

Placement is six entries: the workspace tag, the rule list, the persistence binding and quit save, adoption, the arrangement of unplaced windows, and pose memory. Section 6.5 of the Cordis paper describes the form: a concern that joins several services is an integration component of its own, so each can be replaced, configured, or disabled without touching the others. One policy entry for all of them was rejected, because replacing the layout, the rules, or persistence would mean copying the whole of it. The granularity follows what a configuration changes independently: the rule list, the layout and its options, and the workspace's name are each one entry's configuration, and disabling one leaves the others working. Finer splits are not made where nothing changes separately: install and start of adoption stay together because a start without the native pose source loses hand-placed poses across reloads.

The entries communicate through contracts rather than shared locals. `desktop/arrange` learns of placements from the placement contract's `placed()` and `onPlaced`, which carry the resolved properties, rather than from the start caller's own callback, which only the consumer that started adoption receives. Listening to `panels:onAdded` was rejected: it reaches every panel, from any plugin, without the properties that say whether a rule or saved state already placed it. The two entries that keep state across their own outages, persistence and arrangement, are factories.

`desktop/arrange` removes a panel from its set when the panel is dropped, so a manual placement stays manual and the panel does not return to the arrangement when another window closes. Re-arranging on a drop was rejected: the remaining windows moving as the user lets go of one would undo the arrangement the user is making. The arrangement re-applies when a panel is removed rather than when the native window closes, because the window's panel is removed only on the next update, and an arrangement made at the close would include the closing window.

`rules:setRules` and `rules:fromList` reject a rule under a key outside the list's positions and a rule field other than `match` and `properties`, naming the key. Iterating with `ipairs` would drop such a rule without a word, and `desktop/rules` takes the list as configuration, where a list replaced by a record is an easy mistake.

### The base consumer is three entries

Rendering, monitor mirroring, and the empty-scene hint are `desktop/render`, `desktop/monitors`, and `desktop/hint`, so a configuration replaces the mirroring or the hint without the rendering. One entry for all three was rejected: it would require surfaces, so a surfaces outage would stop panels drawing. Offering panels is a child of `desktop/render` that requires surfaces, rather than a fourth entry, because it shares rendering's lifetime and has nothing to configure; the child loads with its parent and waits for a surfaces provider without holding the parent back. Mirrors are laid in a row from the centre outward, each taking the lowest free place, rather than re-laid when a monitor comes or goes, because a saved arrangement restores a mirror as it appears and a re-layout would move every restored mirror. Tagging mirrors is a child for the same reason as offering: a tags outage would otherwise take the mirrors away.

### The entries need no order but one

Tags are held, so whichever of the workspace, a placement, or the saved arrangement needs `main` first makes it, and it lasts while any holds it. With an exclusive `new`, the workspace consumer would fail whenever a placement made `main` first. Inserts take `before` and `after` for the dependence that remains, a rules source that must be registered before adoption resolves the first window. Reordering existing entries by patch was not added, because no shipped entry depends on another's position except through that one rule, and moving an entry is better said by disabling it and inserting its replacement.

### A kept pose is a drop the arrangement remembers

`desktop/arrange` leaves out a window whose `lunette.pose` property is set, as well as a panel dropped while it was active. `desktop/pose-memory` writes the property on every drop and adoption reads it back after a reload, so the two agree that the window is the user's to place, and a window dragged during an outage of `desktop/arrange` is not arranged again on its return. Recording drops in the drops broker was rejected: the broker's record would end with its activation, and a drops outage would then lose what the property keeps.

### Workspaces are shipped outside the default entries

Workspaces hide windows in unselected workspace tags and add workspace choices to the menu. A configuration opts into that visibility policy. The consumer is installed in `@lunette-plugins`, checked and tested with the rest, and added with the workspace shorthand or one insert, rather than being an example a user copies and keeps up to date. Its menu actions are a child, as the monitors' tagging is, so a menu outage does not show every hidden window or reset workspace selection. Physical workspace chords are not part of the shipped consumer because session controls must remain available through VR input.

### Persistence takes its file, format, and identity

The file, the format, and the identity a window is keyed on are `desktop/persistence`'s options, so changing one does not mean replacing the policy. A format is a pair of functions rather than a name of a built-in one, because a format of a configuration's own is the point, and it answers the loads `format` constructs, so the version rules that stop an old writer from corrupting a newer file hold for it too. The state is made at the first activation, because an option is known only then, and made again only if the options change. The consumer provides `lunette/arrangement`, so a menu action saves without reaching into the factory's state. `examples/desktop/save-menu.luau` demonstrates Save arrangement and Restore arrangement through that contract; `examples/desktop/hide-windows.luau` supplies the example's Hide windows action.

### A relative require resolves against the requiring file

A session resolves a relative require by Luau's rules, the ones an editor and the checker apply. Resolving it as LÖVR's loader does, against the configuration root, was rejected: the checker and the session would agree only for a module at the top level, and a plugin split across a subdirectory would check clean and fail to load. The resolution is a wrapper around the global `require` rather than a patch to LÖVR's loader, because a loader receives only the name and not the chunk that asked for it. Replacing LÖVR's require with Luau's own require library was rejected: it keys its cache apart from `package.loaded`, which source reload clears, and it resolves aliases through `.luaurc` files a session does not read. The wrapper is Lua and calls the original `require` from Lua, so a module's own error reaches its caller as the loader raised it; only the resolution, which needs the requiring chunk's full name, is native.

### Typed patches are a function per entry

`configure` gives each shipped entry that takes options a function typed with that entry's `Config`, answering the plain patch, so the checker reads the options and composition is unchanged. A plain patch's `config` is `{ [string]: any }`, which passes a mistyped option to fail when the entry loads. A patch type discriminated by `id` was rejected: the union needs an arm for an id it does not know, for entries a configuration inserted, and that arm accepts a mistyped option for any shipped entry too. A helper per patch kind beyond configuration, such as one to disable or replace, was not added: those patches carry nothing an entry's types describe.

### A window in several tags is arranged by its selected tag

`desktop/arrange` takes the selected tags first, so a window in several tags is posed by a layout the user is looking at. A window that belongs to every workspace is laid out with the workspace in view, which is what tiling window managers do for a sticky window, and a selection change arranges again, because which tag owns a window can change with it. Arranging a window once per tag was rejected: the last layout to run would decide its pose.

### Layout options are keyed by layout name

`options` are keyed by layout name, and a layout gets its own entry whichever tag uses it, so a tag that chooses another layout than the configured one still gets that layout's options. Options carried by the tag, `tag:setLayout { layout, options }`, were rejected: a tag is membership and selection that any plugin may read, and parameters for one consumer's layouts are that consumer's configuration. Two tags using one layout with different options is the case this does not cover; a layout registered under a second name with other defaults covers it.

### Pacing and scale are providers

Frame pacing and output scale are the `lunette/pacing` and `lunette/scale` providers, which issue #38 specifies, and the `desktop/pacing` and `desktop/scale` entries read the scene and apply them. The providers hand out a pacer per window and a chooser per output, built from the pure rules in `@lunette-plugins/pacing/pacer` and `@lunette-plugins/scale/chooser`. The split follows what a configuration changes independently: a different rule is a `choose` or `ideal` hook or a provider of the contract, and a different reading of the scene, such as pacing by gaze, is a different consumer that keeps the provider. Neither provider requires anything, because a pacer and a chooser read nothing. The issue suggested that scale require panels and interaction; the consumer measures from the head, which is the headset's, and reads no pointer, so it requires frame, panels, and scale only.

The native API answers the two facts the consumers need: the output a window's client is shown on, `window.output`, and the buffer its pixels came from, `window.commit`, which gives the observed commit rate the pacer needs; [The Lua API](lua-api.md#a-window-names-its-output-and-its-latest-commit) records them. The pacer adds no sample for an observation that does not say whether the client drew, and the consumer observes drawing only while the window is unthrottled. Counting a throttled window's commits would end a video's exemption a second after its panel was hidden, since a client paced at 30 Hz commits on a third of the frames. A visible window is always unthrottled, and the tuning has no rate for a shown window: such a rate would be an option of type number or false, which option validation cannot describe, and a `choose` hook paces a shown window when that is wanted.

Both entries are on by default, a user decision: a hidden panel at full rate and a scale fixed at 1 are costs a user would otherwise find rather than choose, and disabling either is one patch. Unloading reverts what an entry changed, because every change a consumer makes to state it does not own is an effect of its owner. Leaving the rates and scales as they were was rejected: an entry disabled by a patch after a reload would leave outputs at whatever step they last had, with nothing to return them. The cost is that a source reload returns each scaled output to its original scale and raises it again on the next frame, two re-layouts a reload. A scale is restored only when it is still the one the entry set, so a scale another plugin set since is not overwritten.

No optional root of helpers sits beside the providers, consumers, and vocabulary. Helpers live beside what they describe, as [the vocabulary decision](#shared-vocabulary-lives-with-what-it-describes) states, and an optional root would be a fourth place for Lua policy, mounted by every session and read by the checker whether or not anything uses it. Every installed root is required, and the `LUNETTE_STDLIB_PATH` override describes the Lua roots in general.

### UI controls use a replaceable owner-scoped contract

Small local VR controls are supplied by the `lunette/ui` provider rather than embedded in each desktop consumer. A neutral contract lets a configuration replace rendering and control policy without importing a built-in panel record or widget implementation. General layout containers and a complete desktop widget framework remain outside this bounded toolkit. Larger application interfaces can remain Wayland clients. Native grapheme segmentation is shared mechanism; text editing, focus integration, themes, and drawing stay in Lua.

### Rounded drawing keeps bounded geometry and input policy

Shared clipped meshes and conservative content rectangles keep drawing, descriptions, and initial hits consistent without a stencil-capable pass or offscreen composition. Smaller safe clips retain overflow reporting instead of changing caller bounds. Custom hooks remain responsible for clipping because the toolkit cannot enforce arbitrary shader and stack operations. Rectangular control and key targets preserve usable corner area on small controls; only the outer panel silhouette removes initial hits. Native dragging retains original-sink release pairing and bounded motion because capture projection would change application input policy.

### A frame attachment belongs to its target

The optional frame attachment conveys resolved header outline style and target-owned eligibility. A general container or shape-transform contract would add unrelated layout responsibility. The target already owns body geometry and actual layer state, so it draws one continuous outline and can retain a dormant attachment across temporary ineligibility. The header outline supersedes the body outline to prevent mixed border widths and a doubled seam. Granted layers remain rectangular to preserve their raw-copy sharpness and claims. A flat header remains separate from a curved body because a continuous curved header is outside this relationship. [Rendering decisions](rendering.md#rounded-meshes-and-conservative-clips) records the rendering alternatives.

### Menu actions are separate from the shared keyboard display

The menu broker holds owner-scoped callbacks and immutable display values without requiring frame, surfaces, UI, or keyboard services. Rendering consumers can reconnect after a broker outage without changing unrelated session state. Enabled and selected values are explicit owner updates rather than getters, so listing and inspection cannot run action policy. A registration token disambiguates a retained row after the id is reused.

`desktop/menu` renders the tracked wrist control and scrollable action list through `lunette/ui`, and invokes actions through `lunette/menu` with each row's registration token. Tracking loss closes the list and cancels its gestures. `desktop/actions` registers reload and shared keyboard visibility; the manager registers Plugins, and workspace actions have their own child lifetime. Keeping rendering separate from action registration lets a configuration replace the UI provider or action broker without rewriting session policy. The shipped reload and workspace controls use menu actions instead of physical session chords, while the neutral bindings provider remains available for custom input bindings.

The shared keyboard display observes focus metadata rather than being required by each widget. This avoids a dependency cycle and lets substitute UI providers request the same keyboard. The display owns one lazy board and keeps manual visibility separate from a field's automatic visibility. Field-to-field changes preserve its placement; explicit hide ends only the matching current route. A replacement display does not replay retained focus because that notification belongs to an earlier display activation.

### Panel movement follows the controller pose

The interaction provider preserves the panel pose relative to the controller during a grab. The pose constraint hook remains available for custom placement policy. Upright-only movement is not a default because headset testing found it less usable than controller-relative translation and rotation.

### Manager refresh is bounded independently of drawing

The manager refreshes external runtime snapshots and widget geometry only while visible, at the schema-configured `refreshInterval` (default 0.25 seconds). Opening and control actions refresh immediately. Drawing retains its per-frame cadence. Full reconstruction on every frame adds graph layout, inspection, catalog, and geometry work unrelated to a display's refresh rate. A bounded refresh preserves observations without that repeated work. Headset frame-time measurement remains required.

### Luau sources use the `.luau` extension

Every Lua source in the tree uses the `.luau` extension, because every source is Luau: type annotations, explicit instantiation, and `read` properties appear throughout, and an editor that sees `.lua` highlights and checks them as Lua, which reports them as errors. The shipped and example configurations, the roots, the specs, and the test fixtures are `.luau`, and the shipped configuration's entry point is `main.luau` beside `conf.luau`. Upstream LÖVR's `boot.lua` names only `main.lua`, so the fork resolves `main.luau` first under Luau ([LÖVR integration](lovr-integration.md#mainluau-as-the-entry-point-under-luau)). A user configuration with only a `main.lua` still boots, because the fallback is LÖVR's rather than lunette's, and `lunette check` still reads `.lua` files; the host makes no separate choice about which file is the entry point. Keeping `.lua` and associating it with Luau in each editor was rejected: every contributor and every user would have to configure it, and any tool that infers the language from the extension would still read the files as Lua.

## Known gaps

Source reload runs no cleanup for Lua code outside the plugin runtime. A non-plugin module that retains native resources keeps them after the reload unless another owner releases them.

The desktop tests do not establish an actual XR or GPU-backed boot, host-desktop acceptance, or successful installed-session execution. Geometry and mesh recorders do not rasterize edges, alpha, depth, stereo seams, or fonts. The operator-run `theme-rounded-content`, `theme-joined-frame`, `theme-widget-edges`, and `theme-rendering-exceptions` gates remain pending, along with `theme-appearance-matrix` and `theme-runtime-switch` for appearance and continuity. The separate `theme-broker-lifecycle` gate remains pending for arbitration and reentrant lifetimes; `theme-font-fit` remains pending for native development and installed-session font loading. [Headset verification](../guide/desktop-configuration.md#headset-verification) lists the rounded-geometry observations.

Virtual key translation has no stateful dead-key or compose engine. Local receivers take committed UTF-8 but have no IME or preedit protocol. Physical batch invalidation can discard unrelated text later in the same update-bounded batch. A native window source refuses a character its seat's keymap cannot represent rather than implicitly using `sink:typeText` with a temporary keymap. [Input](input.md#known-gaps) records the routing limitations.

## Deliberately left open

Pacing reads whether a panel is hidden, not whether it is in the field of view, gazed at, far away, or focused, which [Rendering](rendering.md#frame-pacing) lists among the inputs a policy may use. A panel behind the user is paced as if shown. Pacing by view direction risks a visible stutter as the head turns back, and choosing between the inputs is left until it can be tried on hardware.

The action broker, shared keyboard display, UI wrist menu, and reload and workspace menu actions are implemented. Plugins toggles the manager panel. The manager uses the UI service for its graph region, search and configuration fields, choices, scrollable sidebar regions, and controller actions. It has no `toggleKey` option or global frame key and text handlers; its configuration schema reports a migration diagnostic for a stale `toggleKey`. The checked `examples/ui` configuration adds a movable form through neutral UI, menu, and frame contracts. Logic-headless tests run its controller workflow, provider outages, and source reloads with both UI implementations. The current toolkit excludes full text shaping, bidirectional editing, IME composition, general layout containers, and a complete desktop widget framework. `manual_xr_widget_and_manager_acceptance` remains open for GPU-backed drawing and in-headset acceptance. Further spatial layout algorithms also remain open: the arc is the only shipped layout, and `examples/layout` holds a grid and a follow-me layout as examples rather than as shipped plugins.

Deferred follow-up issues include #15, #36, and #39. Their feature scope remains in the issue records. XR hardware and host-desktop acceptance remain human gates, and new desktop features remain outside this specification until their implementation and acceptance criteria are defined.
