# Standard library

`mullion` is an optional Lua library installed below `$PREFIX/share/lunette/lua/`. Its modules are policy choosers that no provider owns. They use the public `lunette` API, and can be replaced or omitted. `@lunette-plugin`, `@lunette-contracts`, and `@lunette-plugins` provide the typed plugin facade, neutral service contracts, and built-in plugin implementations. `@lunette-desktop` holds the desktop's consumers and the composition that starts them with those providers, which the shipped configuration runs. Their lifecycle and type boundary are specified in [The Lua API](lua-api.md#plugin-authoring) and [Architecture](architecture.md#plugin-runtime).

## Module roots

The source tree is `lua/`. A running session mounts file-backed roots through LÖVR's virtual filesystem. The checker resolves aliases from generated `.luaurc` files. `@lunette` is registered natively through `package.preload`; the checker reads its generated declaration from `lua/lunette/init.luau`.

The plugin facade is `lua/lunette-plugin/`. Shared contracts and vocabulary are in `lua/lunette-contracts/`. Built-in providers are in `lua/lunette-plugins/`. The desktop's consumers and its composition are in `lua/lunette-desktop/`. `lua/mullion/` contains optional policy modules. `lua/spec/` is a development-only root and is not installed. [Build and development](build-and-development.md#module-roots) records the source of truth and install behavior.

The root module `@mullion` re-exports nothing. Each module is required by its own path, such as `require '@mullion/scale'`. A configuration can use `lunette` without loading `mullion`, the built-in providers, or the desktop. No built-in provider, contract, desktop consumer, or the shipped configuration requires `@mullion`, and `crates/lunette/tests/optional_library.rs` checks that.

| Module | Responsibility |
|---|---|
| `mullion.scale` and `mullion.pacing` | Scale selection with hysteresis and per-window frame-pacing choice. No provider or shipped consumer uses them yet. |

That is the whole of `mullion` now: the root module and two choosers, none of which the shipped configuration loads. Pose encoding and the key vocabulary are contracts vocabulary, the default key rows belong to the keyboard provider, and arrangement persistence belongs to the desktop; [Decisions](#decisions) records why each moved. Panels, interaction, lasers, the virtual keyboard, tags, rules, adoption, layouts, and error display are built-in providers, the arc layout is a built-in plugin that registers with the layouts broker, under `@lunette-plugins`, not `mullion` modules, and [Decisions](#decisions) records why their earlier `mullion` implementations were removed.

| Module | Responsibility |
|---|---|
| `@lunette-contracts/vocabulary` | The surface and pointer types shared by several contracts, the per-window pose property, and `encodePose` and `decodePose`, the one encoding of a pose as the property store's sixteen numbers. |
| `@lunette-contracts/keys` | The key vocabulary: `CODES` from `lunette.keyCodes()`, `LOCKS` from `lunette.lockingModifierNames()`, `MODIFIER_ORDER` from `lunette.modifierNames()`, which key latches which modifier, and the translation from LÖVR's desktop key names. |
| `@lunette-desktop/persist`, with `arrangement`, `slots`, and `format` | Arrangement state `desktop/persistence` owns, capture and restore, the saved slot each live window holds, file loading and saving, and the versioned file representation. |

## Contracts and providers

A neutral contract module declares a service shape and exports a capability. The capability pairs a Luau type with an authority-qualified contract name and schema number. Vocabulary that is shared by several contracts belongs in a neutral contract module so service types do not need to import a provider implementation.

A plugin definition declares its name, its required and provided capabilities, and its initializer, whose configuration parameter gives the definition its configuration type. Its context reads required services with `Context:require<T>(capability)`. Its initializer stages provided services with `Publisher:provide<T>(capability, value)`. The native graph validates runtime wiring and publishes all provided values as one provider generation after initialization succeeds. See [Plugin authoring](lua-api.md#plugin-authoring) for the type boundary and runtime checks.

A provider's service methods carry no liveness guard of their own: consumers reach them through the facade's service view, which raises once the provider's activation has ended. Objects a method returns, such as panels, pointers, lasers, keyboards, and tags, outlive the call and check their own state. A provider whose owner-scoped method needs one of its own dependencies registers that work under its own context, inside the effect it places on the caller's owner, rather than forwarding the caller's owner; the adoption provider's `install` registers its rules source this way. A provider subscribes to native events for its own activation through `Context:on`. The adoption provider's `start` subscribes inside the effect it registers on the caller's owner instead, because that subscription belongs to the caller.

A resource a consumer asks a provider for, such as a pointer, a laser and its seat, a keyboard, a focus grant, a tag membership, or a selection override, is released by an inverse registered on the consumer's owner, not on the provider's context. A release that fails while the owner unloads is the owner's failure and quarantines the owner; the provider keeps serving its other consumers. A resource's `destroy` performs the release on its caller's stack and then disposes the owner's effect, whose inverse has nothing left to do, so a failure raises to the caller that asked for it.

Every change a consumer makes to state it does not own is an effect of its owner. A tag membership is held by the owners that added it, and the panel stays a member while any holder remains; an owner removes only its own hold, and the tag's owner removes every hold. A tag's selection is decided by the most recent live selection override, one per owner, and a tag with none has the selection it was created with. Keyboard focus is held by the pointer that gave it or by the owner of a `setFocus` grant, and a holder that ends withdraws the seat's focus natively and is no longer answered by `focused`, unless a later holder has taken the seat. A laser hand has one owner under `attach`, which raises rather than hand one owner another's laser. A rules source name names one registration, and registering a name already registered raises.

The panels contract announces a panel's arrival and removal to owner-scoped listeners, `onAdded` and `onRemoved`. Removal is announced for every cause: the owner destroying the panel or unloading, the source dying, or the provider unloading. Only the owner that created a panel destroys it. Rules ends a placement when its panel is removed, adoption ends an adoption, the desktop's mirror consumer ends a mirror, and persistence restores a monitor panel as it arrives, all through this contract and none through a provider's private module. A listener that raises is reported through `lunette.reportError` and does not fail the operation that added or removed the panel.

LÖVR's frame and input callbacks reach plugins through the `lunette/frame` contract, and the surfaces a pointer picks from are brokered by `lunette/surfaces`; [Frame and surfaces](lua-api.md#frame-and-surfaces) states both. `@lunette-plugins/frame` exports `install`, which binds the LÖVR callbacks to it, beside the module shape every provider has. Both providers call each handler and offer through `@lunette-plugins/protected`, which reports an error through `lunette.reportError` and continues; the panels provider calls its listeners the same way.

Constants and helpers that several providers agree on are neutral vocabulary rather than service fields. The per-window pose property is `@lunette-contracts/vocabulary`'s `POSE_PROPERTY`, written and read with its `encodePose` and `decodePose`; the key names, modifier keys, and locks are `@lunette-contracts/keys`; and ray intersection with a flat quad is `@lunette-contracts/quad`. A name the native API already answers, such as a key's evdev code or the set of modifiers, is read from it rather than restated. A provider's tuning and style are its configuration, merged over its defaults, and each activation receives its own frozen copy, so no consumer can retune another's.

Built-in provider modules exist for adoption, error display, frame dispatch, interaction, keyboard, laser, layouts, panels, rules, surfaces, and tags. The providers use the typed plugin facade. Each module answers `{ definition, define, build, requires }` and validates its configuration, as [Provider modules](lua-api.md#provider-modules) states. The options each takes are what it already tuned: panels' `style`, `priority`, `height`, and `aspect`; interaction's `tuning`; the laser's `style`; the rules provider's default `precedence` and the adoption provider's install `precedence`; and the error display's limiter, placement, size, `background`, and `clock`. Frame, surfaces, layouts, and tags take none. Those services still expose them as upper-case fields, such as `STYLE` and `TUNING`. The keyboard takes `rows`, `layers`, `style`, `modifierKeys`, `locks`, and the `onKey` and `drawKey` hooks, and its service exposes none of them; [Keyboard](lua-api.md#keyboard) states them. The arc layout, `@lunette-plugins/layout/arc`, provides nothing: it registers a layout with the layouts broker, and its module answers `definition`, `define`, and `requires`. It takes `layout`, the name it registers, and `tuning`; [Layouts](lua-api.md#layouts) states them. A pointer carries `vibrate`, which its creator supplies; the laser supplies its hand's controller. Replacing a provider keeps its capability and declared service shape. A replacement implements the existing interface; the contract is not weakened to accommodate it.

## Default configuration

`etc/xdg/lunette/main.lua` is the shipped configuration. It calls `require('@lunette-desktop').run()`, and `lua/lunette-desktop/init.lua` is the source of truth for the composition. The desktop is a list of entries, `{ id, definition, config }`, or `{ id, factory, config }` for a definition that is made once for each runtime. The entries are the frame, surfaces, panels, interaction, laser, keyboard, tags, rules, adoption, layouts, and `error-display` providers and the `layout/arc` registration, each under its definition's name, and the `desktop/base`, `desktop/pointing`, `desktop/input`, `desktop/keyboard`, `desktop/errors`, `desktop/workspace`, `desktop/rules`, `desktop/persistence`, `desktop/arrange`, `desktop/adoption`, and `desktop/demo-terminal` consumers, in that order. `entries()` answers the list, frozen, so a configuration can read the ids.

`run { patches = { ... } }` applies patches to the list, binds the LÖVR callbacks with `frame.install`, and from `lovr.load` makes one runtime, uses and enables each entry in order, and drains it; `lovr.quit` closes it. `run { entries = { ... } }` starts from another list instead of the default. A patch names an entry by `id`:

```lua
require('@lunette-desktop').run {
  patches = {
    { id = 'keyboard', disabled = true },
    { id = 'laser', definition = myLaser },
    { id = 'interaction', config = { tuning = { reach = 4 } } },
    { insert = { id = 'my-hud', definition = hud, config = {} } },
  },
}
```

`disabled = true` removes the entry. `definition` or `factory` replaces what the entry is made from and keeps its configuration. `config` is merged into the entry's configuration: a record, a table with string keys, merges key by key at every depth, and any other value, a list or colour included, replaces the value it lands on. A patch may replace and configure at once. `insert` adds an entry at the end and carries no other field. Ordering is not part of the patch language. The graph orders activation by dependency; among entries that do not depend on each other, the list order is the order they are enabled in and the order the graph loads them again after an outage of something they share. The placement consumers are listed in the order their effects must be in place, as the next paragraphs state, and an inserted plugin that registers a layout comes after `desktop/arrange`, which arranges again when the layout registers. Each id names one patch.

A patch that names an unknown id, an insert whose id is already an entry, two entries or two patches with one id, a field the patch or entry does not name, a patch that disables an entry and also changes it, one that gives both a definition and a factory, and one that changes nothing raise from `run`, with an error that names the id. `run` composes before it binds any callback, so a malformed patch fails the configuration's load and safe mode reports it. An option a plugin does not take is rejected by the plugin when it activates: that instance fails and its error is reported, and the rest of the desktop starts. `compose(options)` answers the patched list without starting it, and `start(entries)` makes a runtime from a list and answers it with the instance made for each id.

`run` also initialises the global guard `desktop/demo-terminal` reads, so source reload does not spawn another demonstration terminal. Each consumer requires the frame and surfaces contracts it uses, as a plugin in a user's configuration would, and validates its configuration with `plugin.options`, so an option it does not take is rejected by name. `desktop/base`, `desktop/pointing`, `desktop/input`, `desktop/errors`, and `desktop/persistence` take none.

Placement is six consumers, each replaceable or configurable by its id:

| Entry | Does | Options |
|---|---|---|
| `desktop/workspace` | Creates the workspace tag, selected, and holds it while active. | `name`, default `main`. |
| `desktop/rules` | Registers its rule list with `rules:setRules` under the default source name and precedence. | `rules`, the list; the default sizes and places Firefox. A list replaces the default wholesale. |
| `desktop/persistence` | A definition factory. Each definition creates one persistence state from `@lunette-desktop/persist` outside its activations, binds it as a rules source at each activation, saves when a grab drops a panel, and saves again at normal quit. | None. |
| `desktop/arrange` | A definition factory. Arranges the workspace's adopted windows that were placed without a pose with a named layout from the layouts broker, and drops a panel from the arranged set when the user drops it. | `layout`, default `arc`; `options`, the layout's own, which replace the default wholesale; `tag`, default `main`. |
| `desktop/adoption` | Installs the adoption provider's native pose source and starts adoption. | `tags`, the tags an adopted window joins unless a rule names others, default `{ 'main' }`. |
| `desktop/demo-terminal` | Spawns the first terminal emulator of its list that starts, once per Lua state, when the first start finds no window open. | `programs`, tried in order; an empty list opens nothing. |

The workspace tag exists before adoption places windows into it, and the rule list and the saved arrangement are sources before adoption resolves the first window, which is why they come first in the list. The rule sources apply in ascending precedence: configured rules at 100, saved arrangement state at 200, and native per-window properties at 300. A higher-precedence source overrides a lower-precedence value for the same property. Saved state supplies pose, size, and tags; the native source supplies hand-placed pose.

`desktop/arrange` reads what to arrange from the adoption contract's `placed()` each time it arranges, and arranges when it activates, when adoption announces a placement through `onPlaced`, when any panel is removed, and when a layout registers or unregisters. The arranged set is every live adoption placed without a pose that is a member of `tag`, in placement order, less every panel dropped while it was active. The dropped panels are kept in the factory's state, weakly, so an outage of the consumer does not return them to the set. A layout registered as `continuous` is also applied on every frame update, in the `scene` phase before the panels update. On the first frame after it activates, `desktop/arrange` logs a warning when no layout is registered under `layout`, naming those that are; it arranges as soon as one registers. A layout's options error is the layout's: it fails the activation that arranged, or is reported through `lunette.reportError` when the arrangement ran from a listener.

A placement owns each implicit tag it creates. Cleanup at the end of the placement's lifetime removes the memberships it added, its panel, and its newly created tags. Existing tags are borrowed and survive cleanup. Borrowing a newly created tag does not extend the creator's lifetime; tags are not reference-counted, and creator cleanup still removes them.

A persistence state retains its loaded arrangement, the slot each live window holds, and any refusal to overwrite a broken or newer-format file while `desktop/persistence` is disabled and re-enabled. A binding belongs to one activation. Its rules source and arrival listener read the arrangement last loaded or saved, so a save reaches the windows and monitors that appear after it. Resolving a window is a query: a window answers the slot it holds, or the lowest slot no live window of its application holds, and only the creation of its panel takes the slot. A window holds its slot until it dies, so a window that closes and reopens takes the slot it left. A monitor panel that appears after the binding, through hotplug or a reload of the mirroring consumer, is restored as it appears. Disposing a binding removes the source and listeners and clears references to the old context and services. A normal quit attempts to save. A returned write failure or a thrown save error is reported by the frame provider, and `lovr.quit` returns `false` so the failure does not veto shutdown.

The desktop consumers each require only the contracts they use. `desktop/base` mirrors monitors, updates and draws panels in the `scene` phase, and offers them as the `desktop/panels` surfaces. `desktop/pointing` attaches the lasers, updates them against every offered surface and draws them in the `pointing` phase, so a laser or interaction outage leaves panels updating and drawing. `desktop/keyboard` offers the wrist button and its keyboard as `desktop/keyboard` and draws them in the `scene` phase after the panels; it draws only the keyboard it made, and takes `hand`, `size`, `offset`, `placement`, and `haptic`. `desktop/input` consumes the reload key as a `binding` and forwards other keys and text to the focused client as `delivery`. `desktop/errors` draws the error display in the `overlay` phase. The frame provider runs each handler under its own protected call and reports a handler's error through `lunette.reportError`, so one handler's error does not stop the others, including the error display.

The desktop integration tests cover frames and input with ten production source reloads requested by F5, selective keyboard, error-display, interaction, laser, and tags outages, an interaction outage in the middle of a drag, placement recovery, retained arrangement and write-refusal state across persistence outages, a dropped window staying out of the arrangement when another closes, the layouts broker's registration, application, and change events, the arc spacing wide panels apart, adoption's placement events, `desktop/arrange` reporting a missing layout and arranging when it registers, monitor hotplug and fast replug, windows that close and reopen, substitute panels, rules, and error-display providers, source precedence, raising frame handlers and surface offers, phase order, key and text consumption, frame registrations ending with their owner, duplicate offer names, a frame provider outage, a plugin without configuration drawing and offering a surface in the shipped composition, quit-save return and exception failures, every kind of patch and every malformed one, a provider built, wrapped, and published through a patch, each provider rejecting an option it does not take and serving one it was given, the wrist keyboard drawing only its own keyboard and pulsing the hand that pressed it, the keyboard example in `examples/keyboard` running through its patches, and the layout example in `examples/layout` arranging by its grid, rejecting a misspelt grid option, and following the head with its continuous layout. `crates/lunette/tests/plugin_keyboard/hooks.lua` covers rows with spacers, offsets, and tall keys, action keys and layers, the modifier and lock sets, row validation, and the `onKey` and `drawKey` hooks wrapping their defaults. The tests use the real provider definitions, the installed desktop root, and its composition with fixture callback and native-resource seams. They do not establish an actual XR or GPU-backed boot, host-desktop acceptance, or successful installation and execution of a copied configuration.

Safe mode is compiled into the binary and requires `lunette` alone. It does not depend on `mullion`, the provider roots, or the desktop, because a missing or broken installed module tree must not prevent recovery. [The Lua API](lua-api.md#errors) records its behavior.

## Module lifecycle

The host's source reload retains the Lua state. It shuts down plugin runtimes, clears native subscribers and configuration callbacks, drops unprotected modules from `package.loaded`, advances the plugin contract epoch, and runs `main.lua` and `lovr.load` again.

Plugin implementations register cleanup effects with their context or owner. The native runtime runs these effects during disable, instance reload, disposal, and shutdown. An expired activation cannot use its context or publisher. A cleanup failure quarantines the instance: the runtime does not retry an inverse that already failed, runs the instance's remaining inverses when its attachment ends, and never loads it again. A quarantined instance keeps its contract reservations but does not hold back its providers or parent. Cleanup failures during a drain are reported through `lunette.onError`; a failing `effect:dispose()` raises to its caller.

Plugin effects are the only cleanup mechanism. There is no Lua teardown registry: the one `mullion` had was absorbed into the effect layer, as issue #32 specifies. A library module keeps no module-level state: a persistence state belongs to the caller that creates it, and its bindings are plugin effects. A Lua module outside a plugin that owns native resources releases them through a lifecycle path of its own or tolerates their continued existence; [Known gaps](#known-gaps) records this.

`lua/spec/` holds specifications for the modules whose behaviour a spec reaches directly: `mullion`, the desktop's persistence, the contracts vocabulary, and the keyboard's default rows. Each spec sits at its module's path under `@spec/`, and `lua/spec/tree.lua` lists those modules; the coverage spec requires an entry for each. The providers, the rest of the contracts, and the desktop consumers are covered by the Rust integration tests under `crates/lunette/tests/`. The root is available only in development. The checker includes the ordinary suite modules, while computed spec requires and negative type probes are handled by their dedicated tests. `make check` includes subprocess integration tests that start `lunette` with headless fixtures. It does not run a hardware acceptance session.

## Policy and mechanism

| Concern | Owner | Reason |
|---|---|---|
| Window and monitor handles, sinks, input delivery, outputs, layers, and capture | `lunette` | These operations cross native, compositor, or device boundaries. |
| Panel layout, surface picking, pointer behavior, and frame-rate policy | Lua modules and providers | Configurations can replace policy without changing the native API. |
| Contract identity, exact provider bindings, lifecycle, and resource cleanup | Native plugin runtime | These rules span service providers and must remain consistent within a runtime graph. |
| Service methods and configuration types | Luau contracts and definitions | The checker can validate local source shapes without inferring the complete runtime graph. |

The panels provider adapts native window and monitor pixels to Lua-defined geometry and interaction. A monitor panel remains an in-scene quad because the native layer claim API accepts windows, not monitors. Interaction keeps pointer hover and keyboard focus separate; pointer motion does not implicitly take focus. These boundaries let a configuration change geometry and input policy without changing Wayland protocol behavior.

## Decisions

The standard library stays optional and separate from `lunette`. The native root exposes mechanism, while `mullion` contains replaceable policy and helpers. Keeping distinct roots avoids making a Lua implementation look like native mechanism and lets a configuration omit the library.

Liveness of a service belongs to the facade, not to each provider. Every provider repeated a guard against calls after its activation ended, and a provider that forgot one exposed torn-down state. The facade's service view enforces it once for every provision. Providers keep the checks that guard objects outliving a call, which the view does not reach.

Neutral contracts stay separate from providers. A contract describes a service without importing the module that implements it. This allows plugins to typecheck against the service surface while keeping provider implementations replaceable.

The plugin API uses local capability and configuration types with runtime graph validation. A recursive inferred type for the complete provider graph exceeded Luau's 20,000 subtype-normalization budget even with an empty initializer. Changing compiler flags or limits was rejected. Local static checking remains useful, while declarations and the lifecycle graph validate whole-runtime wiring.

The native adapter contains erased casts. A mapped `Services<R>` and `Provisions<P>` authoring API is not used. `Context:require<T>(capability)` and init-only `Publisher:provide<T>(capability, value)` keep the public typing model direct and place runtime membership checks at the boundary.

### Desktop consumers reach frame and surfaces through contracts

The desktop consumers took the configuration's callback registry through their configuration, so a consumer could not be moved out of the configuration directory or written by a user without copying the registry. They now require `lunette/frame` and `lunette/surfaces` and take no registry through their configuration, and they are the installed `@lunette-desktop` root rather than configuration files. [The Lua API](lua-api.md#frame-dispatch-and-the-surface-list-are-contracts) records the contracts' shape, the phases, and why the LÖVR callbacks are bound by `frame.install` rather than by the provider. `desktop/base` requires the surfaces contract to offer panels, so a surfaces outage stops panel rendering with it; splitting rendering from offering is left to the split of `desktop/base.lua`.

### Superseded `mullion` modules are removed

The panel, interaction, laser, keyboard, tag, rules, adoption, error, and arc-layout modules of `mullion`, with the signal and teardown modules they were built on, were removed once the built-in providers replaced them. Issue #32 makes the existing standard library the first plugins and absorbs the teardown registry into the effect layer; the providers did both, and the shipped configuration and safe mode used none of the old modules. Keeping them as optional alternatives was rejected. Each was a second implementation of a provider's behaviour with a lifecycle the host no longer runs: their cleanup depended on a teardown registry that source reload and hard restart do not call, so a configuration that used them leaked across every reload, and fixes to a provider would not have reached its legacy twin. The modules that remained were helpers a provider or the persistence binding used, `mullion.pose`, `mullion.keycodes`, and `mullion.persist`, and the scale and pacing choosers, which no provider replaces; [a later decision](#shared-vocabulary-lives-with-what-it-describes-and-nothing-shipped-requires-mullion) moved the helpers out. Their history is in the repository.

### Panel lifecycle is announced through the panels contract

Rules ended a placement when its panel died by importing the panels provider's private events module, and a module-global registry there held one cleanup per panel. A replacement panels provider implementing the contract could not end rules placements, and the registry outlived activations. The contract now carries owner-scoped `onAdded` and `onRemoved` listeners, and every consumer that follows a panel's life uses them. A per-panel destroy hook was considered; owner-scoped listeners were chosen because they are effects of their owner, so a listener ends with the plugin that registered it.

A panel is released before its owner's effect is disposed, rather than by that effect's inverse. The runtime withholds an owner's authority while one of its inverses runs, so a removal announced from inside the inverse would reach the owner's own listeners, such as rules ending its placement, as if the owner were gone.

### Consumer resources are released on the consumer's owner

Pointers, lasers, keyboards, and focus grants registered their native release as an effect of the provider's context, inside an effect on the consumer's owner. A release that failed then quarantined the provider for every consumer. The release is now the inverse on the owner, and a direct `destroy` performs it on its caller's stack. The interaction and laser providers' own teardown still releases anything left, which happens only if an owner never unloaded.

### Focus and tag changes belong to the owner that made them

A pointer's keyboard focus outlived the pointer, `setFocus` changed only the Lua answer and not the native seat, and any consumer could change another's tag selection and memberships with no inverse. Focus is now held, and a holder that ends withdraws it natively. Tag memberships are held per owner. A tag's selection is a stack of per-owner overrides in which the most recent live override wins. Reverting an owner's change to the value from before it was rejected: the revert depends on the order owners unload in, and it can restore a value that belonged to an owner that has already gone.

### One registration per name and one laser owner per hand

Registering a rules source under an existing name replaced the registration, ending a resource another owner still held, and `attach` answered another owner's laser for a hand. Both now raise. A consumer that needs a shared resource borrows it from the provider that brokers it rather than taking another owner's.

### Saved slots are held by windows

The persistence source took a slot on every resolve and never freed one, so `rules:resolve` consumed slots, a window that closed and reopened lost its placement, and the source read the arrangement as it was when the binding was made. A slot is now held from the creation of the window's panel until the window dies, resolving is a query, and the source reads the arrangement last saved. Freeing a slot when the panel is removed was rejected: a provider outage removes every panel while the windows remain, and recovery would then give windows each other's slots.

### The arrangement is saved on a drop and at quit

The documentation said the policy saved on panel removal; it saved on a grab's drop and at quit, and that is kept. A panel is removed mostly by outages, reloads, and unloads, when the binding is ending and a save would capture a desktop that is coming apart. A drop is the moment a user has finished arranging a panel.

A grab that the interaction provider's own teardown ends stores the pose property without emitting the drop, because the provider can no longer emit through the panels contract. The native property is never older than the saved arrangement as a result, and it takes precedence over the arrangement, so the newer pose wins. A grab ended while the provider is live, including by the pointer's owner unloading during an interaction outage, emits the drop and stores the pose, and the saved arrangement and the property agree.

### The desktop is an installed root, changed by patches

The desktop's consumers were files in the shipped configuration directory, required by relative path, and the composition was a hard-coded sequence in `main.lua`. A user configuration could not reuse a consumer without copying it, and changing one provider meant copying `main.lua`. The consumers are now the installed `@lunette-desktop` root, and the composition is a list of entries with ids that a configuration changes with patches. The patches are modelled on profile patches: they name what they change by a stable id, and they say whether to remove, replace, configure, or add, rather than restating the list. Unknown ids and conflicting patches raise, because a patch that silently matches nothing is a configuration that does not do what it says. Each id takes one patch, so the outcome never depends on which of two patches applied last. Exposing the instances as a mutable table the configuration edits was rejected: it would have no error for a misspelt id and no point at which the result is known to be complete.

The root is required for installation, like the provider roots, because the shipped configuration requires it and an installation without it cannot run its own default. Safe mode is compiled into the binary and requires none of it.

### Shared vocabulary lives with what it describes, and nothing shipped requires `mullion`

The keyboard provider and the rules provider required `@mullion/keycodes` and `@mullion/pose`, and the desktop policy required `@mullion/persist`, while `@mullion` is an optional root: an installation without it installed a desktop it could not start. The interaction provider carried a second copy of the pose encoding to avoid the dependency, and the `Input` type was declared twice. Each helper moved to where its subject is.

The key names are the native seat and sink API's vocabulary, because that API speaks evdev codes, so `lunette.keyCodes()` answers them. The table is read from `lunette-capture`'s `VirtualKey`, the closed set the host sinks already emit, so a named key reaches either kind of sink and the names cannot drift from what the runtime sends. `lunette.lockingModifierNames()` answers the modifiers a keymap locks, read from `KeyModifier`, beside `lunette.modifierNames()`. The Luau type of the table is keyed by a `KeyName` union, so a misspelt key is a type error. Generating the table from `linux/input-event-codes.h` was not possible without a new dependency or a copy of the header, and no crate in the tree carries its constants; the codes are instead checked against xkeyboard-config's evdev table through libxkbcommon, which the compositor already links. A hand-written table in `@lunette-contracts` was rejected because it would restate what the runtime knows and go stale when the set changes, as `MODIFIER_ORDER` already recorded for the modifier names.

Which key latches which modifier on an on-screen keyboard, and how LÖVR's desktop key names map to codes, are policy several consumers agree on rather than native facts, so they are `@lunette-contracts/keys`, written in terms of the native names. The default rows are the keyboard provider's `rows` option, because a layout is the keyboard's configuration. Pose encoding is `@lunette-contracts/vocabulary`'s, next to the property it encodes, and it is the one encoding the property store, rule sources, and the arrangement file share. The pose property is `lunette.pose`; it named `mullion`, which no longer encodes it. Persistence is `@lunette-desktop/persist`, because it is desktop policy and `desktop/persistence` is its only user, so the desktop's composition is where a replacement for it is chosen.

What remains of `mullion` is the root module and the scale and pacing choosers. The root is kept: removing it would remove an optional library that a configuration may still use, and both choosers are policy over the native API in the sense `mullion` exists for. Nothing shipped loads it.

### Configuration merges records and replaces everything else

A configuration is merged over the provider's defaults, and a patch's configuration over the entry's. A record merges key by key at every depth, so `{ style = { color = ... } }` changes one colour and leaves the rest of the style. Any other value replaces the default, including a list: a colour or a centre is one value, and merging `{ 1 }` into `{ 0.5, 0.5, 1, 1 }` by position would yield a colour nobody wrote. An empty table is replaced, since nothing distinguishes an empty record from an empty list. A shallow merge was rejected because it makes changing one colour restate the whole style. Validation reads the shape from the defaults, so a provider states its options once: an option the defaults do not name is unknown, and a value of another type than its default is wrong. Every option therefore has a default; one that is absent by default needs a value that stands for absence.

### Provider modules share one shape

Built-in providers exported a bare definition, a `{ definition }` table, or a definition and an `install`, and their builders were module-local or published as they built. Every provider module now answers `{ definition, define, build, requires }`, made by `plugin.provider`. `define` makes a variant without copying the module, and `build` lets a plugin wrap a built service and publish the wrapper. Wrapping changes only the outer surface: a built-in calls its own methods through closures, not through `self`, so a wrapper that replaces one method does not change what the others do. Variation inside a provider is left to hooks; [Provider modules](lua-api.md#provider-modules) records the convention they will follow.

### Placement is six composition entries

`desktop/policy` bundled the workspace tag, the rule list, the persistence binding and quit save, adoption, the arc arrangement of unplaced windows, and the demonstration terminal, and required the arc layout by name. Replacing the layout, the rules, or persistence meant copying the whole file. Section 6.5 of the Cordis paper describes the alternative: a concern that joins several services is an integration component of its own, so each can be replaced, configured, or disabled without touching the others. Each of the six concerns is now an entry, and the granularity follows what a configuration changes independently: the rule list, the layout and its options, the workspace's name, and the terminal list are each one entry's configuration, and disabling one leaves the others working. Finer splits were not made where nothing changes separately: install and start of adoption stay together because a start without the native pose source loses hand-placed poses across reloads.

The entries communicate through contracts rather than shared locals. `desktop/arrange` learns of placements from the adoption contract's `placed()` and `onPlaced`, which carry the resolved properties, rather than from the start caller's own callback, which only the consumer that started adoption receives. Listening to `panels:onAdded` was rejected: it reaches every panel, from any plugin, without the properties that say whether a rule or saved state already placed it. The two entries that keep state across their own outages, persistence and arrangement, are factories, as the policy was.

A panel the user dropped returned to the arc whenever another window closed, because the policy re-applied the arc to every panel it had once found unplaced. `desktop/arrange` now removes a panel from its set when the panel is dropped, so a manual placement stays manual. Re-arranging on a drop was not added: the remaining windows moving as the user lets go of one would undo the arrangement the user is making. The arrangement now also re-applies when a panel is removed rather than when the native window closes, because the window's panel is removed only on the next update, and an arrangement made at the close included the closing window.

The rules service iterated a rule list with `ipairs`, so a rule under a key outside the list's positions, or a rule field other than `match` and `properties`, was dropped without a word; `desktop/rules` takes the list as configuration, where a list replaced by a record is an easy mistake. `rules:setRules` and `rules:fromList` now reject both, naming the key.

## Known gaps

A panel adopted and dragged while `desktop/arrange` is unloaded is not known to have been dropped, so the arrangement that follows the consumer's recovery moves it.

Entries that do not depend on one another are enabled, and reloaded after an outage, in list order, and the placement consumers rely on it: `desktop/workspace` creates its tag before adoption places windows into it, and a tag of that name created first by a placement belongs to the rules provider, so the workspace consumer then fails to activate. An inserted entry cannot be placed before a shipped one.

Source reload runs no cleanup for Lua code outside the plugin runtime. A non-plugin module that retains native resources keeps them after the reload unless another owner releases them.

The desktop integration tests do not establish an actual XR or GPU-backed boot, host-desktop acceptance, or successful installed-session execution.

## Deliberately left open

A 2D widget toolkit remains deferred. Larger settings and desktop interfaces fit better in Wayland clients than in a Lua widget framework. Further layout algorithms also remain open: the arc is the only shipped layout, and `examples/layout` holds a grid and a follow-me layout as examples rather than as shipped plugins. Choosing a layout per tag waits on a tag's `layout` becoming a name the layouts broker resolves.

Deferred follow-up issues include #15, #36, #38, and #39. Their feature scope remains in the issue records. XR hardware and host-desktop acceptance remain human gates, and new desktop features remain outside this specification until their implementation and acceptance criteria are defined.
