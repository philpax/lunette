# Standard library

The Lua standard library is installed below `$PREFIX/share/lunette/lua/`. `@lunette-plugin`, `@lunette-contracts`, and `@lunette-plugins` provide the typed plugin facade, neutral service contracts, and built-in plugin implementations. Every policy the library ships is a provider or a consumer, written against the public `lunette` API, and a configuration replaces or omits it as it does any plugin. `@lunette-desktop` holds the desktop's consumers and the entry list that composes them with those providers, which the shipped configuration runs. Their lifecycle and type boundary are specified in [The Lua API](lua-api.md#plugin-authoring) and [Architecture](architecture.md#plugin-runtime).

## Module roots

The source tree is `lua/`. A running session mounts the file-backed roots through LÖVR's virtual filesystem, and the checker resolves aliases from generated `.luaurc` files. [Build and development](build-and-development.md#module-roots) lists each root's alias, source directory, runtime resolution, and installation, and names the source of truth.

A relative require follows Luau's require-by-string rules in the checker and in a session alike. A module's path is its file's path without `.lua` or `.luau`, and a directory's `init.luau` is the module the directory names. `./` and `../` start from the directory that holds the requiring module, and `@self` from the module itself, so in `keyboard/init.luau`, which is the module `keyboard`, `./draw` is a sibling of the directory and `@self/draw` is inside it. LÖVR's loader takes a name as a path from the root of the virtual filesystem, so the session wraps `require` (`crates/lunette/src/require`) to resolve a relative path against the requiring chunk's file first; the resolved name, such as `nested/b` or `@lunette-plugins/keyboard/draw`, is what the loader finds and what `package.loaded` is keyed by. A relative path cannot leave the root it starts in, the configuration root or a module root, cannot name the root itself, and cannot hold a `.` in a component, which the loader reads as a separator; each raises at the requiring line. A chunk with no file, such as one `lunctl eval` sends, resolves as a module at the configuration root would, and has no `@self`. `pcall(require, './x')` resolves against the chunk that called `pcall`.

A configuration can use `lunette` without loading the built-in providers or the desktop.

Panels, drops, focus, key bindings, interaction, lasers, the virtual keyboard, tags, rules, placement, adoption, layouts, the error stream, frame pacing, and output scale are built-in providers, and the arc layout is a built-in plugin that registers with the layouts broker, all under `@lunette-plugins`. [Decisions](#decisions) records why no optional root of helpers sits beside them. Pose encoding and the key vocabulary are contracts vocabulary, the default key rows belong to the keyboard provider, and arrangement persistence belongs to the desktop. The modules that are neither plugins nor contracts are these:

| Module | Responsibility |
|---|---|
| `@lunette-contracts/vocabulary` | The surface and pointer types shared by several contracts, the per-window pose property, `encodePose` and `decodePose`, the one encoding of a pose as the property store's sixteen numbers, and `PRECEDENCE`, the named precedences of the desktop's rules sources. |
| `@lunette-contracts/keys` | The key vocabulary: `CODES` from `lunette.keyCodes()`, `LOCKS` from `lunette.lockingModifierNames()`, `MODIFIER_ORDER` from `lunette.modifierNames()`, which key latches which modifier, the translation from LÖVR's desktop key names, and `heldModifiers`, the modifiers LÖVR reports held, which the bindings provider and `desktop/input` both read. |
| `@lunette-desktop/persist`, with `arrangement`, `slots`, and `format` | Arrangement state `desktop/persistence` owns, capture and restore, the saved slot each live window holds and the identity it is keyed on, file loading and saving through a chosen format, and the versioned file representation with the constructors a format of a configuration's own answers its loads with. |

## Contracts and providers

A neutral contract module declares a service shape and exports a capability. The capability pairs a Luau type with an authority-qualified contract name and schema number. Vocabulary that is shared by several contracts belongs in a neutral contract module so service types do not need to import a provider implementation.

A plugin definition declares its name, its required and provided capabilities, and its initializer, whose configuration parameter gives the definition its configuration type. Its context reads required services with `Context:require<T>(capability)`. Its initializer stages provided services with `Publisher:provide<T>(capability, value)`. The native graph validates runtime wiring and publishes all provided values as one provider generation after initialization succeeds. See [Plugin authoring](lua-api.md#plugin-authoring) for the type boundary and runtime checks.

A provider's service methods carry no liveness guard of their own: consumers reach them through the facade's service view, which raises once the provider's activation has ended. Objects a method returns, such as panels, pointers, lasers, keyboards, and tags, outlive the call and check their own state. A provider whose owner-scoped method needs one of its own dependencies registers that work under its own context, inside the effect it places on the caller's owner, rather than forwarding the caller's owner; the adoption provider's `install` registers its rules source this way. A provider subscribes to native events for its own activation through `Context:on`. The adoption provider's `start` subscribes inside the effect it registers on the caller's owner instead, because that subscription belongs to the caller.

A resource a consumer asks a provider for, such as a pointer, a laser and its seat, a keyboard, a focus grant, a tag membership, or a selection override, is released by an inverse registered on the consumer's owner, not on the provider's context. A release that fails while the owner unloads is the owner's failure and quarantines the owner; the provider keeps serving its other consumers. A resource's `destroy` performs the release on its caller's stack and then disposes the owner's effect, whose inverse has nothing left to do, so a failure raises to the caller that asked for it.

Every change a consumer makes to state it does not own is an effect of its owner. A tag `hold` made lasts while any owner holds it; a tag `new` made belongs to that owner. A tag membership is held by the owners that added it and an exclusion by the owners that excluded it, and the panel is a member while a holder remains and no exclusion does; an owner removes only its own hold, and the owner of a tag `new` made removes every hold. A tag's selection and its layout are each decided by the most recent live override, one per owner, and a tag with none has the value it was made with. Keyboard focus is held by the owner of a `lunette/focus` grant, one per owner and seat, and the interaction provider holds one for the pointer that last pressed on each seat; a grant that ends withdraws the seat's focus natively and is no longer answered by `focused`, unless a later grant has taken the seat. A panel's visibility is decided by the most recent live override, one per owner, and a panel with none is shown. A key chord names one binding, and binding a chord that is bound raises. A laser hand has one owner under `attach`, which raises rather than hand one owner another's laser. A rules source name names one registration, and registering a name already registered raises.

The panels contract announces a panel's arrival and removal to owner-scoped listeners, `onAdded` and `onRemoved`. Removal is announced for every cause: the owner destroying the panel or unloading, the source dying, or the provider unloading. Only the owner that created a panel destroys it. Rules ends a placement when its panel is removed, adoption ends an adoption, the desktop's mirror consumer ends a mirror, and persistence restores a monitor panel as it arrives, all through this contract and none through a provider's private module. A listener that raises is reported through `lunette.reportError` and does not fail the operation that added or removed the panel.

LÖVR's frame and input callbacks reach plugins through the `lunette/frame` contract, and the surfaces a pointer picks from are brokered by `lunette/surfaces`; [Frame and surfaces](lua-api.md#frame-and-surfaces) states both. `@lunette-plugins/frame` exports `install`, which binds the LÖVR callbacks to it, and `run`, which binds them to a composition, beside the module shape every provider has. Both providers call each handler and offer through `@lunette-plugins/protected`, which reports an error through `lunette.reportError` and continues; the panels provider calls its listeners the same way.

Constants and helpers that several providers agree on are neutral vocabulary rather than service fields. The per-window pose property is `@lunette-contracts/vocabulary`'s `POSE_PROPERTY`, written by `desktop/pose-memory` and read by the adoption provider with its `encodePose` and `decodePose`; the key names, modifier keys, and locks are `@lunette-contracts/keys`; and ray intersection with a flat quad is `@lunette-contracts/quad`. A name the native API already answers, such as a key's evdev code or the set of modifiers, is read from it rather than restated. A provider's tuning and style are its configuration, merged over its defaults, and each activation receives its own frozen copy, so no consumer can retune another's.

Built-in provider modules exist for adoption, bindings, drops, the error stream, focus, frame dispatch, frame pacing, interaction, keyboard, laser, layouts, output scale, panels, placement, rules, surfaces, and tags. The providers use the typed plugin facade. Each module answers `{ definition, define, build, requires }` and validates its configuration, as [Provider modules](lua-api.md#provider-modules) states. Panels take `style`, `priority`, `height`, `aspect`, `chrome`, and the `shape` hooks; interaction takes `tuning`, `focusOnPress`, and the `drive` and `constrain` hooks; the laser takes `style`, `buttons`, and the `readInput` and `draw` hooks; the rules provider takes its default `precedence` and the adoption provider its install `precedence`, by default `PRECEDENCE.rules` and `PRECEDENCE.native`; placement takes the `panelOptions` hook; the error stream takes `window`, `maxKeys`, `history`, and `clock`; frame pacing takes `tuning` and the `choose` hook; and output scale takes `tuning` and the `ideal` hook, which [Frame pacing and output scale](lua-api.md#frame-pacing-and-output-scale) states. Frame, surfaces, drops, focus, bindings, layouts, and tags take none. Panels, interaction, and the laser still expose their style or tuning as upper-case fields, `STYLE` and `TUNING`; [Pointers and interaction](lua-api.md#pointers-and-interaction), [Lasers](lua-api.md#lasers), [Panels](lua-api.md#panels), and [Bindings](lua-api.md#bindings) state the rest. The keyboard takes `rows`, `layers`, `style`, `modifierKeys`, `locks`, and the `onKey` and `drawKey` hooks, and its service exposes none of them; [Keyboard](lua-api.md#keyboard) states them. The arc layout, `@lunette-plugins/layout/arc`, provides nothing: it registers a layout with the layouts broker, and its module answers `definition`, `define`, and `requires`. It takes `layout`, the name it registers, and `tuning`; [Layouts](lua-api.md#layouts) states them. A pointer carries `vibrate`, which its creator supplies; the laser supplies its hand's controller. Replacing a provider keeps its capability and declared service shape. A replacement implements the existing interface; the contract is not weakened to accommodate it.

## Default configuration

`etc/xdg/lunette/main.luau` is the shipped configuration. It calls `require('@lunette-desktop').run()`. The desktop is a list of entries, `{ id, definition, config }`, or `{ id, factory, config }` for a definition that is made once for each runtime: the built-in providers, the `layout/arc` registration, and the `desktop/` consumers the tables below describe, each under its definition's name. `lua/lunette-desktop/init.luau` is the source of truth for the entries and their order. `entries()` answers the list, frozen, so a configuration can read the ids.

`run { patches = { ... } }` applies patches to the list with `plugin.compose` and runs it with `frame.run`, which [Composition](lua-api.md#composition) states with the patch rules and errors. `run { entries = { ... } }` starts from another list instead of the default. `run` composes before it binds any callback, so a malformed patch fails the configuration's load and safe mode reports it. `compose(options)` answers the patched list without starting it, and `plugin.start(entries)` starts a list.

```lua
require('@lunette-desktop').run {
  patches = {
    { id = 'keyboard', disabled = true },
    { insert = { id = 'my-hud', definition = hud, config = {} } },
  },
}
```

The one order the placement entries rely on is that the rule list and the saved arrangement are sources before adoption resolves the first window, as the next paragraphs state; a source a configuration inserts goes `before = 'desktop/adoption'` for the same reason.

`configure` holds a function for each shipped entry whose definition takes options, keyed by the entry's id and typed with the `Config` its module exports. `configure.laser(config)` answers `{ id = 'laser', config = config }`, so the patch is the plain patch and composes the same way, and the checker reads the options against the laser's option types. A plain patch's `config` stays `{ [string]: any }`. Typing `config` by `id` would make the patch type a union of one arm per shipped entry, and the union would need an arm for any other id as well, because a patch also names entries a configuration inserted; a mistyped option for a shipped entry satisfies that arm, so the union checks nothing a function per entry does not, and adds an arm per entry to every patch the checker reads. An entry whose definition takes no options, such as `frame` or `desktop/render`, has no function, and an inserted entry is configured through its own module's typed `define`. Luau does not report a key a table type does not name in a literal, so a misspelt option still reaches the entry's validation, which raises naming it.

`run` also initialises the global guard `desktop/demo-terminal` reads, so source reload does not spawn another demonstration terminal. Each consumer requires the frame and surfaces contracts it uses, as a plugin in a user's configuration would, and validates its configuration with `plugin.options`, so an option it does not take is rejected by name. `desktop/render`, `desktop/input`, `desktop/pose-memory`, and `desktop/scale` take none.

Placement is seven consumers, each replaceable or configurable by its id:

| Entry | Does | Options |
|---|---|---|
| `desktop/workspace` | Holds the workspace tag and selects it while active. | `name`, default `main`. |
| `desktop/rules` | Registers its rule list with `rules:setRules` under the default source name and precedence. | `rules`, the list; the default sizes and places Firefox. A list replaces the default wholesale. |
| `desktop/pose-memory` | Writes a dropped window's panel pose to the window's `lunette.pose` property, which the adoption provider's native source reads back after a reload. | None. |
| `desktop/persistence` | A definition factory. Each definition makes one persistence state from `@lunette-desktop/persist` at its first activation and keeps it outside its activations, binds it as a rules source at each activation, saves when `lunette/drops` announces a drop and again at normal quit, and provides `lunette/arrangement`, whose `save` and `restore` a binding calls. | `file`, the file in the save directory, default `arrangement.state`; `format`, `{ read, render }`, default `persist.FORMAT`; `keyFor`, the identity a window or monitor is saved under, default `persist.defaultKey`. |
| `desktop/arrange` | A definition factory. Arranges placed windows that were placed without a pose, tag by tag, each with its own layout or the configured one from the layouts broker, and leaves out a window the user dropped. | `layout`, default `arc`; `options`, each layout's options keyed by its name, each replacing that layout's defaults wholesale, default none; `tags`, the tags to arrange, every tag when empty, the default. |
| `desktop/adoption` | Installs the adoption provider's native pose source and starts adoption. | `tags`, the tags an adopted window joins unless a rule names others, default `{ 'main' }`; `filter`, which answers whether to adopt a window, default every window. |
| `desktop/demo-terminal` | Spawns the first terminal emulator of its list that starts, once per Lua state, when the first start finds no window open. | `programs`, tried in order; an empty list opens nothing. |

The rule list and the saved arrangement are sources before adoption resolves the first window, which is why they come before it in the list. The workspace tag needs no place in the list: a placement that names it, the saved arrangement restoring a panel into it, and `desktop/workspace` all hold it, so whichever comes first makes it and it lasts while any holds it. The rule sources apply in ascending precedence, which `@lunette-contracts/vocabulary`'s `PRECEDENCE` names: configured rules at `rules`, 100, saved arrangement state at `persisted`, 200, and native per-window properties at `native`, 300. A higher-precedence source overrides a lower-precedence value for the same property. Saved state supplies pose, size, and tags; the native source supplies hand-placed pose.

`desktop/arrange` reads what to arrange from the placement contract's `placed()` each time it arranges, and arranges when it activates, when placement announces a placement through `onPlaced`, when any panel is removed, when a layout registers or unregisters, and when a tag is made, ends, changes its selection, changes its layout, or changes its members. The candidates are every live placement made without a pose, in placement order, less every panel dropped while the consumer was active and every window with a kept pose, the `lunette.pose` property `desktop/pose-memory` writes on a drop, so a window dropped while the consumer was unloaded stays where it was dropped. The dropped panels are kept in the factory's state, weakly, so an outage of the consumer does not return them to the set either. The tags are those `tags` names, or every tag, and the selected ones come first, then the rest, each group in the tags service's order. Each tag poses the candidates that are its members and that no earlier tag posed, with its own layout when it names one and otherwise with `layout`, so a window in several tags is arranged by the first selected tag that holds it, or by the first tag that holds it when none of its tags is selected. A layout is applied with `options[name]`, its own entry, whichever tag uses it, or with none. A layout registered as `continuous` and in use is also applied on every frame update, in the `scene` phase before the panels update. `desktop/arrange` logs a warning, once for each name, on the first frame that finds a layout it would use not registered, naming those that are; it arranges as soon as one registers. A layout's options error is the layout's: it fails the activation that arranged, or is reported through `lunette.reportError` when the arrangement ran from a listener.

A placement holds each tag it names by a string, making it when no tag has that name. Cleanup at the end of the placement's lifetime removes the memberships it added, its panel, its hiding, and its holds, so a tag it made ends with the last placement or other owner holding it. A tag given as a tag is joined as it is.

A persistence state reads its file through its format, by default the versioned Lua table `persist/format` writes. A format of a configuration's own answers its loads with `persist.arrangement`, `persist.fromTheFuture`, `persist.broken`, or `persist.empty`, and keeps the version rules `persist/format` states: a reader answers `fromTheFuture` for a version it cannot write back whole, so the file is refused rather than written over, and a version is bumped when a field is added. A reader that raises or answers something other than a load makes the file broken, and a render that answers something other than text fails the save. `keyFor` answers the identity a window or monitor is saved and restored under; the default is a window's application id and a monitor's id, and a configuration that keeps terminals apart by title answers a window's title. A persistence state retains its loaded arrangement, the slot each live window holds, and any refusal to overwrite a broken or newer-format file while `desktop/persistence` is disabled and re-enabled. A binding belongs to one activation. Its rules source and arrival listener read the arrangement last loaded or saved, so a save reaches the windows and monitors that appear after it. A saved entry that no live panel matches is reported once for the arrangement it belongs to, at the first binding or `restore` that finds it unmatched, and not again by later restores or bindings of the same arrangement. Resolving a window is a query: a window answers the slot it holds, or the lowest slot no live window of its application holds, and only the creation of its panel takes the slot. A window holds its slot until it dies, so a window that closes and reopens takes the slot it left. A monitor panel that appears after the binding, through hotplug or a reload of the mirroring consumer, is restored as it appears. The source and listener are effects of the context the binding was made with, so they end with that activation, and a bind that fails during an initializer is rolled back with the failed load. A binding has no disposal of its own: one kept past its activation answers nothing, refuses to save, and holds no reference to that activation's context or services. A normal quit attempts to save. A returned write failure or a thrown save error is reported by the frame provider, and `lovr.quit` returns `false` so the failure does not veto shutdown.

The desktop consumers each require only the contracts they use:

| Entry | Does | Options |
|---|---|---|
| `desktop/render` | Updates and draws panels in the `scene` phase. A child plugin offers the shown panels as the `desktop/panels` surfaces, so a surfaces outage stops pointing at panels and leaves them drawing. | None. |
| `desktop/hint` | Draws a line of text while no panel exists. | `text`, `position`, `size`. |
| `desktop/decorations` | Draws a border and a title bar for every shown panel without chrome of its own, and offers the bars as `desktop/decorations` surfaces; dragging a bar moves its panel. | `style`: bar height and colours, margin, border thickness, depth, and colours, title height and colour. |
| `desktop/pointing` | Attaches the lasers, updates them against every offered surface and draws them in the `pointing` phase, so a laser or interaction outage leaves panels updating and drawing. | `laser`, the options both lasers are attached with: `name`, `tuning`, `style`, `readInput`. |
| `desktop/input` | Forwards the keys and text no binding consumed to the client `lunette/focus` answers, in the `delivery` phase. It does not require bindings, so a bindings outage leaves typing working. | None. |
| `desktop/bindings` | Binds the reload chord. | `reload`, `{ key, modifiers }`, default F5. |
| `desktop/keyboard` | Offers the wrist button and its keyboard as `desktop/keyboard` and draws them in the `scene` phase after the panels; it draws only the keyboard it made. | `hand`, `size`, `offset`, `placement`, `haptic`. |
| `desktop/errors` | Presents the latest report of the `lunette/errors` stream, or of its history when it activates, on a quad in the `overlay` phase, and nothing once the stream is cleared. | `position`, three numbers; `width`; `textHeight`; `columns` and `lines`, how much text it wraps to and shows; `background`, a colour. |
| `desktop/monitors` | Mirrors the selected monitors side by side, each as a monitor panel, now and as they are plugged in; a child plugin adds the mirrors to tags, and to a tag made later as the tags contract announces it. | `select`, monitor names, every monitor when empty; `placement`, the row's `center`, each mirror's `width`, and the `gap` between them; `tags`. |
| `desktop/pacing` | Paces each window panel's window with `window:setFrameRate` by the rate its `lunette/pacing` pacer answers, in the `overlay` phase, and pauses a hidden monitor panel's capture. | `pauseMonitors`, default true. |
| `desktop/scale` | Sets each output's scale with `output:setMode` by the step its `lunette/scale` chooser answers for the nearest shown window panel on it, in the `overlay` phase. | None. |

`desktop/pacing` observes, for every window panel, whether it is hidden, its window's `contentType`, and whether its window's `commit` changed since the previous frame, and passes them to a pacer kept for the window. Whether the client drew is observed only while the window is unthrottled, because a throttled client's commits describe the throttle; the pacer's exemption is then decided by the history from before the throttle and the hint. With the default tuning a hidden panel's window is paced at 1 Hz, a hidden video, game, or busy window at 30 Hz, and a shown panel's window is unthrottled. A window without a panel is not paced, and a window whose panel is removed is returned to unthrottled. A monitor panel is not a window and has no frame rate; while `pauseMonitors` is true a hidden one's capture is paused with `monitor:setPaused` and resumed when it is shown or removed.

`desktop/scale` measures the distance from the head, `lovr.headset.getPosition 'head'`, to the centre of every shown window panel, takes the nearest for each `window.output`, and sets the output's scale when its chooser's step differs from the scale last set. An output shared by several windows takes the scale its nearest shown panel wants, so the nearest is sharp and the others render more pixels than they need. An output with no shown window panel keeps its scale, a monitor panel gives no distance because a monitor's scale is its host's, and nothing is done while the headset reports no head.

Unloading either entry undoes what it did. `desktop/pacing` returns every window it throttled to unthrottled and resumes every capture it paused. `desktop/scale` sets every output it changed back to the scale it had before the first change, unless the output's scale is no longer the one it set, which means another plugin has set it since. A source reload therefore returns each output to its original scale and raises it again on the next frame.

`@lunette-desktop/workspaces` is shipped and is not one of the entries; a configuration adds it with `{ insert = { id = 'desktop/workspaces', definition = require '@lunette-desktop/workspaces' } }`. It holds one tag for each workspace and selects one, the first already selected or the first in the list. A panel that is a member of a workspace's tag and of no selected one is hidden by its visibility override, which the consumer withdraws rather than overrides to show the panel, so a panel another plugin hid stays hidden; a panel in no workspace's tag is left alone. Its options are `workspaces`, a list of `{ name, key }`, default `main`, `two`, `three`, and `four` on the keys 1 to 4; `modifiers`, held with each key, default `{ 'logo' }`; and `follow`, default true, which moves a window placed into workspaces none of which is shown into the one that is, by excluding it from the others. The chords are a child plugin, so a bindings outage leaves the workspaces as they are.

The frame provider runs each handler under its own protected call and reports a handler's error through `lunette.reportError`, so one handler's error does not stop the others, including the error panel's.

## Module lifecycle

The host's source reload retains the Lua state. It shuts down plugin runtimes, which advances the plugin contract epoch, clears native subscribers and configuration callbacks, drops unprotected modules from `package.loaded`, and runs `main.luau` and `lovr.load` again.

Plugin implementations register cleanup effects with their context or owner. The native runtime runs these effects during disable, instance reload, disposal, and shutdown. An expired activation cannot use its context or publisher. [Architecture](architecture.md#plugin-runtime) states how a cleanup failure quarantines an instance and how the failure is reported.

Plugin effects are the only cleanup mechanism. There is no Lua teardown registry; issue #32 places that role in the effect layer. A library module keeps no module-level state: a persistence state belongs to the caller that creates it, and its bindings are plugin effects. A Lua module outside a plugin that owns native resources releases them through a lifecycle path of its own or tolerates their continued existence; [Known gaps](#known-gaps) records this.

`lua/spec/` holds specifications for the modules whose behaviour a spec reaches directly: the desktop's persistence, the contracts vocabulary, the keyboard's default rows, the interaction provider's picking arithmetic, the panels provider's curved geometry, the pacing provider's pacer, and the scale provider's chooser. Each spec sits at its module's path under `@spec/`, and the runner collects every `*_spec.luau` file there. The shipped modules running again after a source reload is covered by the desktop integration tests' production source reloads and by `crates/lunette/tests/reload.rs`. The providers, the rest of the contracts, and the desktop consumers are covered by the Rust integration tests under `crates/lunette/tests/`. The root is available only in development. The checker includes the ordinary suite modules, while computed spec requires and negative type probes are handled by their dedicated tests. `make check` includes subprocess integration tests that start `lunette` with headless fixtures. It does not run a hardware acceptance session.

## Policy and mechanism

| Concern | Owner | Reason |
|---|---|---|
| Window and monitor handles, sinks, input delivery, outputs, layers, and capture | `lunette` | These operations cross native, compositor, or device boundaries. |
| Panel layout, surface picking, pointer behavior, and frame-rate policy | Lua modules and providers | Configurations can replace policy without changing the native API. |
| Contract identity, exact provider bindings, lifecycle, and resource cleanup | Native plugin runtime | These rules span service providers and must remain consistent within a runtime graph. |
| Service methods and configuration types | Luau contracts and definitions | The checker can validate local source shapes without inferring the complete runtime graph. |

The panels provider adapts native window and monitor pixels to Lua-defined geometry and interaction. A monitor panel remains an in-scene quad because the native layer claim API accepts windows, not monitors. Interaction keeps pointer hover and keyboard focus separate; pointer motion does not implicitly take focus. These boundaries let a configuration change geometry and input policy without changing Wayland protocol behavior.

## Decisions

The Lua roots stay separate from `lunette`. The native root exposes mechanism, while the providers and consumers hold replaceable policy. Keeping distinct roots avoids making a Lua implementation look like native mechanism and lets a configuration replace or omit any provider.

Liveness of a service belongs to the facade, not to each provider. A guard in every provider against calls after its activation ends is repeated code, and a provider that omits one exposes torn-down state. The facade's service view enforces liveness once for every provision. Providers keep the checks that guard objects outliving a call, which the view does not reach.

Neutral contracts stay separate from providers. A contract describes a service without importing the module that implements it. This allows plugins to typecheck against the service surface while keeping provider implementations replaceable.

The plugin API uses local capability and configuration types with runtime graph validation. A recursive inferred type for the complete provider graph exceeds Luau's 20,000 subtype-normalization budget even with an empty initializer. Changing compiler flags or limits was rejected. Local static checking remains useful, while declarations and the lifecycle graph validate whole-runtime wiring.

The native adapter contains erased casts. A mapped `Services<R>` and `Provisions<P>` authoring API is not used. `Context:require<T>(capability)` and init-only `Publisher:provide<T>(capability, value)` keep the public typing model direct and place runtime membership checks at the boundary.

### Desktop consumers reach frame and surfaces through contracts

The desktop consumers require `lunette/frame` and `lunette/surfaces` and take no callback registry through their configuration, and they are the installed `@lunette-desktop` root rather than configuration files. A registry passed through configuration would tie a consumer to the configuration directory: it could not be moved out of it or written by a user without copying the registry. [The Lua API](lua-api.md#frame-dispatch-and-the-surface-list-are-contracts) records the contracts' shape, the phases, and why the LÖVR callbacks are bound by `frame.install` rather than by the provider. Offering panels as surfaces is a child plugin of `desktop/render`, so a surfaces outage stops pointing at panels and leaves them drawing.

### Panel lifecycle is announced through the panels contract

The panels contract carries owner-scoped `onAdded` and `onRemoved` listeners, and every consumer that follows a panel's life uses them. A consumer that imports the panels provider's private modules cannot work with a replacement provider that implements only the contract, and a module-global registry of per-panel cleanups outlives activations. A per-panel destroy hook was rejected: owner-scoped listeners are effects of their owner, so a listener ends with the plugin that registered it.

A panel is released before its owner's effect is disposed, rather than by that effect's inverse. The runtime withholds an owner's authority while one of its inverses runs, so a removal announced from inside the inverse would reach the owner's own listeners, such as rules ending its placement, as if the owner were gone.

### Consumer resources are released on the consumer's owner

Pointers, lasers, keyboards, and focus grants release their native resource through an inverse on the consumer's owner, and a direct `destroy` performs the release on its caller's stack. Registering the release as an effect of the provider's context was rejected: a release that failed would quarantine the provider for every consumer. The interaction and laser providers' own teardown releases anything left, which happens only if an owner never unloaded.

### Focus and tag changes belong to the owner that made them

Keyboard focus is held, and a holder that ends withdraws the focus from the native seat as well as from the Lua answer, so focus does not outlive the pointer that took it. Tag memberships are held per owner. A tag's selection is a stack of per-owner overrides in which the most recent live override wins. No consumer changes another's focus, selection, or memberships without an inverse. Reverting an owner's change to the value from before it was rejected: the revert depends on the order owners unload in, and it can restore a value that belonged to an owner that has already gone.

### One registration per name and one laser owner per hand

Registering a rules source under a name already registered raises, and so does `attach` for a hand whose laser another owner holds. Replacing the registration, or answering the existing laser, was rejected: either ends or shares a resource another owner still holds. A consumer that needs a shared resource borrows it from the provider that brokers it.

### Saved slots are held by windows

A slot is held from the creation of the window's panel until the window dies, resolving is a query, and the source reads the arrangement last saved. Taking a slot on every resolve was rejected: `rules:resolve` would consume slots, and a window that closed and reopened would lose its placement. Freeing a slot when the panel is removed was rejected: a provider outage removes every panel while the windows remain, and recovery would then give windows each other's slots.

### The arrangement is saved on a drop and at quit

The arrangement is saved on a grab's drop and at quit. Saving on panel removal was rejected: a panel is removed mostly by outages, reloads, and unloads, when the binding is ending and a save would capture a desktop that is coming apart. A drop is the moment a user has finished arranging a panel.

A drop is announced through `lunette/drops`, and pose memory and the save both hear it, so the saved arrangement and the native property agree. A grab ended while the interaction provider is live, including by the pointer's owner unloading during an interaction outage, emits the drop. A grab the provider's own teardown ends emits nothing, because the provider's context can no longer act as an owner; that happens only to a pointer whose owner never unloaded, and the pose is then neither remembered nor saved until quit.

### A persistence binding ends with its activation

A persistence binding has no disposal of its own. Its rules source and arrival listener are effects of the context it was bound with, so they end with that activation, and a bind that fails during an initializer is rolled back with the failed load. A `dispose` method was rejected: with the effects owned by the context, it could only stop the binding answering while its source still held the source name, so a second bind in the same activation would fail.

### The desktop is an installed root, changed by patches

The desktop's consumers are the installed `@lunette-desktop` root, and the composition is a list of entries with ids that a configuration changes with patches. Consumers kept in the configuration directory, composed by a fixed sequence in `main.luau`, were rejected: a user configuration could not reuse a consumer without copying it, and changing one provider would mean copying `main.luau`. The patches are modelled on profile patches: they name what they change by a stable id, and they say whether to remove, replace, configure, or add, rather than restating the list. Unknown ids and conflicting patches raise, because a patch that silently matches nothing is a configuration that does not do what it says. Each id takes one patch, so the outcome never depends on which of two patches applied last. Exposing the instances as a mutable table the configuration edits was rejected: it would have no error for a misspelt id and no point at which the result is known to be complete.

The root is required for installation, like the provider roots, because the shipped configuration requires it and an installation without it cannot run its own default. Safe mode is compiled into the binary and requires none of it.

### Shared vocabulary lives with what it describes

Each shared helper lives where its subject is. A helper kept in an optional root would make a shipped provider depend on a root an installation may lack, and a copy kept to avoid that dependency would drift from the original.

The key names are the native seat and sink API's vocabulary, because that API speaks evdev codes, so `lunette.keyCodes()` answers them. The table is read from `lunette-capture`'s `VirtualKey`, the closed set the host sinks emit, so a named key reaches either kind of sink and the names cannot drift from what the runtime sends. `lunette.lockingModifierNames()` answers the modifiers a keymap locks, read from `KeyModifier`, beside `lunette.modifierNames()`. The Luau type of the table is keyed by a `KeyName` union, so a misspelt key is a type error. Generating the table from `linux/input-event-codes.h` is not possible without a new dependency or a copy of the header, and no crate in the tree carries its constants; the codes are instead checked against xkeyboard-config's evdev table through libxkbcommon, which the compositor already links. A hand-written table in `@lunette-contracts` was rejected because it would restate what the runtime knows and go stale when the set changes.

Which key latches which modifier on an on-screen keyboard, and how LÖVR's desktop key names map to codes, are policy several consumers agree on rather than native facts, so they are `@lunette-contracts/keys`, written in terms of the native names. The default rows are the keyboard provider's `rows` option, because a layout is the keyboard's configuration. Pose encoding is `@lunette-contracts/vocabulary`'s, next to the property it encodes, and it is the one encoding the property store, rule sources, and the arrangement file share. The pose property is `lunette.pose`, named for the session rather than for the module that encodes it. Persistence is `@lunette-desktop/persist`, because it is desktop policy and `desktop/persistence` is its only user, so the desktop's composition is where a replacement for it is chosen.

### Configuration merges records and replaces everything else

A configuration is merged over the provider's defaults, and a patch's configuration over the entry's. A record merges key by key at every depth, so `{ style = { color = ... } }` changes one colour and leaves the rest of the style. Any other value replaces the default, including a list: a colour or a centre is one value, and merging `{ 1 }` into `{ 0.5, 0.5, 1, 1 }` by position would yield a colour nobody wrote. An empty table is replaced, since nothing distinguishes an empty record from an empty list. A shallow merge was rejected because it makes changing one colour restate the whole style. Validation reads the shape from the defaults, so a provider states its options once: an option the defaults do not name is unknown, and a value of another type than its default is wrong. Every option therefore has a default; one that is absent by default needs a value that stands for absence.

### Provider modules share one shape

Every provider module answers `{ definition, define, build, requires }`, made by `plugin.provider`, so a configuration varies, wraps, or replaces any provider the same way. `define` makes a variant without copying the module, and `build` lets a plugin wrap a built service and publish the wrapper. Exporting a bare definition was rejected: a variant would copy the module, and a plugin could not reach the built service to wrap it. Wrapping changes only the outer surface: a built-in calls its own methods through closures, not through `self`, so a wrapper that replaces one method does not change what the others do. Variation inside a provider is left to hooks; [Provider modules](lua-api.md#provider-modules) records the convention they follow.

### Placement is composition entries

Placement is seven entries: the workspace tag, the rule list, the persistence binding and quit save, adoption, the arrangement of unplaced windows, pose memory, and the demonstration terminal. Section 6.5 of the Cordis paper describes the form: a concern that joins several services is an integration component of its own, so each can be replaced, configured, or disabled without touching the others. One policy entry for all of them was rejected, because replacing the layout, the rules, or persistence would mean copying the whole of it. The granularity follows what a configuration changes independently: the rule list, the layout and its options, the workspace's name, and the terminal list are each one entry's configuration, and disabling one leaves the others working. Finer splits are not made where nothing changes separately: install and start of adoption stay together because a start without the native pose source loses hand-placed poses across reloads.

The entries communicate through contracts rather than shared locals. `desktop/arrange` learns of placements from the placement contract's `placed()` and `onPlaced`, which carry the resolved properties, rather than from the start caller's own callback, which only the consumer that started adoption receives. Listening to `panels:onAdded` was rejected: it reaches every panel, from any plugin, without the properties that say whether a rule or saved state already placed it. The two entries that keep state across their own outages, persistence and arrangement, are factories.

`desktop/arrange` removes a panel from its set when the panel is dropped, so a manual placement stays manual and the panel does not return to the arrangement when another window closes. Re-arranging on a drop was rejected: the remaining windows moving as the user lets go of one would undo the arrangement the user is making. The arrangement re-applies when a panel is removed rather than when the native window closes, because the window's panel is removed only on the next update, and an arrangement made at the close would include the closing window.

`rules:setRules` and `rules:fromList` reject a rule under a key outside the list's positions and a rule field other than `match` and `properties`, naming the key. Iterating with `ipairs` would drop such a rule without a word, and `desktop/rules` takes the list as configuration, where a list replaced by a record is an easy mistake.

### The base consumer is three entries

Rendering, monitor mirroring, and the empty-scene hint are `desktop/render`, `desktop/monitors`, and `desktop/hint`, so a configuration replaces the mirroring or the hint without the rendering. One entry for all three was rejected: it would require surfaces, so a surfaces outage would stop panels drawing. Offering panels is a child of `desktop/render` that requires surfaces, rather than a fourth entry, because it shares rendering's lifetime and has nothing to configure; the child loads with its parent and waits for a surfaces provider without holding the parent back. Mirrors are laid in a row from the centre outward, each taking the lowest free place, rather than re-laid when a monitor comes or goes, because a saved arrangement restores a mirror as it appears and a re-layout would move every restored mirror. Tagging mirrors is a child for the same reason as offering: a tags outage would otherwise take the mirrors away.

### The entries need no order but one

Tags are held, so whichever of the workspace, a placement, or the saved arrangement needs `main` first makes it, and it lasts while any holds it. With an exclusive `new`, the workspace consumer would fail whenever a placement made `main` first. Inserts take `before` and `after` for the dependence that remains, a rules source that must be registered before adoption resolves the first window. Reordering existing entries by patch was not added, because no shipped entry depends on another's position except through that one rule, and moving an entry is better said by disabling it and inserting its replacement.

### A kept pose is a drop the arrangement remembers

`desktop/arrange` leaves out a window whose `lunette.pose` property is set, as well as a panel dropped while it was active. `desktop/pose-memory` writes the property on every drop and adoption reads it back after a reload, so the two agree that the window is the user's to place, and a window dragged during an outage of `desktop/arrange` is not arranged again on its return. Recording drops in the drops broker was rejected: the broker's record would end with its activation, and a drops outage would then lose what the property keeps.

### Workspaces are shipped outside the default entries

Workspaces hide every window not on the shown workspace and take four chords, which is a change in behaviour a configuration should choose rather than find. The consumer is installed in `@lunette-desktop`, checked and tested with the rest, and added with one insert, rather than being an example a user copies and keeps up to date. Its chords are a child, as the monitors' tagging is, so a bindings outage does not show every hidden window.

### Persistence takes its file, format, and identity

The file, the format, and the identity a window is keyed on are `desktop/persistence`'s options, so changing one does not mean replacing the policy. A format is a pair of functions rather than a name of a built-in one, because a format of a configuration's own is the point, and it answers the loads `persist/format` constructs, so the version rules that stop an old writer from corrupting a newer file hold for it too. The state is made at the first activation, because an option is known only then, and made again only if the options change. The consumer provides `lunette/arrangement`, so a key binding saves without reaching into the factory's state.

### A relative require resolves against the requiring file

A session resolves a relative require by Luau's rules, the ones an editor and the checker apply. Resolving it as LÖVR's loader does, against the configuration root, was rejected: the checker and the session would agree only for a module at the top level, and a plugin split across a subdirectory would check clean and fail to load. The resolution is a wrapper around the global `require` rather than a patch to LÖVR's loader, because a loader receives only the name and not the chunk that asked for it. Replacing LÖVR's require with Luau's own require library was rejected: it keys its cache apart from `package.loaded`, which source reload clears, and it resolves aliases through `.luaurc` files a session does not read. The wrapper is Lua and calls the original `require` from Lua, so a module's own error reaches its caller as the loader raised it; only the resolution, which needs the requiring chunk's full name, is native.

### Typed patches are a function per entry

`configure` gives each shipped entry that takes options a function typed with that entry's `Config`, answering the plain patch, so the checker reads the options and composition is unchanged. A plain patch's `config` is `{ [string]: any }`, which passes a mistyped option to fail when the entry loads. A patch type discriminated by `id` was rejected: the union needs an arm for an id it does not know, for entries a configuration inserted, and that arm accepts a mistyped option for any shipped entry too. A helper per patch kind beyond configuration, such as one to disable or replace, was not added: those patches carry nothing an entry's types describe.

### A window in several tags is arranged by its selected tag

`desktop/arrange` takes the selected tags first, so a window in several tags is posed by a layout the user is looking at. A window that belongs to every workspace is laid out with the workspace in view, which is what tiling window managers do for a sticky window, and a selection change arranges again, because which tag owns a window can change with it. Arranging a window once per tag was rejected: the last layout to run would decide its pose.

### Layout options are keyed by layout name

`options` are keyed by layout name, and a layout gets its own entry whichever tag uses it, so a tag that chooses another layout than the configured one still gets that layout's options. Options carried by the tag, `tag:setLayout { layout, options }`, were rejected: a tag is membership and selection that any plugin may read, and parameters for one consumer's layouts are that consumer's configuration. Two tags using one layout with different options is the case this does not cover; a layout registered under a second name with other defaults covers it.

### Pacing and scale are providers

Frame pacing and output scale are the `lunette/pacing` and `lunette/scale` providers, which issue #38 specifies, and the `desktop/pacing` and `desktop/scale` entries read the scene and apply them. The providers hand out a pacer per window and a chooser per output, built from the pure rules in `@lunette-plugins/pacing/pacer` and `@lunette-plugins/scale/chooser`. The split follows what a configuration changes independently: a different rule is a `choose` or `ideal` hook or a provider of the contract, and a different reading of the scene, such as pacing by gaze, is a different consumer that keeps the provider. Neither provider requires anything, because a pacer and a chooser read nothing. The issue suggested that scale require panels and interaction; the consumer measures from the head, which is the headset's, and reads no pointer, so it requires frame, panels, and scale only.

The native API answers the two facts the consumers need: the output a window's client is shown on, `window.output`, and the buffer its pixels came from, `window.commit`, which gives the observed commit rate the pacer needs; [The Lua API](lua-api.md#a-window-names-its-output-and-its-latest-commit) records them. The pacer adds no sample for an observation that does not say whether the client drew, and the consumer observes drawing only while the window is unthrottled. Counting a throttled window's commits would end a video's exemption a second after its panel was hidden, since a client paced at 30 Hz commits on a third of the frames. A visible window is always unthrottled, and the tuning has no rate for a shown window: such a rate would be an option of type number or false, which option validation cannot describe, and a `choose` hook paces a shown window when that is wanted.

Both entries are on by default, a user decision: a hidden panel at full rate and a scale fixed at 1 are costs a user would otherwise find rather than choose, and disabling either is one patch. Unloading reverts what an entry changed, because every change a consumer makes to state it does not own is an effect of its owner. Leaving the rates and scales as they were was rejected: an entry disabled by a patch after a reload would leave outputs at whatever step they last had, with nothing to return them. The cost is that a source reload returns each scaled output to its original scale and raises it again on the next frame, two re-layouts a reload. A scale is restored only when it is still the one the entry set, so a scale another plugin set since is not overwritten.

No optional root of helpers sits beside the providers, consumers, and vocabulary. Helpers live beside what they describe, as [the vocabulary decision](#shared-vocabulary-lives-with-what-it-describes) states, and an optional root would be a fourth place for Lua policy, mounted by every session and read by the checker whether or not anything uses it. Every installed root is required, and the `LUNETTE_STDLIB_PATH` override describes the Lua roots in general.

### Luau sources use the `.luau` extension

Every Lua source in the tree uses the `.luau` extension, because every source is Luau: type annotations, explicit instantiation, and `read` properties appear throughout, and an editor that sees `.lua` highlights and checks them as Lua, which reports them as errors. The shipped and example configurations, the roots, the specs, and the test fixtures are `.luau`, and the shipped configuration's entry point is `main.luau` beside `conf.luau`. Upstream LÖVR's `boot.lua` names only `main.lua`, so the fork resolves `main.luau` first under Luau ([LÖVR integration](lovr-integration.md#mainluau-as-the-entry-point-under-luau)). A user configuration with only a `main.lua` still boots, because the fallback is LÖVR's rather than lunette's, and `lunette check` still reads `.lua` files; the host makes no separate choice about which file is the entry point. Keeping `.lua` and associating it with Luau in each editor was rejected: every contributor and every user would have to configure it, and any tool that infers the language from the extension would still read the files as Lua.

## Known gaps

Source reload runs no cleanup for Lua code outside the plugin runtime. A non-plugin module that retains native resources keeps them after the reload unless another owner releases them.

The desktop integration tests do not establish an actual XR or GPU-backed boot, host-desktop acceptance, or successful installed-session execution.

## Deliberately left open

Pacing reads whether a panel is hidden, not whether it is in the field of view, gazed at, far away, or focused, which [Rendering](rendering.md#frame-pacing) lists among the inputs a policy may use. A panel behind the user is paced as if shown. Pacing by view direction risks a visible stutter as the head turns back, and choosing between the inputs is left until it can be tried on hardware.

A 2D widget toolkit remains deferred. Larger settings and desktop interfaces fit better in Wayland clients than in a Lua widget framework. Further layout algorithms also remain open: the arc is the only shipped layout, and `examples/layout` holds a grid and a follow-me layout as examples rather than as shipped plugins.

Deferred follow-up issues include #15, #36, and #39. Their feature scope remains in the issue records. XR hardware and host-desktop acceptance remain human gates, and new desktop features remain outside this specification until their implementation and acceptance criteria are defined.
