# lunette v1 Design

## Summary

This document plans the first implementation of lunette: a Rust binary that links LÖVR and runs as an OpenXR overlay, hosting Wayland applications as panels and mirroring the host desktop, arranged and driven from Lua. No lunette code exists yet, so the plan starts from an empty repository and ports the Wayland compositor from WayVR rather than writing one from scratch.

The implementation is organised around one binary and four crates split along thread and dependency lines: a crate wrapping LÖVR's C build, a compositor crate that must stay independent of LÖVR and the GPU so it can be tested without either, a capture crate for monitor mirroring, and the binary crate that owns the main loop and Lua integration. The compositor runs on its own thread and communicates with the main thread through commands, events, and a per-frame snapshot, so Lua never blocks on Wayland protocol work and the whole session can be recreated in place for a fast reload. The phased plan front-loads risk: phase 1 gets a reproducible build running LÖVR's own boot sequence, and phase 2 is a vertical slice that proves a spawned client's window can be imported as a GPU texture and clicked, before later phases add composition layers, monitor mirroring, text and clipboard handling, the Lua standard library, and the control socket.

## Definition of Done

- lunette runs as an OpenXR overlay under Monado alongside another application, showing mirrored monitors and spawned Wayland applications as panels realised on composition layers, with in-scene fallback.
- The user can point, click, scroll, type, and copy-paste into both, using per-hand seats; arrange panels through Lua; reload config in-headset without losing running applications; and drive the running instance from `lunctl`.
- The build is reproducible from a Nix devshell, LÖVR is a submodule with an MIT patch set, and logic-headless tests cover the compositor crate.
- Out of scope: dashboard/launcher/notifications furniture, spatial audio, explicit sync, libei, IME, GPU-headless harness, OpenVR, sandboxing.

## Acceptance Criteria

### lunette-v1.AC1: Applications become sources of pixels and input
- **lunette-v1.AC1.1 Success:** A client launched by `lunette.spawn` connects to lunette's socket, and its toplevel appears in `lunette.windows()` on the frame after it maps.
- **lunette-v1.AC1.2 Success:** A committed dmabuf is imported, and `window:getTexture()` returns a texture whose dimensions match the surface.
- **lunette-v1.AC1.3 Success:** A process started outside lunette with `WAYLAND_DISPLAY` pointing at its socket is adopted, reported with `external = true`, and attributed to a process handle.
- **lunette-v1.AC1.4 Failure:** Spawning a non-existent executable reports the failure through an event and creates no window.
- **lunette-v1.AC1.5 Failure:** After a client exits, its handle reports `dead == true`, reads return last-known values, and every method returns `false` without raising.
- **lunette-v1.AC1.6 Edge:** A client using `wl_shm` rather than dmabuf still produces a usable texture.

### lunette-v1.AC2: Panels render, on layers where possible
- **lunette-v1.AC2.1 Success:** A window texture drawn on an in-scene quad appears at the pose Lua specified.
- **lunette-v1.AC2.2 Success:** A granted claim yields a real LÖVR `Layer`, and the panel renders through the runtime's compositor at the surface's native resolution.
- **lunette-v1.AC2.3 Failure:** When the pool is exhausted, the lowest-priority claim is revoked, `lovr.lunlayerrevoked` fires, and the panel continues rendering as an in-scene quad.
- **lunette-v1.AC2.4 Success:** A revoked layer is reused by the next claim of an identical key, with no new allocation. The key is width, height, and the four properties `LayerInfo` fixes at creation; format is not part of it, because there is exactly one.
- **lunette-v1.AC2.5 Success:** Raising a panel's output scale causes the client to re-render at the higher resolution, and the layer samples the new buffer.

### lunette-v1.AC3: The host desktop is visible and controllable
- **lunette-v1.AC3.1 Success:** A mirrored monitor appears as a source with a texture matching the captured output's resolution.
- **lunette-v1.AC3.2 Success:** Pointer coordinates sent to a monitor sink move the host cursor to the corresponding position on that physical display.
- **lunette-v1.AC3.3 Success:** Keystrokes sent to a monitor sink reach whatever the host compositor currently focuses.
- **lunette-v1.AC3.4 Success:** Monitors identify themselves by connector name via the portal's `mapping_id`, without the user selecting screens in a prescribed order, and that identity survives a restart.
- **lunette-v1.AC3.5 Success:** Dismissing a mirrored monitor stops its capture stream; re-adding it restarts capture.

### lunette-v1.AC4: Text and clipboard work, with two hands
- **lunette-v1.AC4.1 Success:** Two seats hover two different windows simultaneously, each with its own pointer position and focus.
- **lunette-v1.AC4.2 Success:** Keycodes with modifier state produce the characters the active xkb layout defines.
- **lunette-v1.AC4.3 Success:** `Sink:typeText` enters text the active layout cannot express, and the client's own keymap handling is restored afterwards.
- **lunette-v1.AC4.4 Success:** A click at a pixel covered by a popup is delivered to the popup's surface in surface-local coordinates, not to the toplevel.
- **lunette-v1.AC4.5 Success:** Text copied on the host pastes into a lunette client and text copied in a lunette client pastes on the host, for both the clipboard and the primary selection.

### lunette-v1.AC5: Arrangement is scripted, and iteration is fast
- **lunette-v1.AC5.1 Success:** A panel created through `mullion` appears at the pose and metre size the configuration specifies.
- **lunette-v1.AC5.2 Success:** A rule matching on `appId` places a newly spawned window without further scripting.
- **lunette-v1.AC5.3 Success:** A saved arrangement is restored after a restart.
- **lunette-v1.AC5.4 Success:** `lunette.reload()` applies an edited layout without disconnecting any client, and teardown hooks run so timers and signal connections do not accumulate.
- **lunette-v1.AC5.5 Success:** `lunette.restart()` rebuilds the Lua state and the XR session while clients stay connected.

### lunette-v1.AC6: It is an overlay, not an application
- **lunette-v1.AC6.1 Success:** lunette runs with `XR_EXTX_overlay` under Monado while another OpenXR application holds the primary session.
- **lunette-v1.AC6.2 Success:** lunette's layers composite over the underlying application rather than replacing its view, and areas Lua did not draw remain transparent.

### lunette-v1.AC7: The overlay stays cheap
- **lunette-v1.AC7.1 Success:** A client stalled inside its own dispatch does not extend lunette's frame time, because compositor work runs off the frame thread.
- **lunette-v1.AC7.2 Success:** A surface undamaged since its last blit is not copied again.
- **lunette-v1.AC7.3 Success:** A panel outside the view is throttled toward the floor, and its client continues to process input rather than appearing hung.
- **lunette-v1.AC7.4 Success:** With only layers drawn and no Lua scene content, the projection layer is skipped.

### lunette-v1.AC8: The session is controllable and survivable
- **lunette-v1.AC8.1 Success:** `lunctl` evaluates a chunk between frames and returns nested tables, with handles serialised as opaque ids.
- **lunette-v1.AC8.2 Failure:** A chunk that exceeds the wall-clock budget is abandoned with an error rather than stalling the frame loop indefinitely; the socket is created mode 0600 and never listens on a network address.
- **lunette-v1.AC8.3 Failure:** An error raised in a user callback is caught, reported through `lovr.lunerror` and an error panel, and the session continues; identical errors repeating each frame are rate-limited.
- **lunette-v1.AC8.4 Failure:** A `main.lua` that fails to load produces safe mode with a laser, a panel, and a reload key, not a black headset.

### lunette-v1.AC9: Cross-cutting
- **lunette-v1.AC9.1 Success:** A clean recursive clone builds with `nix develop` followed by `cargo build`, with no network access during the cmake step.
- **lunette-v1.AC9.2 Success:** `cargo +nightly fmt --all -- --check` and both clippy invocations from `CONTRIBUTING.md` pass.
- **lunette-v1.AC9.3 Success:** Every file ported from WayVR carries a provenance header, `vendor/lovr` patches are MIT, and `CREDITS.md` records provenance.
- **lunette-v1.AC9.4 Success:** The `lunette-compositor` test suite runs without a GPU, an XR runtime, or a headset.

## Glossary

- **ArcSwap**: A Rust crate for publishing and reading a shared value across threads without a lock. lunette uses it to publish the per-frame compositor snapshot.
- **ash**: A Rust binding to the Vulkan graphics API. The compositor thread uses it to import client buffers as GPU images.
- **Claim**: A request from Lua for a panel to be rendered as a composition layer instead of an in-scene quad. The layer pool grants or revokes claims by priority.
- **Composition layer**: An OpenXR mechanism for compositing a separate image directly into the headset's output, bypassing the main 3D scene. A panel rendered this way is sharper than the same panel drawn as an in-scene quad.
- **dmabuf**: A Linux kernel mechanism for sharing a GPU buffer between processes without copying it. Wayland clients hand their rendered window contents to lunette this way.
- **DRM format modifier**: Metadata describing the memory layout of a GPU buffer (tiling, compression), needed to interpret a dmabuf correctly when importing it.
- **Layer pool**: The Rust-owned mechanism that assigns a limited number of OpenXR composition layer swapchains to panels, based on priority claims from Lua.
- **Logic-headless tests**: Tests that exercise compositor logic without a GPU, an XR runtime, or a headset attached, so they can run in ordinary CI.
- **LÖVR**: A Lua game engine providing OpenXR, Vulkan, composition layers, and a Lua scripting environment. lunette links LÖVR as a library and lets it own the main loop.
- **lunctl**: A command-line tool that connects to lunette's control socket and evaluates Lua chunks inside the running session, for inspection and scripting from outside the headset.
- **Monado**: An open-source OpenXR runtime for Linux. lunette targets Monado as its primary runtime.
- **mullion**: lunette's Lua standard library, built on top of the native `lunette` module, providing panels, layout, and interaction as ordinary Lua code.
- **OpenXR**: A cross-vendor standard API for virtual and augmented reality applications and runtimes. lunette is an OpenXR application.
- **Overlay (`XR_EXTX_overlay`)**: An OpenXR extension letting one application composite its output above another application's session rather than replacing it. lunette runs as an overlay so it can sit alongside another VR application.
- **Panel**: A Lua-level object representing a window or mirrored monitor rendered somewhere in space, either as an in-scene quad or as a composition layer.
- **Portal (xdg-desktop-portal)**: A Linux desktop service that mediates access to resources such as screen capture, asking the user for permission on behalf of an application. Monitor mirroring goes through it.
- **Primary selection**: A clipboard-like buffer, separate from the normal clipboard, that holds whatever text was last selected and is pasted with a middle click. It is bridged between host and clients alongside the normal clipboard.
- **Seat**: A Wayland concept grouping one set of input devices, such as a pointer and keyboard. lunette gives each hand its own seat.
- **Sink**: lunette's term for a destination that can receive input, such as a client window or a mirrored monitor.
- **smithay**: A Rust library for building Wayland compositors. lunette's compositor crate is ported from a smithay-based implementation.
- **Snapshot**: An immutable copy of compositor state (windows, monitors, outputs) published once per frame for Lua to read, decoupling Lua from the compositor's own thread.
- **Subsurface / popup**: Wayland concepts for a surface positioned relative to a parent window, such as a dropdown menu, requiring its own coordinate handling separate from the parent.
- **Swapchain**: A set of GPU images that a rendering pipeline cycles through. Here, one swapchain backs one OpenXR composition layer and is recycled by size and format rather than reallocated.
- **Toplevel**: The Wayland term for an application's main window, as distinct from a popup or subsurface.
- **uinput**: A Linux kernel interface for creating virtual input devices from userspace, used to inject input into the host desktop.
- **Vulkan**: The graphics and GPU compute API that LÖVR and lunette both use. LÖVR performs the actual GPU submissions; lunette imports buffers and issues copies into LÖVR's own command stream.
- **Wayland**: A Linux display server protocol. lunette implements the server (compositor) side, so Wayland applications can run inside it as windows.
- **WayVR**: An existing Linux VR project that lunette's compositor and capture code is ported from, with per-file attribution preserved.
- **wl_shm**: A Wayland protocol for sharing pixel buffers through plain shared memory, used as a fallback for clients that do not support dmabuf.
- **xkb**: A library and data format for keyboard layouts, used to translate keycodes into characters.
- **XWayland**: A compatibility layer letting X11 applications run inside a Wayland compositor. lunette spawns a variant of it, `xwayland-satellite`, for this purpose.

## Architecture

lunette is one Rust binary that dynamically links LÖVR and owns `main()`. LÖVR provides OpenXR, Vulkan, composition layers, and the Lua environment. Rust provides the Wayland compositor, capture, input injection, process management, and the control socket.

Four crates:

```
lunette-lovr        build.rs drives cmake; FFI declarations; safe wrappers
lunette-compositor  smithay; ported from WayVR; no LÖVR or GPU dependency beyond image creation
lunette-capture     wlx-capture and HidProvider wrappers
lunette             binary; owns main(), Lua injection, frame orchestration
```

`lunette-compositor` must not depend on `lunette-lovr`. This keeps logic-headless testing available and prevents the graphics module becoming a dependency of window management.

### Boot

Rust replicates what `inspiration/lovr/src/main.c` does, against symbols exported by building with `LOVR_BUILD_SHARED=ON` and `LOVR_BUILD_WITH_SYMBOLS=ON`. It creates the `lua_State`, opens libraries, calls `luax_preload`, installs the `lunette` module through mlua's `init_from_ptr`, sets `arg`, then runs LÖVR's own embedded `boot.lua` and steps the closure it returns.

LÖVR's `boot.lua` runs unmodified, so `lovr.conf`, `lovr.run`, `lovr.errhand`, and the restart cookie behave as LÖVR documents. `lovr.filesystem.setSource` points at `~/.config/lunette`, falling back to `$SYSCONFDIR/xdg/lunette`. The `mullion` standard library mounts read-only from `$PREFIX/share/lunette/lua`, overridable by `LUNETTE_STDLIB_PATH`.

Per-frame work injects around LÖVR's existing loop steps rather than replacing them. Compositor events drain and handles refresh at frame start. Layer blits are issued between `lovr.update` and `lovr.draw`. `lovr.headset.setLayers` is called once at frame end from granted claims.

### Threads

| Thread | Owns |
|---|---|
| Main | Lua state, OpenXR session, GPU submission, rendering |
| Compositor | Wayland display, smithay state, clients, surfaces, seats, child processes |
| Control | The `lunctl` Unix socket |

Startup order is forced by the GPU dependency. LÖVR boots first; graphics initialises; the compositor thread then starts, receiving `VkInstance`, `VkPhysicalDevice`, `VkDevice`, and the queue family from `gpu_vk_get_*`. It creates the socket, exports `WAYLAND_DISPLAY`, and spawns `xwayland-satellite` best-effort. Clients cannot connect before the device exists.

The compositor thread creates images. It never submits queue work. Every copy is issued inside LÖVR's command stream on the main thread, so ordering against LÖVR's rendering is internal to LÖVR.

### Thread protocol

Commands travel down a bounded mpsc channel, events travel up a second channel, and an immutable snapshot is published per compositor tick through `ArcSwap`. No lock is held across a frame.

```rust
enum Command {
    Spawn { argv: Vec<String>, env: Vec<(String, String)>, cwd: Option<PathBuf>, output: OutputId, xwayland: bool },
    CloseWindow(WindowId),
    ConfigureWindow { id: WindowId, size: (u32, u32), states: ToplevelStates },
    Pointer { seat: SeatId, target: SinkId, x: f64, y: f64 },
    Button { seat: SeatId, target: SinkId, button: u32, pressed: bool },
    Scroll { seat: SeatId, target: SinkId, dx: f64, dy: f64 },
    Key { seat: SeatId, keycode: u32, pressed: bool },
    SetModifiers { seat: SeatId, mods: ModifierState },
    TypeText { seat: SeatId, text: String },
    SetFrameRate { surface: SurfaceId, hz: f32 },
    NewOutput(OutputSpec),
    NewSeat(String),
    SetClipboard { seat: SeatId, mime: String, data: Vec<u8> },
}

enum Event {
    WindowOpened(WindowId, WindowInfo),
    WindowClosed(WindowId),
    TitleChanged(WindowId, String),
    SurfaceDamaged(SurfaceId, Rect),
    BufferImported { surface: SurfaceId, image: ImportedImage },
    ClipboardOffer { seat: SeatId, mimes: Vec<String> },
    ProcessExited { pid: u32, code: i32 },
    ProcessOutput { pid: u32, stream: Stream, bytes: Vec<u8> },
}

struct Snapshot {
    generation: u64,
    windows: Vec<WindowSnapshot>,
    monitors: Vec<MonitorSnapshot>,
    outputs: Vec<OutputSnapshot>,
}
```

Lua reads the latest snapshot at frame start. Mutations queued during Lua callbacks flush once at frame end.

### Texture import

Client buffers arrive as dmabufs. The compositor thread imports them with `ash` against LÖVR's device, following the sequence WayVR uses: `vkCreateImage` with `VkExternalMemoryImageCreateInfo` plus `VkImageDrmFormatModifierExplicitCreateInfoEXT` (or the list variant), `vkAllocateMemory` with `VkImportMemoryFdInfoKHR` and a dedicated allocation, then `vkBindImageMemory2`.

Advertised formats come from `vkGetPhysicalDeviceFormatProperties2` with `VkDrmFormatModifierPropertiesListEXT`, filtered to single-plane modifiers. Coverage matches WayVR's `fourcc_to_vk`: `Abgr8888`, `Xbgr8888`, `Argb8888`, `Xrgb8888`, `Abgr2101010`, `Xbgr2101010`. Multi-plane YUV is a known gap. `wl_shm` clients use a memcpy path into a LÖVR-owned texture.

The `VkImage` travels to the main thread over the event channel, which wraps it through `lovrTextureCreate` with `TextureInfo.handle` set. An import cache keyed on the dmabuf means a surface rotates among its buffers rather than allocating. `window:getTexture()` is per-frame and must not be held across frames.

### Layer pool

Rust owns OpenXR layer swapchains and recycles them by `(width, height, format)`. A claim carries a Lua-supplied scalar priority. Rust sorts by that number and assigns the top N deterministically; it does not invent the ranking. Grants and revocations land on frame boundaries, never mid-frame, and a granted claim yields a real LÖVR `Layer` userdata. Blits are skipped for surfaces undamaged since their last blit.

## Existing Patterns

There is no lunette code yet. This is the first implementation work in the repository. The design follows patterns established in three places.

`docs/` is the normative specification and every decision here traces to it: the mechanism-in-Rust and policy-in-Lua split, the snapshot model, inert dead handles, the two API roots, and the prohibition on Rust holding long-lived references into Lua.

`CONTRIBUTING.md` sets the code conventions: Rust 2024, nightly rustfmt with `imports_granularity = "Crate"` and `group_imports = "StdExternalCrate"`, no `unwrap` or `expect` in production code, manual `Display`/`Error` implementations rather than `thiserror`, exact dependency pins in `[workspace.dependencies]`, and the Lua conventions for `mullion`.

WayVR supplies the compositor patterns being ported, with per-file provenance headers. Four of its structures change during the port because they are thread-affine: `Rc<ToplevelSurface>` in `window.rs` becomes `Arc`, `Rc<[_]>` in `hit_test.rs` becomes `Arc<[_]>`, `SyncEventQueue` (which is `Rc<RefCell<VecDeque>>` despite its name) becomes a real channel, and imported images are handed over the event channel rather than stored on the `WlSurface`. That last change is required because smithay's `UserDataMap::insert_if_missing` is thread-affine and returns `None` from another thread with no error, which would make textures vanish silently.

Two patterns are copied from LÖVR itself. `headset.c:45-48` forward-declares the `gpu_vk_get_*` accessors rather than importing a header, and `lunette-lovr` does the same. `gpu_xr_acquire`/`gpu_xr_release` (`gpu_vk.c:2899-2939`) is the model for the imported-image barrier patch.

### Phase 7: Reload, lunctl, and error handling

**Goal:** In-headset iteration without losing running applications, and external control.

**Components:** `lunette.reload` clearing `package.loaded` and re-running `main.lua` with teardown hooks; `lunette.restart` via `lovr.event.restart`; the control thread and a 0600 socket at `$XDG_RUNTIME_DIR/lunette-0.sock` evaluating chunks between frames within a wall-clock budget, serialising nested tables and representing handles as opaque ids; `xpcall` around every user callback with rate-limited repeats; `lovr.lunerror`; built-in safe mode when `main.lua` fails to load.

**Dependencies:** Phase 6.

**Covers:** `lunette-v1.AC5.4`, `AC5.5`, `AC8.1`, `AC8.2`, `AC8.3`, `AC8.4`.

**Done when:** end-to-end shell tests drive `lunctl` to spawn a client, assert state, and tear down; a soft reload applies a layout change without disconnecting clients; an error in a callback shows a panel and the session continues; a syntactically invalid `main.lua` produces safe mode rather than a black headset.

### Phase 8: Outputs, scale, and pacing

**Goal:** Per-panel resolution and frame rate.

**Components:** `lunette.newOutput` with per-client output filtering so each client sees only its assigned outputs; `wp_fractional_scale_v1` with discrete scale steps and hysteresis in Lua; per-surface frame-callback throttling with a 1 Hz floor and video exemption; damage-driven blit skipping extended to layer submission; projection layer skipped when Lua draws nothing.

**Dependencies:** Phases 3 and 6.

**Done when:** a client reports only its own output, approaching a panel raises its scale and the client re-renders sharper, a backgrounded panel's client stops redrawing at full rate while remaining responsive, and an idle lunette with only layers drawn skips scene rendering.

## Additional Considerations

**Error handling.** Native owns exactly one failure path, the load-time safe mode. Everything else is Lua's, because `lovr.errhand` is overridable and the standard library must be replaceable. Compositor-thread panics abort the process rather than poisoning shared state, since a half-dead compositor holding a Wayland socket is worse than a clean exit.

**Process lifetime.** Spawned processes are `setsid` and signalled by process group, with `PR_SET_PDEATHSIG` as a backstop. WayVR signals only the direct child (`process.rs`), which strands grandchildren behind shell wrappers. Client attribution copies WayVR's auth-key mechanism: a random key exported into the child's environment and matched against `/proc/<pid>/environ` on connection, because the connecting pid is usually not the spawned child under flatpak or a wrapper.

**Licensing.** lunette is GPL-3.0-only. Patches in `vendor/lovr` are MIT to match upstream and remain upstreamable; the fork is repointed from upstream to a lunette-owned fork before the first push. Ported WayVR files carry provenance headers, and `CREDITS.md` records what came from where.

**Deferred, with the mechanism left reachable.** Explicit sync needs an external-semaphore patch to LÖVR and is not in v1; implicit sync works on Mesa in practice, as WayVR demonstrates. Multi-plane YUV requires `VkSamplerYcbcrConversion`, which LÖVR has no concept of. Per-application spatial audio depends on the process identity machinery built in phase 2, which is why that machinery is a first-class concept rather than a private detail.

**Static linking.** v1 links LÖVR dynamically. A static build would still require `libluajit.so`, `libglfw.so`, `libmsdfgen.so`, and `libphonon.so`, because LÖVR sets `BUILD_SHARED_LIBS ON` for each, so the single-binary property is not obtained by adding a static target alone. Revisit when packaging demands it.
