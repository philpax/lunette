# Decisions and gaps

awesome being GPLv2 means its code cannot enter a GPLv3 project. This has no practical effect, because no awesome code is taken. Every layout algorithm it has is two-dimensional, and the open question in this design is what those concepts mean when the walls are wherever the user decided they are.

Credit is explicit and prominent. WayVR's contribution is not incidental: galister and contributors solved capture across every Linux compositor, worked out which OpenXR extensions function on which runtime, and found the Monado input-blocking mechanism. This design depends on that work.

## Recorded decisions

Choices made deliberately, recorded with their reasoning, so they are not relitigated by accident.

OpenXR only; OpenVR never. SteamVR does not implement `XR_EXTX_overlay`. Supporting it would require a second full backend, which would require routing XR outside LÖVR, which would make `lovr.headset` inaccurate. The architecture depends on LÖVR owning the session.

Zero-copy import over stable per-surface textures. Zero-copy is cheaper and matches what other compositors do. The stabilising copy is available as an opt-in. See [Rendering](rendering.md#texture-import) for the numbers.

Compositor off the frame thread, at the cost of Lua seeing snapshots rather than live state. WayVR ticks on the main thread and this works for WayVR; lunette does not follow that arrangement because an overlay's value depends on not disturbing the application underneath.

Rust owns the layer pool; Lua supplies the priority. Layer allocation needs one owner and a recycling policy; ranking is application knowledge. This decision was revisited mid-design: the first proposal put the pool in Lua, and layer churn is what ruled it out.

The pool recycles whole `Layer` objects, not their swapchains. The original framing put the swapchain in that role, keyed by size and format; that is the obvious framing and will be proposed again, so the reason it was not taken is recorded here. LÖVR offers no way to detach one from the other. `struct Layer` embeds its `Swapchain` by value, `lovrLayerDestroy` calls `xrDestroySwapchain` inline and unconditionally, every swapchain function is `static`, and there is no setter for the swapchain a layer's `subImage` names. Patching the fork to allow it would mean splitting `Swapchain` out into a refcounted object and rewriting `subImage` on both the quad and the cylinder structs, because `lovrLayerSetCurve` copies `subImage` between them and a stale handle left in the inactive one resurfaces on a curve change. That is a behavioural change to an existing path, which the fork discipline forbids. The original framing was wrong about the unit and right about the goal, and the goal is met exactly by keeping the whole layer: everything a panel varies has a setter and lives outside `LayerInfo`, so a layer of a given size serves any panel wanting that size, and keeping the layer alive keeps its swapchain alive. Format leaves the key for a separate reason — `lovrSwapchainInit` hard-codes `VK_FORMAT_R8G8B8A8_SRGB` and session start aborts if the runtime refuses it, so there is exactly one and nothing to key on.

mlua, not the raw C API or LuaJIT FFI. A Lua mistake must raise a catchable error, not crash the window manager.

Multi-seat by default, collapsible to one. Faking multi-seat over a single seat is the position WayVR is in; collapsing multi-seat to one seat is a small change.

Control socket over Lua eval, not a typed protocol. awesome's design has held for seventeen years. lunette changes the transport (a 0600 Unix socket, not the session D-Bus), makes it deliberate rather than incidental, and serialises properly.

Standard library on disk, not embedded. It should be legible to someone who has the binary and not the source.

Compositor tests connect over a socketpair, not a bound socket. `Connection::from_socket` and `DisplayHandle::insert_client` both take a `UnixStream` directly, so a test gives one end of a `UnixStream::pair()` to each side and the filesystem is never involved. Only the listener's own tests — bind, listen, accept, and socket-path selection — bind a real socket, in a per-test temporary directory, because that is the code under test. The real socket in [Build and development](build-and-development.md#testing) means a real Wayland connection, not a real path on disk.

The exit status is tested by spawning the binary, which is the one place a test runs a real subprocess. `boot::run` returns an `ExitCode`, which is opaque and carries no accessor, and the code that produces it cannot be reached without a live LÖVR Lua thread, so the status is observable only from outside the process. `crates/lunette/tests/exit_status.rs` runs the binary against a fixture configuration directory that opens no window and disables the audio, graphics, and headset modules, so no display, XR runtime, or sound device is needed. `lovr.filesystem.setIdentity` creates a save directory on every run and fails the boot when it cannot, so each run points `XDG_DATA_HOME` at its own temporary directory and each fixture carries a distinct identity. That keeps the write inside the temporary directory, keeps two parallel runs from racing to create one shared leaf, and makes the run independent of `HOME` and of the running uid having a passwd entry. The exception exists because reading the status from the wrong Lua stack slot once made every exit report success while the suite stayed green.

Dead handles go inert rather than raising errors. This is a compromise, made because it is less disruptive than a race condition taking down the session.

An opaque dmabuf's alpha is forced by the consumer, not by the import. This leaves the same semantic problem solved two different ways in one crate: a `wl_shm` buffer is repacked on the way in, so the padding byte becomes one during the copy and the question never reaches Lua, while a dmabuf is imported without a copy, so whatever the client left in the padding byte survives to the sampler and `window.opaque` reports that it must be ignored. The asymmetry follows from zero-copy import rather than from a preference: there is no write to the dmabuf's memory to fix it in, and adding one would give up the property the import exists for. The alternative considered was a `VkComponentMapping` on the image view, which resolves it structurally at no per-frame cost and would make `window.opaque` unnecessary. It was not taken because LÖVR creates the view itself from `TextureInfo`, so it needs a fifth patch to the fork adding a swizzle field, and the patch set is kept narrow while the milestone is still measuring. It remains the right fix if a second consumer has to repeat the shader. See [Rendering](rendering.md#alpha) for what a consumer does today.

That obligation is discharged by making composition layers opaque. A layer hands its image to the XR runtime rather than through `lovr.draw`, so no Lua consumer exists on that path and no shader runs, and the padding byte would reach the compositor as alpha. Neither of the two mechanisms named above reaches it. A `VkComponentMapping` lives on an image view, and the copy into a layer is `vkCmdCopyImage` or `vkCmdBlitImage`, both of which read the image and ignore views; and there is no way to force a component during a copy. What is left is the layer's own blend flag. `LayerProperties::PANEL` therefore clears `transparent`, LÖVR passes no `XR_COMPOSITION_LAYER_BLEND_TEXTURE_SOURCE_ALPHA_BIT`, and the runtime does not look at the layer's alpha channel at all — for every source format, before and after a client renegotiates one, with no per-frame check to bypass. Premultiplication stops being a question on this path for the same reason.

The cost is that a genuinely translucent client is composited opaque while it holds a layer. Lua chooses: a panel that wants translucency renders as an in-scene quad, where the shader path resolves alpha correctly, and one that wants sharpness claims a layer. Making transparency a per-claim property was considered and rejected: the key is fixed when the claim is made, a client's format changes under it, and a layer that had become wrong for its source would have to be revoked from the blit path rather than from the ranking.

The layer path does not use smithay's `RendererSurfaceState` for damage. `on_commit_buffer_handler` is what populates it, and its first act is `attrs.buffer.take()` — the same buffer `CompositorState::apply_commit` reads to perform the import. Calling it first, as smithay documents, therefore leaves the import path with nothing to import and no client ever displays anything; reading the buffer back out of `RendererSurfaceState` instead would move buffer ownership to smithay, which releases a `wl_buffer` when it drops its own `Arc`, and lunette already releases the same buffer itself. So lunette counts its own installs instead: `TextureLedger` stamps every texture it installs with a `SurfaceCommit` drawn from one counter for the whole session, and the blit path copies when the stamp behind a claim differs from the one it last copied. That predicate is also strictly better than the one smithay offers, because `DamageSnapshot::add` returns without incrementing when a commit posted no non-empty rectangle, so a new buffer with no damage moves neither the counter nor the damage set, while counting installs sees it.

Monitors are correlated to portal streams by logical geometry, not by the portal's `mapping_id`. `mapping_id` looks like exactly the right tool and will be proposed again, so the evidence is recorded here. It was introduced in ScreenCast portal version 5 to match a libei region in a RemoteDesktop session, not to name an output, and its content is backend-defined. xdg-desktop-portal-wlr sets it to the `wl_output` name, which on wlroots is the DRM connector name (`src/screencast/screencast.c:666-668`) — the case that makes it look right. mutter sets it to `g_uuid_string_random()` from a per-EIS table (`src/backends/meta-eis.c:526-538`), which names nothing and changes every session, and emits it only when the ScreenCast session is attached to a RemoteDesktop session (`src/backends/meta-screen-cast-stream.c:426-440`); a plain ScreenCast session on GNOME gets none. xdg-desktop-portal-kde never emits it. So the field yields a connector name on wlroots, an unstable random string on GNOME under one session shape, and nothing on KDE. The portable mechanism is correlating each stream's `position` and `size` against `wl_output` logical geometry, which is what wlx-overlay-s itself does. `mapping_id` is not read at all, because `wl_output.name` supersedes it: version 4 of `wl_output` added a `name` event whose documented content is the connector name, and both wlroots and mutter send it. That is a real connector name on every backend rather than on one, and it arrives from the compositor lunette is already talking to rather than from the portal. It is still parsed against the kernel's list of connector types before being stored, because a compositor is free to put anything there and a name that is not a connector must not be recorded as one.

Monitor identity is make and model, then connector, then position, and is weaker than a compositor's. A Wayland client cannot read a serial: the `wl_output.geometry` event carries make and model only, and the EDID blob is available to whoever owns the DRM device. niri, which does own it, keys on `"{make} {model} {serial}"` and falls back to the connector. lunette copies that shape without the serial, so two monitors of the same model report one descriptor and cannot be told apart by it. The later of the two is therefore demoted to its connector alone, following niri's rule for the case where a serial does collide; where no connector is available either — GNOME or KDE with two identical monitors — the fallback is the monitor's logical position, and lunette warns that the identity will not survive the monitors being rearranged. The alternative is silence, and a mirrored monitor attaching to the wrong screen after a restart is confusing in a way an explicit warning is not.

The host's outputs are enumerated with `wayland-client` directly rather than through `wlx-capture`'s `WlxClient`. `WlxClient` connects through `WAYLAND_DISPLAY` itself and takes no socket parameter, and `CONTRIBUTING.md` forbids a library reading the environment. That is not a stylistic objection here: lunette's entry point overwrites `WAYLAND_DISPLAY` with lunette's own socket before any other thread exists, because it has to be written while the process is single-threaded, so anything reading the variable afterwards enumerates lunette's compositor and finds one virtual output. The socket is therefore resolved by the binary before that write and passed down as a path, which is the arrangement `WlVirtualConfig` already uses for the same reason. Writing the enumeration against `wayland-client` also costs nothing: it is already in the tree, `WlxClient` carries a dmabuf and screencopy client lunette has no use for, and the eight events that matter are `wl_output`'s `geometry`, `mode`, `scale`, and `name`, plus `zxdg_output_v1`'s `logical_position` and `logical_size`.

A mirrored monitor's textures are a separate ledger from a surface's, keyed by monitor identity. Reusing `TextureLedger` would mean parameterising it over its key, and the two ledgers want different bookkeeping rather than the same bookkeeping under two keys: a surface carries a death flag, a damage flag, a stabilised copy, and a retirement schedule, because a client can exit mid-frame and Lua can ask for a copy that outlives the frame, and a monitor has none of those. What a monitor's ledger needs and a surface's does not is the image handle behind the texture, because the dmabuf importer answers a recurring PipeWire buffer with the image it already made — so without recording which image is installed, every frame from a recycled buffer would allocate a fresh texture over memory a texture already covers.

Restore tokens are stored in a versioned file that an older lunette refuses to rewrite. The portal's restore token is single-use: the backend invalidates the one it was given and returns a new one in every `Start` response, so the store is rewritten after every grant rather than only when nothing was held. The granted `persist_mode` is recorded, never the requested one, because a backend may downgrade it and xdg-desktop-portal-wlr does (`src/screencast/screencast.c:171-181`). The file declares a format version, and a file from a later version yields no store at all rather than an empty one; the case that corrupts rather than fails is an old writer rendering its own fields over a newer file, which drops everything it does not know about. Anything unrecognised within a version this lunette does understand is refused rather than ignored, for the same reason: a field silently dropped on read is a field lost on the next write. The format is TOML, because the file holds a monitor's make and model, which is whatever its EDID says, and quoting arbitrary text is not worth handrolling.

A selection transfer passes the descriptor rather than copying the bytes. lunette never buffers a clipboard's content and never reads or writes a selection pipe. A lunette client pasting supplies a pipe to `wl_data_offer.receive`; smithay hands that descriptor to `SelectionHandler::send_selection`, and it is forwarded unread to `ext_data_control_offer_v1.receive` on the host connection, so the host's own clipboard owner writes into the lunette client's pipe. The host pasting supplies a pipe to lunette's data-control source; the descriptor crosses back to the compositor thread and is handed to `request_data_device_client_selection`, so the lunette client that owns the data writes into the host's pipe. The alternative is what WayVR does (`comp.rs:365-383`): read the bytes, hold them, and spawn a detached thread per request to write them out, with no join, no bound, and no cancellation, so a client requesting the selection in a loop spawns threads without limit. Passing the descriptor removes the whole class of problem rather than bounding it — there is no buffer to size, no worker to schedule, and a client that never reads its pipe stalls only the process that owns the data, exactly as it would with no lunette in the middle. It also removes format negotiation: the MIME list is re-offered exactly as the source advertised it, in both directions, so nothing is substituted and nothing is dropped, and a request for a type the offer does not carry is refused rather than answered with the nearest thing. The cost is that the two ends must both be alive for a transfer to complete, which is already true of any Wayland selection, and that a stale `wl_data_offer` has to be distinguished from a current one: each announcement from the host carries a strictly increasing identifier, and a read quoting a superseded one is refused rather than answered with what the user copied afterwards.

One designated bridge seat for the host clipboard, rather than last writer wins. With one seat per hand, each seat owns a clipboard and a primary selection while the host owns exactly one of each. Letting every seat write the host's clipboard means two hands copying in quick succession race, and which one the host ends up holding depends on the order two commands reach the compositor thread — timing the user cannot see and cannot control, producing a paste of the wrong thing with no way to tell why. Reading is worse: every seat would be offered the same host selection, so the two hands would silently share a clipboard that the rest of the model says is per-seat. One seat is therefore bridged in both directions and the others keep selections that stay inside lunette, which is the arrangement a user can predict — the bridged hand is the one that talks to the desktop. The default is the seat every session starts with, so a configuration that never mentions the clipboard behaves as a single-seat compositor does, and `seat:setClipboardBridge` moves it because which hand is the desktop's is policy. The alternative considered and not taken was merging the two: bridging every seat's clipboard onto the host and reflecting the host's onto all of them. That is last writer wins with extra steps, and it also makes a seat's clipboard change under it because another hand copied.

One layout group per seat, and a configuration naming more than one is refused. Every keymap query in the compositor resolves against layout group zero, and nothing in the API carries a group: `seat:strokeFor` answers with a keycode and modifiers, and `sink:key` takes a keycode. smithay's own keyboard state does track a group and applies layout-switch actions from the keymap, so a seat compiled with `us,de` and `grp:alt_shift_toggle` would have every answer silently drift the moment the user toggled — `sink:typeText('yz')` would emit the keycodes that spell `zy`. The choices were to model the group throughout, threading it through the snapshot, the query signatures, and the typing planner, and to read it back from `KeyboardHandle::with_xkb_state`; or to refuse the configuration. Refusing was taken, because there is no way to *set* the group either, so modelling it would add a parameter nothing could yet control. Lifting it means adding the group to `SeatSnapshot`, to every `Keymap` query, and to `type_text::plan`, plus a way for Lua to read and set it. A configuration wanting a second layout today creates a second seat.

The refusal applies only to a layout a configuration named. A desktop's own default reaches lunette through `XKB_DEFAULT_LAYOUT`, and naming several layouts there is ordinary: NixOS writes the list from `services.xserver.xkb.layout`, and sway and Hyprland export it the same way. Refusing an inherited list would take away the seat of a user who wrote no layout line at all, and a session with no seat has no keyboard, no pointer, and no clipboard. An inherited list is therefore narrowed to its first entry, with the matching variant, and the narrowing is logged with the advice that a second layout wants a second seat. The five `XKB_DEFAULT_*` variables are read by the binary and passed to the compositor as `KeymapDefaults`, rather than left to libxkbcommon to resolve from an empty name. That is what makes the narrowing possible: libxkbcommon offers no way to ask a compiled keymap which RMLVO layout produced it, so a keymap compiled from an empty name cannot be cut down afterwards. It also keeps the compositor crate free of environment reads, so a test states the inherited default rather than depending on the machine it runs on.

The host clipboard's echo is suppressed by ownership, and the suppression is logged. Publishing a selection to the host makes the host announce that selection back on lunette's own data-control device, because a data-control device sees every selection including the ones it set. Re-offering it would replace the lunette client's source with a proxy of itself, so an announcement arriving while lunette owns a live source for that kind is discarded. That rests on the host cancelling a source before announcing the one that replaced it, which is what smithay and wlroots both do and what neither `ext-data-control-v1` nor `zwlr-data-control-v1` states. A host that announced first would have a genuine selection discarded, and lunette's clients would keep pasting the previous one until the next copy — silent, sticky, and indistinguishable from a broken bridge. The alternative considered was a nonce MIME type appended to what lunette publishes, which an echo would carry back and a genuine selection could not. It was not taken because it gives up the property that lunette re-offers a source's own list unchanged, which is the same property that makes the rest of the clipboard path free of substitution. What was taken instead is a warning on every discard, naming the MIME list, so a gate on a real desktop can tell a compositor that announces out of order from a bridge that is broken.

Only a selection lunette owns is ever withdrawn or cleared. `set_selection(null)` is not "stop offering mine" in either data-control protocol: wlroots passes the null straight to `wlr_seat_request_set_selection` and smithay does the same, so it unsets the seat's selection whoever owns it. Sending one while the user's own copy sits on the host clipboard would empty their desktop's clipboard, on an operation both documents describe as safe to call freely. So the bridge records which selections lunette published and withdraws only those, and the compositor clears a seat's selection only when `current_data_device_selection_userdata` reports it as compositor-owned — which is exactly "lunette put this here from the host". A selection a lunette client set is that client's, and moving or removing the bridge is not a reason to destroy it.

Per-window state lives in a native store as well as in `win.userdata`, and the redundancy is the point. `userdata` is a Lua table on a Lua handle, and a soft reload discards the Lua state, so nothing in it survives one. That is the right lifetime for most of what a configuration attaches: state a rule derived comes back when the rules re-run, and keeping a stale copy of it across a reload would defeat the reload. What it is the wrong lifetime for is state no rule can derive — a pose the user placed by hand, a size they dragged, a tag they assigned by hand — which a reload that lost it would scramble, on the one operation the design promises is instant and invisible. So `win:setProperty` and `win:getProperty` keep those in Rust, where the reload cannot reach. The lineage is awesome's, which keeps per-client state in X properties on the window because those outlive the window manager's own process and lets a restart skip or alter rule application when it finds some; lunette has no X server, so the store is native. The store holds a number, a string, or a boolean and refuses a table by name, because a table would hold Lua values and put the same problem one level down; a caller wanting structure encodes it into a string and knows that it did. The alternative considered was making `userdata` itself survive by serialising it at teardown, and it was not taken for that reason — it can hold a function, a coroutine, or a handle, none of which serialises, so it would either fail on ordinary contents or silently drop them. Entries are keyed by `WindowId` and last as long as the window, which works because a soft reload does not restart the compositor thread and so does not change an identifier. A hard restart does, and anything that has to cross one is `mullion`'s to write to disk under a key the compositor did not mint.

The standard library is mounted by wrapping the `package.preload` entry LÖVR builds `lovr.filesystem` from. `vendor/lovr/etc/boot.lua:76` creates that module and `:183` requires `main.lua`, both on the first resume of the coroutine the host drives, so there is no moment between them the host can reach from outside: before the resume the module does not exist, and after it the configuration has already run. Wrapping the loader puts the mount between the two, which is what a configuration whose first line is `require 'mullion'` needs. The wrapper is a C closure holding the original loader and the path as Lua upvalues rather than a Rust closure holding Lua values, so Rust keeps no reference into a state a soft reload will discard. The alternatives considered were pointing `package.path` at the tree, which works but takes the standard library out of the virtual filesystem the rest of the session reads through, and patching `boot.lua`, which is upstream's file and would make every LÖVR bump a merge.

Resolution has two candidates and no third: `LUNETTE_STDLIB_PATH` when it is set, and `$PREFIX/share/lunette/lua` otherwise. A relative override is taken as it stands, unlike the XDG variables, because pointing the variable at a working tree is the whole development loop for `mullion`. A `./lua` fallback was considered, so that a build tree worked without the variable, and was not taken: it makes what a session loads depend on the directory it happened to be started from, which is a property no user can see and no configuration can state.

The shipped configuration sets `saveprecedence = false`, which LÖVR defaults to true. The default mounts the save directory ahead of every other archive, so a file written there shadows the one it is named after — the mechanism a packaged LÖVR application is patched through. For lunette it is a trap: a session that writes `mullion/init.lua` or `main.lua` into its save directory replaces the standard library or the configuration for every session after it, and a reload cannot undo it because the reload reads the shadowing copy too. Turning it off leaves the save directory mounted and readable and only stops it winning a name collision. The mount itself is read-only regardless, since a physfs mount is: `lovr.filesystem.write` cannot modify a file in the standard library on disk. A configuration that sets `saveprecedence` back to true gets LÖVR's behaviour and the hazard with it.

Safe mode is a Lua chunk compiled into the binary, not a file installed beside the default configuration. It exists for the moment `main.lua` fails to load, and a broken standard library, a missing install, or a `LUNETTE_STDLIB_PATH` pointing at nothing is one of the reasons it might have — so a fallback that read anything off disk would be unavailable in a fair share of the cases it exists for. It therefore requires `lunette` and nothing else, never `mullion`, and does its own ray-plane solve for one fixed axis-aligned panel rather than reaching for `mullion.panel`. That duplicates a little of the shipped configuration, which is the price of always working, and both sites say so, so neither is later simplified by pointing at the other. `crates/lunette/src/safe_mode.lua` is the chunk and `safe_mode.rs` embeds it with `include_str!`, so it stays a Lua file that an editor highlights and a diff can be read against `etc/xdg/lunette/main.lua`. The alternative considered was installing it as a third file under `$SYSCONFDIR`, which reads better and fails in exactly the case the feature is for.

## Known gaps

Named, not solved.

There is no flake package output, so `nix build` produces nothing and the install path is the `Makefile`. The blocker is the one [Build and development](build-and-development.md#nix) already names: LÖVR's `deps/` are nested submodules, and a flake source does not carry submodules unless it is fetched with `submodules=1`, so a derivation building from `./.` would find `vendor/lovr` empty. The `Makefile` installs the binary, the LÖVR shared libraries, the standard library, and the default configuration at the documented paths, and an installed tree resolves its own libraries through the executable's `$ORIGIN/../lib/lunette` rpath entry.

A captured frame is imported only as a dmabuf. PipeWire can negotiate shared memory instead, as a memfd or a mapped pointer, and lunette refuses both by name rather than showing a black mirror. The mapped-pointer case is the awkward one: the pointer is valid only inside PipeWire's callback, so supporting it means copying every frame on the capture thread, which is the one thing the raw-forwarding arrangement exists to avoid. The refusal is counted and logged once per stream rather than per frame.

wlx-capture discards the granted `persist_mode` before lunette can read it. `parse_start_response` (`wlx-capture/src/pipewire/mod.rs:686-691`) reads `streams` and `restore_token` and drops it, so lunette records that the backend stated no persistence rather than what it granted. It is an upstream change and it is not load-bearing — a stated persistence mode is a diagnostic — and the seam models the field, so lifting it upstream is a change to one adapter. `parse_streams` (`mod.rs:693-733`) likewise drops `mapping_id`, which no longer matters: the connector name comes from `wl_output.name`.

A rotated monitor's reported resolution is the panel's mode, unrotated. `wl_output.mode` describes the panel, and whether a capture stream of a rotated output delivers frames in the panel's orientation or the desktop's has not been verified on any backend. The stream reports its own frame size and that is what the texture ends up being; `monitor.width` and `monitor.height` report the mode. The two agree on every unrotated monitor, which is every monitor observed so far.

Host-to-lunette drag-and-drop. No protocol exists for a drag crossing a compositor boundary. In-compositor drag-and-drop works.

Input blocking is Monado-only. `libmonado`'s `BlockFlags` has no OpenXR-standard equivalent. On other runtimes, clicking a panel also reaches the application underneath.

Multi-planar YUV costs a conversion. LÖVR has no `VkSamplerYcbcrConversion`. This affects hardware-decoded video and some capture formats.

Implicit sync only, for now. This works on Mesa in practice, as WayVR demonstrates. Explicit sync needs a LÖVR patch.

Dynamic output scale makes some clients flicker. GTK in particular re-lays-out aggressively. This is mitigated by discrete steps and hysteresis in Lua, not eliminated.

Multi-seat is less-travelled ground. Toolkit bugs around popup grabs and drag-and-drop ownership are expected.

XWayland semantics are whatever `xwayland-satellite` provides. Override-redirect windows, `_NET_WM` hints, and transient-for relationships are mapped onto xdg-shell approximately.

The `lovr.lun*` prefix squats in LÖVR's callback namespace permanently. It is distinctive enough that a collision is unlikely, but this remains an assumption rather than a guarantee.

`lunctl` has root-equivalent access to the session. Anything that can write to the socket controls the machine. This follows from the single-user assumption, stated explicitly, and the socket is never network-reachable.

Soft reload can leak. Timers, signal connections, and coroutines from a previous config persist unless torn down. `mullion` provides the hook; nothing forces its use.

No sandboxing. Spawned applications are as privileged as lunette.

## Deliberately left open

`lovr.thread` and `lovr.task` access. The lunette API is main-state only. There may eventually be a use for read-only snapshot access from worker states. The ownership rules in [Architecture](architecture.md#ownership-rules) do not preclude it, but nothing is designed for it yet.

2D widget toolkit. Deferred, and may end up as a recommended separate library rather than part of `mullion`. Ambitious UI should be a real Wayland client, spawned rather than built in.

Layout algorithms. There is no prior implementation to copy and no comparable system to consult.

## Imported images are abandoned at a restart, not destroyed

Decided 2026-08-07, building Phase 7 Task 3.

A restart destroys the `VkDevice` every imported image was created against, so the images have to be dealt with before `luax_close` runs. They are forgotten rather than destroyed.

Destroying them there would be invalid. LÖVR retires an imported texture's image *view* through its own morgue, and that morgue is emptied only by `gpu_destroy`; `vkDestroyImage` on an image that still has a view is not allowed. The deferral that makes this work in an ordinary frame counts in frames, and a restart has no further frames of that device to count. This is the same reasoning Phase 2 recorded for shutdown, and the answer is the same.

Nothing is leaked: `vkDestroyDevice` frees what the device still owns, and it runs moments later. What forgetting buys is the thing that would otherwise be a defect rather than an untidiness — no handle from the old device survives into the new one's lifetime, where destroying it would be a use-after-free against a device that never created it.

The alternative considered was flushing LÖVR's morgue before the teardown. LÖVR exposes no way to do that, and adding one would be a behavioural patch to an existing path, which `CONTRIBUTING.md` rules out for the fork.

## The lunctl time budget is best-effort

Decided 2026-08-06, built in Phase 7 Task 6.

A `lunctl` chunk runs under a LuaJIT count hook that raises once the wall clock passes its budget. Two things escape it, and neither is fixable from inside Lua.

JIT-compiled code does not call debug hooks. A trace in a tight loop never returns to the interpreter, so the hook never fires. `jit.off(chunk, true)` is applied to the loaded chunk to force interpretation, which makes the hook reliable; the cost is irrelevant, because a control-plane chunk is not a hot path. Building LuaJIT with `-DLUAJIT_ENABLE_CHECKHOOK` would remove the need for that, and would slow the whole session to bound one feature.

Even interpreted, the bound stays advisory. An `error()` raised from a hook is catchable, so a `pcall` inside the user's own chunk swallows it; and a loop inside a C function, or a blocking FFI call, is uninterruptible by any hook.

A hard bound would need a watchdog outside Lua. Since the chunk holds the Lua thread, the only thing such a watchdog could do is abort the process — turning a bad `lunctl` command into a crash that takes every connected client with it. That is worse than the hang it prevents, so it is not built. `lunette-v1.AC8.2`'s first clause is stated as best-effort in the design plan for the same reason, and the tests assert the escape as the behaviour it is rather than as an aspiration.

## lunctl refuses what it cannot represent

Decided 2026-08-07, building Phase 7 Task 7.

A serialiser meets values with no wire form: functions, coroutines, userdata that is not a lunette handle, and table or function keys. It errors on each, naming the path to the offending value, rather than falling back to `tostring`. Dropping content silently is a correctness bug per `CONTRIBUTING.md`, and the `tostring` fallback is exactly what [the Lua API](lua-api.md#lunctl) criticises awesome's remote control for.

Three further cases needed an answer, and each is a source of silent corruption if left implicit.

**A cycle is an error, not a back-reference.** A back-reference would be more faithful, and it would make the value tree a graph that every consumer — including `lunctl`'s own renderer — has to be total over. A `lunctl` chunk that wants to inspect a cyclic structure can break the cycle itself; a renderer that has to guard against one cannot.

**Shared subtables are duplicated, and identity is not preserved.** That follows from the choice above: without back-references there is nothing to share with. The node cap is what keeps a wide directed acyclic graph from expanding without bound, and it produces a clean error rather than an allocation failure.

**Metamethods are not honoured.** Traversal is raw, so what is serialised is what the table actually holds. `__index` can fabricate fields that do not exist and `__pairs` can hide ones that do, and a wire format whose contents depend on which of those a caller happened to install is not an inspection tool.

A handle serialises as its kind and the identity the session keys it on, never as `tostring(handle)`. Addresses are reused after collection, so an id derived from one could come to refer to a different object — a defect that appears only under memory pressure. The identity is `win.id` and its siblings, which Phase 6 recorded as the stable thing; the userdata itself is minted fresh on every read and is not identity-stable at all.

## Errors, safe mode, and the end-to-end harness

The native side of the callback boundary rate-limits nothing. `crates/lunette/src/callback_error.rs` splits the message from the traceback and hands both to `mullion.error`, which owns the limiter, the wording, and the panel. Two limiters keyed differently would produce gaps that neither of them explains: an occurrence suppressed natively never reaches the Lua one, whose window then starts from the wrong occurrence. The cost is that a session with no standard library loaded has no limiter at all, and logs an error raised every frame every frame. That is stated in [the Lua API](lua-api.md#errors) rather than papered over.

The error panel is a module of its own, `mullion.error.panel`, rather than part of `mullion.error`. Drawing needs a `Pass` and reporting does not, and `mullion.error` is loaded by sessions that switch the graphics module off — the spec run is one. It wraps the handler's documented `report` seam rather than being wired in from the handler, so a configuration that wants a different error surface leaves it out instead of displacing it.

Safe mode is triggered by wrapping `lovr.boot`, not by installing a `lovr.errhand`. `lovr.boot` is the one function whose failure means the configuration did not load; everything that is not a load failure happens after it has returned the frame loop, so the wrapper cannot mistake one for the other. `lovr.errhand` is reached by every error that escaped a callback boundary and belongs to the configuration — `mullion.error` installs one — so taking it would both over-trigger and displace policy.

The end-to-end tests are Rust and not the shell script [build and development](build-and-development.md#testing) originally described. They drive the same two binaries over the same socket; a shell script would add a second harness to keep in step and report failures worse. The part of that description that is not yet met is the client: a headless fixture switches the graphics module off, so no device is lent to the compositor thread, the thread does not start, and nothing can connect to the Wayland socket. That half needs the GPU-headless tier and is recorded as a gate in [milestone 0 findings](milestone-0-findings.md#outstanding) until it exists.
