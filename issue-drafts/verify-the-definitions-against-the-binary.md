# Check the generated definitions against the running binary

Labels: enhancement

## Current state

`etc/lunette/definitions.luau` declares the runtime that `lunette check` and a user's editor check Lua against. It is generated by `crates/lunette-generate-definitions` from the lovr-docs metadata, and nothing compares it against what the binary exposes.

The mismatch occurs in both directions, and both have already happened. A declaration for something absent from the runtime passes the check and surfaces as an error only when a session runs: `io`, `lovr.vector`, and `lovr.quaternion` were each declared and absent, and the `io` declaration hid four crashes in mullion's error paths until the binary was probed by hand. Something present and undeclared is invisible to the checker and to an editor, which is the larger gap: the runtime's global `vector` exposes around thirty members against the eleven lovr-docs documents.

The `lunette` module's own declarations are covered elsewhere. `lua/lunette/init.luau` is generated from the Rust registration surface, where a property is declared beside the closure that answers it, so the two cannot disagree. What remains is the LÖVR half.

## Change

A test instantiates a Luau state from the binary, with the `lovr` modules registered as a session registers them, and compares the live surface against `etc/lunette/definitions.luau` in each direction.

Present-but-undeclared is the cheaper half: walk the live tables and look for each key in the definitions. Declared-but-absent needs the definitions parsed, which means enumerating declarations through Luau's AST in `crates/lunette-lovr/src/analyze.cpp`. That half is the one that catches a declaration with nothing behind it, which is the `io` case, so it stays.

A regular expression over the definitions text does not substitute for the AST. The declarations nest, carry intersections that span lines, and are generated, so a pattern over the text would break on a generator change and keep passing on a runtime change, which reverses what the check is for.

lovr-docs' own `api/main.lua` validates its metadata against a live `lovr` table as it aggregates, and `lunette-generate-definitions` runs it. That covers part of the LÖVR half already, under a flag that is off, and reading it before writing a second implementation is worthwhile.

## Done when

`cargo test --workspace` fails if the `lovr` runtime carries a name the definitions do not declare, and fails if a declaration names something the runtime does not carry.
